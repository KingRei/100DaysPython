Day 22 — 不用比較的排序：counting、radix、bucket

程式碼：day 22 on GitHub

100 Days of Python - day 22

到目前為止這個系列裡的每一種排序，都只問一種問題：a 是不是小於 b？只問這個問題，就有一個 下限。排序演算法可以看成一棵決策樹，它必須有辦法走到全部 n! 種排列，而有 n! 片葉子的二元樹 至少 log2(n!) 深，這個值就是 n log n。我實際量了 merge sort 離自己的下限有多遠：

n =      16:  log2(n!) =        44   merge sort 用了        48   (1.08x)
n =   1,000:  log2(n!) =     8,529   merge sort 用了     8,690   (1.02x)
n = 100,000:  log2(n!) = 1,516,704   merge sort 用了 1,536,501   (1.01x)

只差 1%。也就是說，比較排序這條路上已經沒有什麼聰明的空間了，唯一還能往下的方法，是不要再問 那個問題。今天講的就是三個不問的演算法，外加一個我工作上天天在看、結果它本質上就是其中之一的 kernel。

昨天講的是 selection：因為只要 top k，所以不用排序。今天是另一個出口 - 東西還是全部排好，只是 從頭到尾沒有比較過。

Counting sort：直方圖就是位址表

如果 key 本來就是 0..k-1 的整數，那它本身就是一個位址。數、scan、散，三步。

def counting_sort(keys, k, payload):
    counts = [0] * k
    for v in keys:                 # count
        counts[v] += 1
    total, starts = 0, [0] * k     # scan
    for v in range(k):
        starts[v] = total
        total += counts[v]
    out = [None] * len(keys)       # scatter
    cursor = list(starts)
    for i, v in enumerate(keys):
        out[cursor[v]] = payload[i]
        cursor[v] += 1
    return out

中間那個迴圈就是整件事的重點。做 scan 之前，第 v 格的意思是「有幾個 v」；做完之後，它的意思 變成「有幾個元素排在第一個 v 前面」- 也就是 v 這一桶的起始位址。直方圖變成了位址表， 接下來的 scatter 只是往一個算出來的索引寫值而已。全程沒有比較，所以 n log n 那個下限根本套不 上來 - 下限講的是「只能問 a &lt; b」這個模型，不是排序這件事。

這裡順帶掉出兩個性質。第一，它本質上是個排列（permutation），所以任何跟 key 同索引的 payload 都能免費跟著搬。第二，它是穩定的：我們從左往右掃輸入，cursor 也往右長，所以相同 key 的元素會保持原本的順序。現在看起來只是個好性質 - 等一下它會變成正確性條件。

成本是 2n + k，而那個 k 不是裝飾。k 是 key 空間的大小，不是元素個數。用 counting sort 排一萬個 32-bit 整數，等於要開 43 億個桶，而且幾乎全都是 0。

Radix sort：用趟數換桶數

保留 counting sort，自己動手把 k 縮小：一次只排幾個 bit，從最低位開始，每個 digit 跑一趟穩定的 counting sort。

圖的上半是 4-bit 的值、2-bit 的 digit 的正確 LSD radix sort。最下面那一列是同一份程式碼，只改 一件事：每一桶從後往前填，而不是從前往後。單獨看，那仍然是對某個 digit 的正確排序。但是連跑 兩趟之後，整個陣列沒有排好：

stable   passes: 3137 3729 17269 20628 24236 36059 42072 49669 51152 54485 61495 64703
unstable passes: 3729 3137 17269 24236 20628 36059 42072 51152 49669 54485 64703 61495
sorted?  False

第二趟把第一趟剛排好的低位順序反轉掉了，而且沒有任何後面的趟能救回來 - 資訊已經丟了。所以 在 radix sort 裡，stable 不是「有比較好」的性質，它就是這個演算法會對的唯一理由。這也是為什麼 GPU 的實作寧可花力氣讓每個 thread 維持自己的 cursor，而不是讓 atomicAdd 去決定誰拿到哪個位置。

那 digit 到底該多寬？教科書的模型是「一趟一份直方圖」，算出來會說 16 bit 最好。但真實的實作是 一個 tile 一份直方圖，因為只有這樣計數器才待得住快速記憶體 - 一個 thread block 只有 64 KB shared memory，而 65,536 格的 32-bit 直方圖要 256 KB。誠實一點的模型是 work = passes * (2n + tiles * 2**r)，一百萬個 32-bit key、tile 大小 1,024：

r =  4 bits:  8 趟 x     16 桶  ->  work =  16,125,056   直方圖      0 KB  放得下
r =  8 bits:  4 趟 x    256 桶  ->  work =   9,000,448   直方圖      1 KB  放得下
r = 11 bits:  3 趟 x  2,048 桶  ->  work =  12,002,688   直方圖      8 KB  放得下
r = 16 bits:  2 趟 x 65,536 桶  ->  work = 132,057,344   直方圖    256 KB  放不下

誠實的模型給的答案是 8 bit，4 bit 緊追在後 - 這剛好就是實務上 radix sort 待的那個區間。不誠實的 模型則會推薦一個硬體根本放不下的選項。

用 radix sort 排浮點數還需要一樣東西：保序的 key。IEEE-754 的原始 bit 會把所有負數排在所有 正數上面，而且負數之間還是反的，因為 sign bit 是個旗標、不是最高位。把正數的 sign bit 翻掉、負數 的 32 個 bit 全翻，unsigned 的順序就跟數值順序一致了 - 跟 day 21 radix select 用的是同一把 key。 一旦比較變成計數，所有東西都得先變成整數。

Bucket sort 賭的是分布

第三個演算法不再把 key 當位址，而是當估計值：把值線性縮放進 m 個桶，桶內用什麼排法都行，最後 接起來。同樣的程式碼、同樣的 n、同樣 2,000 個桶，換兩種輸入：

均勻分布: 最滿的桶   6 / 2,000   空桶   756   桶內排序搬移     551 次
擠成一團: 最滿的桶 132 / 2,000   空桶 1,956   桶內排序搬移  47,038 次

沒有任何錯誤訊息。那個「線性」的排序只是安靜地變成了平方，因為幾乎所有元素都落在同一個桶裡，而 桶內排序是 O(len**2)。bucket sort 沒有在排資料，它是在賭分布；均勻這個假設是對輸入的前置 條件，不是分析裡的一行註腳。GPU 上每次按 key range 去 partition 資料，下的是同一個賭注 - 資料 一歪，拿到胖桶的那些 block 就變成長尾。

中間那個 scan 才是難的地方

數是一個 thread 一個元素，散也是一個 thread 一個元素。夾在中間的 prefix sum 不是：starts[v] 要讀上一輪剛寫進去的值，這就是序列的定義。整個平行排序的難點，全部縮在這一行裡。

n = 1,024      sequential      1,023 次加法 / 深度 1,023
               Hillis-Steele   9,217 次加法 / 深度    10
               Blelloch        2,046 次加法 / 深度    20

這幾個數字要仔細看，因為它跟大家想像中的「平行」不太一樣：兩種平行 scan 做的加法都比它取代掉的 序列迴圈還多。Hillis-Steele 每一輪把 stride 加倍、所有元素同時加上左邊 off 格，用 n log n 的 work 換到 log n 的 depth。Blelloch 上掃時蓋一棵 reduction tree（n/2 + n/4 + ... = n-1 次 加法），下掃再把部分和推回去，用線性的 work 拿到同一個 depth 等級。兩個在序列上都沒有比較快，它們 會贏，唯一的理由是那些 lane 本來就閒著 - 這就是 work-depth 的取捨，也是為什麼在 GPU 上「總共做 幾次運算」不再是對的問題。

Blelloch 還要求長度是 2 的冪，這就是為什麼 sglang 的 MoE kernel 在 HIP path 上會先把 expert 的 直方圖補零到 2 的冪再 scan。演算法的限制會一路長進 kernel 的參數裡。

真的 kernel：moe_align_block_size 就是一個 counting sort

每個 MoE 模型的每一步 decode 都會跑這個東西。router 說每個 token 要送去哪些 expert；而 grouped GEMM 要求同一個 expert 的 token 連續、而且對齊固定的 block size。expert id 是小整數 - 所以 這就是一個 counting sort。

用純 Python 重現 sglang docstring 裡那個範例，一模一樣：

topk_ids         [[2, 3, 4], [1, 2, 4], [1, 3, 4], [1, 2, 3]]   block_size = 4
展平後            [2, 3, 4, 1, 2, 4, 1, 3, 4, 1, 2, 3]
counts           [0, 3, 3, 3, 3]
padded           [0, 4, 4, 4, 4]
prefix           [0, 0, 4, 8, 12, 16]
sorted_token_ids [3, 6, 9, 12, 0, 4, 10, 12, 1, 7, 11, 12, 2, 5, 8, 12]
expert_ids       [1, 2, 3, 4]

跟教科書版比只多兩件事。第一，每一桶在 scan 之前先無條件進位到 block_size，於是每個 expert 的區段都從 block 邊界開始；補出來的洞先填上 token id 12 - 也就是最後一個 token 再加一 - 讓 GEMM 整塊讀進來之後再 mask 掉。真的 kernel 更狠：用一整個獨立的 thread block、以 int4 向量寫入去鋪這 些 sentinel，跟直方圖同時進行，反正兩件事互不相干。

第二，expert_ids（第 b 個 block 屬於哪個 expert）根本不用另外算，直接拿同一個 prefix 陣列做二分 搜尋就好。那個陣列從一次 scan 得到，卻做了三份工：scatter 的桶起點、scatter 過程中會移動的 cursor、 以及之後二分搜尋的 key。

sgl-kernel 為這一個函式準備了兩個 kernel，理由跟 day 21 碰到的非決定性是同一個。atomicAdd 版本每次跑出來的排列都不一樣（但每一個都是正確的排列）；per-thread histogram 版本則可重現。兩者 都餵給同一個 GEMM，因為 GEMM 的列根本不在乎自己是以什麼順序進來的。切換條件寫死在程式碼裡： topk_ids.numel() < 1024 && num_experts <= 64 - 小 batch 拿決定性，大 batch 拿 atomic。

實際尺寸下（4,096 個 token、256 個 expert 取 top-8、block 64），32,768 個 routed token 會變成 40,704 個 slot，其中 19.5% 是 padding。那就是固定 block size 的價格，而 counting sort 的工作， 正是把資料排成讓這個價格付得下去的樣子。

LeetCode 75 - Sort Colors

兩趟（三個計數器的直方圖 + 重寫），或者一趟（三個指標）。follow-up 要的是一趟版本，而它難在一個 不對稱：從高位換下來的值還沒被檢查過，所以那一步 mid 不能前進；從低位換上去的值則已經看過了。

def sort_colors(nums):
    low, mid, high = 0, 0, len(nums) - 1
    while mid <= high:
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1; mid += 1
        elif nums[mid] == 2:
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1              # 不能 mid += 1
        else:
            mid += 1

LeetCode 164 - Maximum Gap

「排序後相鄰兩數的最大差，而且要 O(n)」，翻譯過來就是「不准真的排序」。把 n 個數丟進 n-1 個寬度為 ceil((max - min) / (n - 1)) 的桶，鴿籠原理保證至少有一個桶是空的，所以最大 gap 至少有一個 桶那麼寬，因此它不可能落在同一個桶裡面。每個桶只留 min 和 max，其他值直接扔掉，最後掃一次邊界。

w  = max(1, ceil((hi - lo) / (n - 1)))
nb = (hi - lo) // w + 1
for v in nums:
    b = (v - lo) // w
    bmin[b] = v if bmin[b] is None else min(bmin[b], v)
    bmax[b] = v if bmax[b] is None else max(bmax[b], v)
best, prev = 0, bmax[0]
for b in range(1, nb):
    if bmin[b] is None:  continue
    best = max(best, bmin[b] - prev)
    prev = bmax[b]

注意什麼東西從頭到尾沒被算過：桶內的順序。這就是整個技巧所在，而它跟前面那個 kernel 是同一種直覺 - 線性解不是排得比較快，是看出哪一段排序可以不做。

這些東西之後會用在哪

影響最深遠的是 prefix sum。它是每一種平行 counting sort 的骨架，是 fused MoE layer 用來算出每個 expert 的列從哪裡開始的東西；而這裡 work 對 depth 的那套論證，跟一批請求要怎麼排到多個裝置上是 同一套。radix sort 的保序 key，則是量化格式能被當成整數比較的原因。至於「哪一段排序可以省掉」這個 念頭，每次看到 kernel 在每個 tile 上只留一份摘要而不是留整個 tile，你看到的就是它。
