100 Days of Python - day 22

Every sort in this series so far has asked exactly one kind of question: is a less than b? Ask only that, and there is a floor. A sorting algorithm is a decision tree, it has to be able to reach all n! orderings, a binary tree with n! leaves is at least log2(n!) deep, and that is n log n. I measured how close merge sort gets to its own floor:

n =      16:  log2(n!) =        44   merge sort used        48   (1.08x)
n =   1,000:  log2(n!) =     8,529   merge sort used     8,690   (1.02x)
n = 100,000:  log2(n!) = 1,516,704   merge sort used 1,536,501   (1.01x)

One percent. There is no clever comparison sort left to discover. The only way down is to stop asking that question - and today is the three algorithms that do, plus the kernel in my day job that turns out to be one of them.

Yesterday was selection: not sorting, because we only wanted the top k. Today is the other escape hatch - still sorting everything, but never comparing.

Counting sort: the histogram is an address table

If a key is an integer in 0..k-1, it is already an address. Count, scan, scatter.

def counting_sort(keys, k, payload):
    counts = [0] * k
    for v in keys:                 # count
        counts[v] += 1
    total, starts = 0, [0] * k     # scan
    for v in range(k):
        starts[v] = total
        total += counts[v]
    out = [None] * len(keys)       # scatter
    cursor = list(starts)
    for i, v in enumerate(keys):
        out[cursor[v]] = payload[i]
        cursor[v] += 1
    return out

The middle loop is the whole idea. Before it, entry v means "how many v are there". After it, entry v means "how many elements come before the first v" - the starting address of bucket v. The histogram has become an address table, and the scatter is then just a write to a computed index. Nothing was compared, so the n log n bound does not apply; the bound is a statement about a question, not about sorting.

Two properties fall out. It is a permutation, so a payload indexed like the keys rides along for free. And it is stable: the input is walked left to right and the cursors also grow to the right, so equal keys keep their input order. That looks like a nicety. It is about to become a correctness condition.

The cost is 2n + k, and that k is not decoration. It is the size of the key space, not the number of elements. Sorting ten thousand 32-bit integers by counting means allocating four billion buckets, essentially all of them zero.

Radix sort trades passes for buckets

Keep the counting sort, shrink k by hand: sort a few bits at a time, least significant digit first, one stable counting sort per digit.

The top half of that figure is a correct LSD radix sort on 4-bit values with 2-bit digits. The bottom row is the same code with one change - each bucket is filled back to front instead of front to back. That is still a perfectly valid sort of a single digit. Run two passes with it and the array comes out unsorted:

stable   passes: 3137 3729 17269 20628 24236 36059 42072 49669 51152 54485 61495 64703
unstable passes: 3729 3137 17269 24236 20628 36059 42072 51152 49669 54485 64703 61495
sorted?  False

Pass 1 reverses ties that pass 0 had just ordered, and there is no later pass that can put them back - the information is gone. In radix sort, stability is not a nice property to have, it is the reason the algorithm is correct at all. It is also why GPU implementations work so hard to give each thread a private cursor rather than letting atomicAdd decide who gets which slot.

So how wide should a digit be? The textbook model charges one histogram per pass and concludes 16 bits. Real implementations build a histogram per tile, because that is what keeps the counters in fast memory - a thread block gets 64 KB of shared memory, and a 65,536-entry histogram of 32-bit counters wants 256 KB. Charging honestly, work = passes * (2n + tiles * 2**r), for a million 32-bit keys in tiles of 1,024:

r =  4 bits:  8 passes x     16 buckets  ->  work =  16,125,056   histogram      0 KB  fits
r =  8 bits:  4 passes x    256 buckets  ->  work =   9,000,448   histogram      1 KB  fits
r = 11 bits:  3 passes x  2,048 buckets  ->  work =  12,002,688   histogram      8 KB  fits
r = 16 bits:  2 passes x 65,536 buckets  ->  work = 132,057,344   histogram    256 KB  DOES NOT FIT

The honest model puts the answer at 8 bits with 4 close behind, which is exactly the window production radix sorts live in. The dishonest one recommends the option that does not fit in the hardware.

Radix sort over floats needs one more thing: an order-preserving key. Raw IEEE-754 bits sort every negative float above every positive one and sort the negatives backwards, because the sign bit is a flag rather than a most significant digit. Flip the sign bit on positives, flip all 32 bits on negatives, and unsigned integer order matches numeric order - the same key day 21 used for radix select. Once comparisons become counting, everything has to be an integer.

Bucket sort bets on the distribution

The third algorithm stops treating the key as an address and treats it as an estimate: scale each value into one of m buckets, sort inside each bucket with whatever you like, concatenate. Same code, same n, same 2,000 buckets, two different inputs:

uniform  : fullest bucket   6 of 2,000   empty 756     inner-sort moves     551
clustered: fullest bucket 132 of 2,000   empty 1,956   inner-sort moves  47,038

Nothing raises. The "linear" sort just quietly becomes quadratic, because almost everything landed in one bucket and the inner sort is O(len**2). Bucket sort does not sort the data, it bets on the distribution; the uniformity assumption is a precondition on the input, not a footnote in the analysis. The same bet is being placed every time a GPU partitions data by key range - skew the input and the blocks holding the fat buckets become the long tail.

The scan in the middle is the hard part

Counting is one thread per element. Scattering is one thread per element. The prefix sum between them is not: starts[v] reads what the previous iteration just wrote, which is the definition of sequential. All of the difficulty of parallel sorting collapses into that line.

n = 1,024      sequential      1,023 adds / 1,023 deep
               Hillis-Steele   9,217 adds /    10 deep
               Blelloch        2,046 adds /    20 deep

Read those numbers carefully, because they are not what "parallel" usually suggests. Both parallel scans do more additions than the sequential loop they replace. Hillis-Steele doubles a stride and has every element add the one off to its left, reaching log n depth at a cost of n log n work. Blelloch builds a reduction tree on the way up (n/2 + n/4 + ... = n-1 additions) and pushes partial sums back down, getting the same depth class for linear work. Neither is faster in serial. They win only because the lanes were idle - that is the work-depth trade, and it is the reason "how many operations" stops being the right question on a GPU.

Blelloch also wants a power-of-two length, which is why sglang's MoE kernel zero-pads its expert histogram before scanning on the HIP path. Algorithmic constraints grow out into kernel parameters.

A real one: moe_align_block_size is a counting sort

This runs on every decode step of every MoE model. The router says which experts each token is routed to; the grouped GEMM requires each expert's tokens to be contiguous and aligned to a fixed block size. Expert ids are small integers - so this is a counting sort.

Reproducing sglang's own docstring example exactly, in pure Python:

topk_ids         [[2, 3, 4], [1, 2, 4], [1, 3, 4], [1, 2, 3]]   block_size = 4
flattened        [2, 3, 4, 1, 2, 4, 1, 3, 4, 1, 2, 3]
counts           [0, 3, 3, 3, 3]
padded           [0, 4, 4, 4, 4]
prefix           [0, 0, 4, 8, 12, 16]
sorted_token_ids [3, 6, 9, 12, 0, 4, 10, 12, 1, 7, 11, 12, 2, 5, 8, 12]
expert_ids       [1, 2, 3, 4]

Two changes from the textbook version. Each bucket is rounded up to block_size before the scan, so every expert's region starts on a block boundary; the resulting holes are pre-filled with token id 12 - one past the last real token - which the GEMM masks out. In the real kernel a whole separate thread block does that fill with int4 vector stores while the histogram is still running, because the two jobs never touch each other.

And expert_ids, which expert owns block b, is not computed separately at all: it is a binary search over the same prefix array. That array does three jobs from one scan - the bucket starts for the scatter, the moving cursors during it, and the search key afterwards.

sgl-kernel ships two kernels for this one function, and the reason is the same non-determinism day 21 ran into. The atomicAdd scatter gives a different (still correct) permutation on every run; the per-thread-histogram scatter is reproducible. Both feed the same GEMM, because rows of a GEMM do not care what order they arrive in. The switch is hard-coded: topk_ids.numel() < 1024 && num_experts <= 64 - small batches get determinism, large batches get atomics.

At real sizes - 4,096 tokens, top-8 of 256 experts, block 64 - 32,768 routed tokens become 40,704 padded slots, so 19.5% of the rows are padding. That is the price of a fixed block size, and arranging the data so the price is payable is exactly what the counting sort is for.

LeetCode 75 - Sort Colors

Two passes with a three-counter histogram, or one pass with three pointers. The follow-up wants the one-pass version, and its difficulty is an asymmetry: a value swapped down from the high end has never been examined, so mid must not advance after that swap, while a value swapped up from the low end has been.

def sort_colors(nums):
    low, mid, high = 0, 0, len(nums) - 1
    while mid <= high:
        if nums[mid] == 0:
            nums[low], nums[mid] = nums[mid], nums[low]
            low += 1; mid += 1
        elif nums[mid] == 2:
            nums[mid], nums[high] = nums[high], nums[mid]
            high -= 1              # NOT mid += 1
        else:
            mid += 1

LeetCode 164 - Maximum Gap

"Largest gap between successive elements in the sorted order, in O(n)" is really "solve this without sorting". Drop n numbers into n-1 buckets of width ceil((max - min) / (n - 1)). Pigeonhole guarantees at least one bucket is empty, so the largest gap spans at least one bucket width, so it can never sit inside a bucket. Keep one min and one max per bucket, throw the rest away, sweep once across the boundaries.

w  = max(1, ceil((hi - lo) / (n - 1)))
nb = (hi - lo) // w + 1
for v in nums:
    b = (v - lo) // w
    bmin[b] = v if bmin[b] is None else min(bmin[b], v)
    bmax[b] = v if bmax[b] is None else max(bmax[b], v)
best, prev = 0, bmax[0]
for b in range(1, nb):
    if bmin[b] is None:  continue
    best = max(best, bmin[b] - prev)
    prev = bmax[b]

Notice what is never computed: the order inside a bucket. That is the whole trick, and it is the same instinct as the kernel above - the linear answer is not a faster sort, it comes from noticing which part of the sort you can skip.

Why this matters later

The prefix sum is the piece with the longest reach. It is the skeleton of every parallel counting sort, it is how a fused MoE layer works out where each expert's rows begin, and the work-versus-depth argument here is the same one that decides how a batch of requests gets scheduled across devices. Radix sort's order-preserving key is what lets quantised formats be compared as integers. And the "which part of the sort can I skip" move shows up every time a kernel keeps a summary per tile instead of the tile itself.

LeetCode 75 - Sort Colors

The task. You are given an array whose every element is 0, 1 or 2 - think red, white and blue objects thrown in a box. Rearrange the array in place so that all the 0s come first, then all the 1s, then all the 2s. You may not call the library sort.

Input / output. Input is the array nums; there is no return value, the array itself must end up sorted.

Example. nums = [2,0,2,1,1,0] becomes [0,0,1,1,2,2].

Constraints. 1 <= len(nums) <= 300, and every nums[i] is one of 0, 1, 2. The interesting part is the follow-up: do it in one pass with O(1) extra space.

LeetCode 164 - Maximum Gap

The task. Given an unsorted integer array, return the largest difference between two successive elements once the array is sorted. If the array has fewer than two elements the answer is 0.

Input / output. Input is nums; output is a single integer.

Example. nums = [3,6,9,1]. Sorted it is [1,3,6,9], the successive gaps are 2, 3, 3, so the answer is 3.

Constraints. 1 <= len(nums) <= 10^5 and 0 <= nums[i] <= 10^9. The problem explicitly asks for linear time and linear extra space, which is what rules out "just sort it" and forces a bucket/radix argument.
