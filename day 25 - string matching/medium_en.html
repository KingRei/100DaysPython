String matching: KMP and Rabin-Karp

Code: day 25 on GitHub

100 Days of Python - day 25

Finding a substring is the most elementary problem in this whole series, and Python spells it needle in haystack. I still think it deserves a day, because the two classical algorithms for it - KMP and Rabin-Karp - are not really about text. They are about two different ways of not doing work, and both of them show up, unlabelled, in the guts of an LLM inference server. One of them shows up together with a bug that only appears when speculative decoding is switched on.

Yesterday's radix tree stored a shared prefix once. Today is about finding one.

The naive matcher forgets

Line the pattern up at every position and compare. On 'a' * 40 + 'aaab' searching for 'aaab', that costs 164 character comparisons where KMP costs 84.

The interesting part is not the ratio, it is the reason. Look at the moment a comparison fails at offset j. The matcher has just proved that the last j characters of the text are the first j characters of the pattern. Then it throws the proof away, slides one position right, and starts again from zero. Everything KMP does follows from refusing to do that.

The failure function is a table of borders

A border of a string is a prefix that is also a suffix. fail[i] is the length of the longest border of pat[:i+1], and for ababaca the table is [0, 0, 1, 2, 3, 0, 1].

def build_failure(pat):
    fail = [0] * len(pat)
    k = 0                              # length of the current border
    for i in range(1, len(pat)):
        while k > 0 and pat[i] != pat[k]:
            k = fail[k - 1]            # fall back to a shorter border
        if pat[i] == pat[k]:
            k += 1
        fail[i] = k
    return fail

The while line is the whole algorithm: if a border of length k cannot be extended, the next candidate is not k - 1, it is fail[k - 1], because a shorter border of the pattern must also be a border of that border. k rises by at most one per iteration, so the total number of fall-backs cannot exceed the total number of rises - which is why building the table is O(m) even though it contains a loop inside a loop.

With the table in hand, searching is one pass:

def kmp_search(text, pat):
    fail, j, hits = build_failure(pat), 0, []
    for i, ch in enumerate(text):      # i never goes backwards
        while j > 0 and ch != pat[j]:
            j = fail[j - 1]
        if ch == pat[j]:
            j += 1
        if j == len(pat):
            hits.append(i - len(pat) + 1)
            j = fail[j - 1]
    return hits

i only moves forward. That is not a micro-optimisation, it is a change in what the algorithm can run on: a text you cannot rewind. A socket. A token stream.

A stop string arriving in four pieces

Every generation request carries stop strings - </s>, \n\nHuman:, whatever ends a turn. The server must detect them while it is still streaming text to the client, which rules out both obvious implementations: waiting for the end is not streaming, and re-scanning the whole output per token is quadratic.

One KMP state per stop string solves it with an integer per pattern and no memory of the text. The part worth internalising is the hold-back:

When the match length is 3, those three characters might be the start of a stop string, and text already sent to the client cannot be recalled - so they are withheld until the next chunk resolves them. Feeding ['The answer is 4', '2.<', '/s', '> and then some more'] emits The answer is 4, then 2. while holding <, then nothing while holding <, /, s, and then stops.

sglang solves the same problem in schedule_batch.py, and it is instructive that it does not use KMP. check_match_stop_str_prefix tries every suffix length and compares slices, which is O(m²) - perfectly fine, because it first clips the tail to stop_str_max_len + 1 characters. Bounding the input is a legitimate alternative to a better algorithm, as long as you can prove the bound. Which brings us to the bug.

Tokens are not characters

A stop string is written in characters. A model emits tokens, and token boundaries have nothing to do with anything a human typed. In my toy vocabulary the stop string ]] has its first ] buried inside the token " 42]" and its second one as a whole token.

So every step decodes the last few tokens back into text and searches there. How few is safe? With one token per step, stop_max_len + 1 characters is enough: a stop string that has just completed must end on the token just appended. Speculative decoding breaks the assumption.

Several tokens land at once, and the stop string can complete in the middle of the accepted batch, entirely behind a fixed-size window. Running my example both ways: one token per step detects ]] at token 5; four tokens per step with the same fixed window never detects it at all. sglang's fix is _stop_match_tail_len:

min(stop_str_max_len + 1 + max(new_accepted_len - 1, 0), len(output_ids))

Extending by accepted - 1 pulls the whole batch back into view. Reading a character count as a token count is safe in the conservative direction, because a token decodes to at least one character. And detecting the stop is only half of it - the finish length is counted in tokens, so _locate_str_stop_finished_len decodes growing prefixes of the window until the stop appears, answering "finish after 5 tokens, keep The answer is 42". The match lives in character space, the bookkeeping lives in token space, and decoding is the only bridge.

This is the kind of bug worth studying: not a wrong line, but a correct line whose precondition quietly stopped holding when a feature was turned on somewhere else.

Rabin-Karp: compare fingerprints, then verify

The other classical approach changes the question. Read the current window as a base-256 number modulo a large prime; sliding one place right costs one multiply-add.

ht = ((ht - ord(text[i]) * high) * base + ord(text[i + m])) % mod

Unequal fingerprints mean definitely not. Equal fingerprints mean maybe - so every fingerprint hit is followed by a real comparison.

That verify line is part of the algorithm, not defensive programming. With mod = 101, aah and aca share fingerprint 41, and searching for aca inside xaahy gives one fingerprint hit, one verified rejection, zero matches. Delete the verify and nothing crashes; the function just silently reports a position where the pattern is not. Against a KMP-shaped problem Rabin-Karp wins nothing. Where it wins is k patterns of the same length in one pass: a set of fingerprints costs the same to test as one.

The other kind of fingerprint, and the one you cannot verify

sglang names each KV cache page with a chained SHA-256 (mem_cache/utils.py): each page digest folds in the digest of the page before it, so an id stands for the whole prefix up to here, not for the four tokens it holds.

Two requests sharing a system prompt get identical ids for the shared pages and diverge exactly where their tokens do. A page containing the same four tokens after a different history gets a different id, deliberately, because attention keys and values depend on the entire prefix.

Now put it next to Rabin-Karp: there is no verify step here, and there cannot be one. The tokens you would compare against are long gone; at hit time the server holds nothing but an id. All the correctness rests on SHA-256 not colliding. Swap in a cheap hash and a collision does not make the server slow - it makes one request read another request's KV cache. When choosing a hash, "can I check afterwards?" matters far more than "is it fast?".

28 (strStr) is the algorithm itself. The pair I would actually prepare is 459 and 214, because neither is a search - both use the border quantity directly.

def repeated_substring_pattern(s):          # LC 459
    n = len(s)
    b = build_failure(s)[-1]                # longest border
    return b > 0 and n % (n - b) == 0       # n - b is the period

def shortest_palindrome(s):                 # LC 214
    if not s:
        return s
    probe = s + "\x00" + s[::-1]
    k = build_failure(probe)[-1]            # longest palindromic prefix
    return s[k:][::-1] + s

If the longest border of s has length b, sliding s right by n - b lands it on itself, so n - b is a period and s is a repetition iff that period divides n. The b > 0 guard is the interview trap: without it abc counts as its own repetition. For 214, the longest palindromic prefix of s is the longest prefix of s that is also a suffix of reversed(s), so one failure function over s + separator + reversed(s) answers it - and the separator must appear in neither half, or a border straddles the join and over-counts. LC 1044 is the Rabin-Karp side of the same coin: binary search the length, verify each rolling-hash candidate.

Why this matters later

Borders and rolling hashes are the substrate under the rest of the string part of this series: suffix arrays and Aho-Corasick generalise "what have I already matched" to many patterns at once, and MinHash generalises "compare fingerprints, not contents" to similarity rather than equality. BM25 and hybrid retrieval lean on the same rolling-hash shingling. And the two inference-server mechanisms above - the stop-string window and the chained page id - are the reason I wanted the naive matcher and the hash side by side in one day: one of them can verify its guesses, the other one structurally cannot, and that difference decides which hash you are allowed to choose.
