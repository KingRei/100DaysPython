The memory hierarchy and the roofline: why some kernels never get faster

Code: day 63 on GitHub

100 Days of Python - day 63

Every performance number in this series has turned out to be a memory number, and I did not plan that. Decode is slow because it reads the weights once per token. The KV cache is the capacity limit. MoE is a communication problem. Quantization helps because fewer bits means fewer bytes. Not one of those is a statement about arithmetic.

So this day is the model underneath all of them: what the hierarchy looks like, the one inequality that decides whether a kernel is limited by arithmetic or by traffic, and why tiling - FlashAttention included - is the only move that changes which side you are on.

The hierarchy

level                   capacity  bandwidth     latency
----------------------  --------  ------------  ---------
registers               256 KB    100,000 GB/s  1 ns
shared memory / LDS     160 KB    20,000 GB/s   20 ns
L2 cache                50 MB     7,000 GB/s    200 ns
HBM                     192 GB    5,300 GB/s    600 ns
host memory over PCIe   1 TB      64 GB/s       2,000 ns
another node over RDMA  -         50 GB/s       10,000 ns

Vendor specifications, not measurements. The last two rows are earlier days: the host memory row is why HiCache has tiers, and the RDMA row is why DeepEP ships two different sets of kernels.

Measured here: order is everything

Summing an array is bandwidth-bound at every size, so it should fall off a cliff when the array leaves cache. On this machine it moves by about 1.3x - the prefetcher sees a sequential read coming and starts it early. Read the same bytes in a random order and the hierarchy appears in full: 1.1 ns per access in cache against 11.7 ns out of it, a factor of 11.

Bandwidth is what the specification sells you; locality is what decides whether you get it. Every structure in this series that looks like a pointer chase - a radix tree, a block table, a gather of expert weights - pays the second price.

The roofline

A machine is two numbers: 1300 TFLOP/s and 5300 GB/s. Their ratio is the machine balance, 245 FLOPs per byte, and a kernel that does less arithmetic per byte than that cannot be compute-bound however it is written.

kernel                        FLOPs/byte  bound    time
----------------------------  ----------  -------  --------
decode: one linear (GEMV)     1.00        memory   0.02 ms
prefill: one linear (GEMM)    3185.78     compute  0.37 ms
decode: attention over KV     1.00        memory   0.01 ms
prefill: attention (untiled)  128.00      memory   0.41 ms
RMSNorm                       1.00        memory   0.01 ms
residual add                  0.17        memory   0.02 ms
decode: the whole 70B model   1.00        memory   26.42 ms

Read the first two rows together: the same weights and the same kernel, memory-bound as a matrix-vector product in decode and compute-bound as a matrix-matrix product in prefill. The kernel did not change; the number of rows did.

Batching moves you along it

batch  FLOPs/byte  bound    per token
-----  ----------  -------  ---------
1      1.00        memory   22.2 us
16     15.96       memory   1.4 us
256    247.17      compute  0.1 us
1024   896.00      compute  0.1 us

The weights are read once whatever the batch, so intensity grows linearly until it crosses the ridge and the cost per token falls by two orders of magnitude. The day on speculative decoding measured the same curve from the other end.

Tiling is the only way to raise intensity

A kernel cannot choose its FLOPs. It can choose how many times it re-reads the same bytes. A 4096x4096 matmul moves 549.8 GB untiled and 5.4 GB in tiles of 104 - 103x less, and the factor is exactly the tile size. The tile size is not free: three tiles must fit in cache at once, so T = sqrt(cache / 3).

FlashAttention is that argument, applied to attention

Day 52 proved the online-softmax identity - the same answer in one pass over the keys, to the last bit. This is why it is worth doing, and the honest version has two parts.

At seq 4096 with 32 heads of 128 and 160 KB of shared memory, the block is 160 rows, K and V are re-read 26 times, and the traffic falls only 2.4x (4.43 GB to 1.81 GB). The traffic saving scales with d_head^2 / SRAM, which is why it looked larger in the original paper at d_head 64.

The real prize is the other column: the 1.07 GB score matrix is never allocated - 6,554 times the shared memory the kernel runs in. That is a capacity argument, not a bandwidth one, and it is why long contexts are servable at all. The backward pass does the same thing: it stores the log-sum-exp per row, one number instead of seq numbers, and recomputes the scores from Q and K, because recomputation is cheaper than the round trip - which is only true because of the first column of the roofline table.

Latency, and why bandwidth alone is not enough

Little's law: keeping the pipe full needs bandwidth x latency bytes in flight, which here is 3.2 MB, or about 24,800 simultaneous requests. A kernel that issues one load and waits is slow however clean it is.

And a cache line is fetched whole. Measured on this machine, reading with a stride of 16 leaves 6.2% of the fetched bytes useful and makes the loop slower, because the same 16 MB is fetched for a sixteenth of the payload. That is coalescing on a GPU and array-of-structs on a CPU: one hardware fact, two names.

memory_hierarchy.py closes with the matching sections for PyTorch (torch.profiler, max_memory_allocated, torch.compile fusion, scaled_dot_product_attention) and JAX (memory_analysis() and cost_analysis() - a roofline the compiler computes before you run anything - XLA's default fusion, and Pallas when you need to choose the block sizes yourself).

Where this comes back

Everything after this day is an application of the same inequality. A kernel is memory-bound or it is not; batching, fusing, tiling and quantizing are four different ways of changing the ratio, and a profile is only readable once you know which side of the ridge each kernel sits on.
