Segment tree and Fenwick tree: range queries when the data keeps changing

Code: day 29 on GitHub

100 Days of Python - day 29

Two operations on one array. Write a single cell. Ask for the sum of a slice. Pick the obvious structure for either one and you have made the other one terrible.

A plain array updates in O(1) and answers a range sum in O(n). A prefix-sum array answers in O(1) and needs O(n) for a single write, because touching a[2] invalidates every prefix from index 2 onward. On a million elements that is a million adds per query, or a million rewrites per update. They are mirror images, each perfect at one job and useless at the other.

Everything today exists to refuse that trade. Yesterday's balanced trees kept a set of keys short to search; today's structures keep a summary of ranges cheap to maintain, which is a different problem with a very similar shape.

The segment tree: cut the range into whole subtrees

The idea is to precompute the sum of every "natural" block - the whole array, each half, each quarter, down to single elements - and then answer any query by gluing together a few of those blocks.

The iterative version is the one I would actually write. It stores the tree in a flat array of size 2n: leaf i lives at t[n + i], and the parent of node k is k >> 1. No node objects, no recursion, no pointers.

class SegmentTree:
    def __init__(self, data):
        self.n = len(data)
        self.t = [0] * (2 * self.n)
        self.t[self.n:] = data
        for k in range(self.n - 1, 0, -1):        # build bottom up
            self.t[k] = self.t[2 * k] + self.t[2 * k + 1]

    def update(self, i, value):
        k = i + self.n
        self.t[k] = value
        while k > 1:                               # walk up the parent chain
            k >>= 1
            self.t[k] = self.t[2 * k] + self.t[2 * k + 1]

    def query(self, l, r):                         # half open [l, r)
        res, l, r = 0, l + self.n, r + self.n
        while l < r:
            if l & 1: res += self.t[l]; l += 1     # l is a right child: take it
            if r & 1: r -= 1; res += self.t[r]     # r is a right child: take r-1
            l >>= 1; r >>= 1
        return res

Both pointers start at the leaves and climb. On each level, a node is harvested only when it lies entirely inside the range, and the two & 1 tests are exactly the "am I an overhang?" question. canonical_cover(16, 3, 13) returns [5, 6, 19, 28] - four stored sums answer a ten-element query.

The bound is 2·log2(n), and the argument is short enough to keep in your head: on each level at most one node can be a partial overhang on the left and one on the right, so you can never take more than two per level. Measured over random ranges, it is comfortably better than the bound - n = 65536 averages 13.25 nodes against a bound of 32, and n = 1000000 averages 17.03 against 38.

One thing to notice, because it comes back at the end: the query only ever combines disjoint pieces. Nothing is ever subtracted. That means the merge can be any associative operation - sum, min, max, gcd, matrix product - with a two-line change.

Lazy propagation: the same idea, moved to the update side

Now add delta to every element of a range. Walking to each leaf is O(n) and throws the tree away. But the query already knows how to cut a range into whole subtrees, and a node that is fully covered does not need to ask its children anything: its sum goes up by exactly delta * width.

So apply it there, leave a note, and stop.

def _apply(self, k, delta, width):
    self.t[k] += delta * width          # this node's sum is now correct
    if k < self.size:
        self.lazy[k] += delta           # the children are owed the same delta

def _push(self, k, lo, hi):
    if self.lazy[k]:
        mid = (lo + hi) // 2
        self._apply(2 * k,     self.lazy[k], mid - lo + 1)
        self._apply(2 * k + 1, self.lazy[k], hi - mid)
        self.lazy[k] = 0

The invariant is worth stating precisely, because it is what makes the whole thing safe: a node's stored sum is always correct; its children may be stale by whatever is recorded in lazy. The debt is settled by _push, and only when someone actually descends past that node.

This is deferred work, not skipped work, and the saving is not marginal. On 100000 elements with 2000 random range-adds: the eager version makes 100775266 node visits, the lazy version 116963, with 42681 pushes. 862 times fewer.

The tag does not have to be a number, either - it only has to compose. "Assign this value", "multiply by this factor", "apply this affine map" are all legal tags, which is why the same trick shows up in interval scheduling, in paint-the-subtree problems, and anywhere an operator is applied to a whole region at once.

The Fenwick tree: throw the tree away, keep the bits

And now the other answer, which reaches the same complexity with no tree at all.

Peter Fenwick published it in 1994 and called it a binary indexed tree in the paper itself - so yes, "BIT" and "Fenwick tree" are the same structure, and you will see both names in the same discussion. It stores n + 1 numbers and no links. The entire design is one expression: i & -i, the lowest set bit of i.

def prefix(self, i):                 # sum of a[0:i]
    s = 0
    while i > 0:
        s += self.t[i]
        i -= i & -i                  # strip the lowest set bit
    return s

def add(self, i, delta):             # a[i] += delta
    i += 1
    while i <= self.n:
        self.t[i] += delta
        i += i & -i                  # climb to the next responsible cell

t[i] holds the sum of the i & -i elements ending at i. t[8] covers a[0:8], t[12] covers a[8:12], t[6] covers a[4:6], t[7] covers only a[6:7]. That staircase is not a layout someone designed; it is what binary counting implies.

prefix(13) peels the set bits of 1101: 13 → 12 → 8 → 0, one read per set bit. add climbs the complementary chain. Both loops run at most log2(n) times, usually fewer - on n = 1000000 the average prefix takes 9.88 steps against a worst case of 19.

The payoff is memory and constants. On a million 64-bit cells an iterative segment tree needs 2n, a recursive one 4n, a lazy one 8n, and a Fenwick tree n + 1. On 20000 elements with 2000 update-plus-query pairs, I measured 22.5 ms for the Fenwick tree, 44.0 ms for the segment tree, 87.4 ms for the plain array and 9068.1 ms for prefix sums. Six lines of code, a quarter of the memory of a lazy tree, twice the speed of the simplest one.

It also does more than prefix sums, which is the part people tend not to know. Run one BIT over the difference array and a range add becomes two point updates. Run two BITs and you get range add plus range sum, via prefix(i) = B1.prefix(i) * i - B2.prefix(i) - a lazy segment tree's asymptotics in a quarter of its memory. And lower_bound, the smallest index whose prefix reaches a target, is a binary lift over the same array in O(log n), which is how a Fenwick tree turns into a weighted sampler.

What a Fenwick tree cannot do

So why keep the segment tree at all?

a = [5, 3, 8, 1]; a[3] = 9
real min          = 3
prefix-min BIT    = 1     # wrong - it never forgot the 1
min segment tree  = 3

Every BIT range query is range(l, r) = prefix(r) - prefix(l). That subtraction is not an implementation detail, it is a requirement on the operation: there must be an inverse. Addition has one. Xor has one. min does not. Once a 1 has been folded into a cell, nothing takes it back out - so a prefix-min BIT can only ever let values decrease, and when a value increases it returns a plausible, wrong answer without raising anything.

The segment tree never subtracts. It combines disjoint pieces, so associativity is the only requirement, and min, max, gcd and matrix products all work unchanged.

That, not the constant factor and not the memory, is the real dividing line: ask whether the operation can be undone.

The LeetCode problems

307. Range Sum Query - Mutable is the canonical problem for this whole topic, built so that neither naive answer survives. Both structures solve it in a few lines, but the BIT version hides the detail interviewers listen for: a BIT stores deltas, not values, so "set a[i] to val" has to be written add(i, val - a[i]), which means keeping the original array beside the tree. Miss it and the structure drifts quietly, never erroring. The other easy loss is the interval convention - LeetCode's sumRange is inclusive, so a half-open range_sum needs r + 1.

315. Count of Smaller Numbers After Self is the reduction worth memorising. Compress the values to ranks, scan right to left so that "after me" becomes "already seen", and use the BIT as a histogram of counts. Each element then costs one prefix(rank) and one add. At n = 4000 that ran about 30 times faster than the double loop. The move - turning a counting question into a prefix query - is the same one behind inversion counts, sliding-window ranks and offline range statistics.

370. Range Addition is a deliberate anticlimax. Every update arrives before any query, so a difference array in O(n + k) is optimal and a tree buys nothing.

Which makes the decision procedure short. Are the updates and the queries interleaved? If not, use prefix sums or a difference array. If they are and the operation has an inverse, write the six-line Fenwick tree. If they are and it does not, build the segment tree - and if the updates cover ranges too, give it lazy tags.

Why this matters later

A prioritised replay buffer in reinforcement learning is a sum-tree: sampling proportional to priority is exactly lower_bound on a prefix-sum structure, and priorities change after every gradient step, so this is the interleaved case by construction. Sampling from a token distribution with dynamic weights is the same operation. Interval-overlap queries, sweep-line algorithms and offline range statistics all sit on one of these two structures, and choosing between them still comes down to that one question about the inverse.

Appendix: the LeetCode problems in full

Restated in my own words - what is being asked, what goes in and comes out, one worked example, and the constraints that actually change which algorithm is allowed.

LeetCode 307 - Range Sum Query - Mutable

The task. Build a NumArray over an integer array supporting two operations mixed in any order: update(index, val) sets one element, and sumRange(left, right) returns the sum of the inclusive slice.

Input / output. Constructor takes nums; update returns nothing, sumRange returns an integer.

Example. With nums = [1,3,5]: sumRange(0, 2) is 9; after update(1, 2) the array is [1,2,5] and sumRange(0, 2) is 8.

Constraints. 1 <= len(nums) <= 3 * 10^4, -100 <= nums[i] <= 100, up to 3 * 10^4 calls to update and sumRange combined. Both of the obvious answers fail: a plain array makes sumRange O(n), a prefix-sum array makes update O(n). This is exactly the problem a Fenwick tree or a segment tree exists to solve, at O(log n) for both.

leetcode.com/problems/range-sum-query-mutable

LeetCode 315 - Count of Smaller Numbers After Self

The task. For every position i, count how many elements to the right of nums[i] are strictly smaller than it, and return those counts as an array.

Input / output. Input is nums; output is a list of the same length.

Example. nums = [5,2,6,1] → [2,1,1,0]: to the right of 5 sit 2 and 1; to the right of 2 sits 1; to the right of 6 sits 1; nothing is to the right of 1.

Constraints. 1 <= len(nums) <= 10^5, values in [-10^4, 10^4]. The quadratic double loop is 10^10 operations, so it will not pass. Scanning from the right while inserting into a Fenwick tree indexed by value gives O(n log U); a merge sort that counts inversions, or an order-statistic skip list, get there too.

leetcode.com/problems/count-of-smaller-numbers-after-self

LeetCode 370 - Range Addition

The task. You start with an array of n zeros and a list of updates, each of the form [start, end, inc], meaning "add inc to every element from index start to index end, inclusive". Apply them all and return the final array.

Input / output. Input is length and updates; output is the resulting array.

Example. length = 5, updates = [[1,3,2],[2,4,3],[0,2,-2]] → [-2,0,3,5,3].

Constraints. 1 <= length <= 10^5, 0 <= len(updates) <= 10^4, indices inside the array and -1000 <= inc <= 1000. Applying each update literally is O(length * updates). The difference array - add inc at start, subtract it at end + 1, then take one prefix sum at the end - makes every update O(1), and it is the same trick a Fenwick tree generalises into range-update plus point-query.
