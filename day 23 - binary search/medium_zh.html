100 Days of Python - day 23

二分搜尋我可以憑記憶寫出來，你大概也可以。然後大概有一半的機率，我們其中一個人寫出來的版本會回傳一個少一格的 index、乾淨地結束、不丟任何例外，而且是錯的。

這就是這個演算法有趣的地方。它是每個人最早學會的演算法，也是最晚寫對的演算法之一，原因是課本上那個版本 — 把區間對半砍直到 a[mid] == x — 幾乎不是真的會上線的版本。實際的程式碼要的是邊界：第一個大於等於某個 key 的 位置、CUDA graph 抓過的形狀裡最小能裝下這個 batch 的那一個、來得及吃完的最低速度、某個 token 屬於哪一個 request。這些全部都是同一個問題 —— 「false 是在哪裡變成 true 的」 —— 而且沒有一個是用相等判斷回答的。

昨天講 counting sort，用 prefix sum 把直方圖變成位址表。今天講的其中一件事，就是把它倒回去的那個操作 —— 而那正是 sglang 裡五處二分搜尋的其中一處。

一句不變式，其他都是推論

用兩個 index lo 和 hi 描述一個半開區間 [lo, hi)，然後從頭到尾維持同一句話：

a[:lo] 已經確定太小，a[hi:] 已經確定夠大，中間那段還不知道。

從 [0, len(a)) 開始，這句話自動成立，因為兩邊已知的區域都是空的。接下來每一步都要保住它。如果 a[mid] < x，那 mid 不可能是答案，所以 lo = mid + 1；如果 a[mid] >= x，那 mid 有可能就是答案， 所以 hi = mid —— 不是 mid - 1，因為那會把剛剛才證明有資格的那一格丟掉。

def lower_bound(a, x):
    lo, hi = 0, len(a)              # 半開區間：hi 是長度，不是最後一格
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] < x:
            lo = mid + 1            # 答案嚴格在 mid 右邊
        else:
            hi = mid                # mid 自己可能就是答案
    return lo                       # lo == hi 就是邊界

這個迴圈裡沒有任何提早 return。區間變空的時候，不變式說 lo 左邊全部太小、右邊全部夠大，那個位置就是邊界， 所以 lo 就是答案 —— 包含「答案在最後面之後」這種情況，這也正是 hi 要從長度開始而不是從最後一格開始的理由。 也不需要寫「找不到」的分支，lo == hi 已經把話講完了。

另一個版本只差一個字元

def upper_bound(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] <= x:             # <= 而不是 <
            lo = mid + 1
        else:
            hi = mid
    return lo

差別就這樣：相等的元素要不要算在邊界的左邊。這兩個就是標準函式庫的 bisect_left 和 bisect_right，而且成對用 比單獨用有價值得多。upper_bound(x) - lower_bound(x) 是 x 出現的次數；upper_bound(x) - 1 是 「最後一個小於等於 x 的位置」，也就是「我在哪一桶」的定義 —— 記住這一個，文章後面還會回來找它。

三個看起來對的迴圈

二分搜尋只有兩種錯法，而且這兩種的能見度差很多。

第一種是區間沒有變小。閉區間 [lo, hi] 配上 hi = mid，一旦 lo == hi 就轉不出去；半開區間寫成 lo = mid 而不是 lo = mid + 1，則是在 hi - lo == 1 的時候卡死，因為那時 (lo + hi) // 2 就等於 lo， 這個賦值等於沒做。兩個都會掛住，而掛住至少會被發現。

第二種是區間把答案丟掉了：

        else:
            hi = mid - 1            # <-- 會結束，而且是錯的

在 a = [1, 2, 3, 4, 5, 6, 7] 上找第一個 >= 4 的位置，它回傳 2，正確答案是 3。沒有例外、沒有卡住、沒有任何 提示。它正好在比較剛證明 a[mid] 有資格的那一刻，把 a[mid] 跨過去了。

還有一個，在 Python 裡不會發生，但在別的地方天天發生：

mid = (lo + hi) // 2                # lo = 2_000_000_000, hi = 2_100_000_000

在 int32 裡這個加法會繞成 -194967296，於是 mid 是 -97483648；lo + (hi - lo) // 2 則給你 2050000000。Python 的整數是任意精度所以這裡不會出事，但同一個迴圈寫在 CUDA kernel 裡索引的是 int32 offset —— 這就是 2006 年 Joshua Bloch 寫文章講的、在 java.util.Arrays.binarySearch 裡躺了九年的那個 bug。

根本不需要有陣列

把迴圈剝到只剩骨頭，它真正需要的其實是一個單調的述詞：一個 ok(x)，在搜尋範圍上是 false、false、…、 false、true、true、…、true。排序好的陣列只不過是 ok(i) = a[i] >= x 這個特例而已。

def search_first_true(lo, hi, ok):
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if ok(mid): hi = mid
        else:       lo = mid + 1
    return lo

所以配方變成：先想清楚答案是什麼的數字，寫出 ok(candidate)（通常是一次模擬而不是一次比較）， 論證它單調，然後跑上面那個迴圈。

第三步才是全部的工作。ok 不單調的時候，迴圈照樣結束、照樣回傳一個數字，而那個數字沒有意義，也沒有人會抗議。

LeetCode 875，Koko 吃香蕉：給定每堆香蕉和時限，求來得及吃完的最小速度。答案是一個速度，那就對速度做二分。

def koko_hours(piles, speed):
    return sum(-(-p // speed) for p in piles)       # 向上取整的除法

def min_eating_speed(piles, h):
    return search_first_true(1, max(piles) + 1, lambda s: koko_hours(piles, s) <= h)

它單調，因為吃得更快不可能花更久。piles = [30, 11, 23, 4, 20]、h = 6 的答案是每小時 23 根，在 30 格的 範圍裡只探測了 5 次：

圖裡那一列 T 從來沒有被建出來，五次模擬就是全部的成本。LeetCode 410 是同一個形狀 —— 把陣列切成 m 段，最大 那一段的和最小可以是多少 —— 範圍從 max(nums) 到 sum(nums)，述詞則是一次貪婪切段。

當述詞很貴，而且會說謊

sglang 的 autotuner 就是對請求速率做二分搜尋：它問「這個 qps 下伺服器還守得住 SLA 嗎」，而每一個答案都要跑一次 完整的 benchmark。ok 一旦變成量測，有兩件事就變了。

終止條件不能再是 lo < hi，因為浮點區間永遠還可以再對半砍一次，所以迴圈要靠容忍度加上回合上限來收。 而且四捨五入過的中點有可能剛好落在端點上，那一刻區間就不再變小 —— 這是整數版無窮迴圈的浮點雙胞胎，要自己擋：

        mid = round((lo + hi) / 2, 4)
        if mid <= lo or mid >= hi:
            break                       # 中點塌到端點上了

更麻煩的是述詞不再單調。真實容量 13.7 qps、跑跑之間有 ±0.6 的雜訊，十次探測裡就有兩次跟真值不一致 —— 其中一次 量到 13.256，於是把本來該過的 13.55 判成沒過。而二分搜尋不會回頭，被丟掉的那一半永遠不會再看第二眼，所以 中段的一次誤判是救不回來的。

這就是為什麼真的迴圈要留住確實跑過而且確實過關的那個最佳值，而不是回報區間的端點；也是為什麼容忍度一定要 開得比雜訊大。在有雜訊的量測上收斂到小數點後三位，只是把雜訊當成訊號而已。

一次探測到底多貴

sglang 的 radix cache 每一個進來的 request 都要回答「這兩條 token 序列共用多長的前綴」。它不一格一格走，也 不直接對整條做二分搜尋。RadixKey.match 是先比長度 1、2、4、8… 的視窗，直到某一個視窗不一樣，再只對那個 視窗做二分搜尋。

為什麼不用單純的二分搜尋？因為看你怎麼算。兩條 4096 個 token 的序列：

       p |  linear          |  binary          |  gallop
         | probes   tokens  | probes   tokens  | probes   tokens
  -------+------------------+------------------+-----------------
       0 |      1        1  |     13     4108  |      1        1
      17 |     18       18  |     12     4171  |      9       46
     250 |    251      251  |     12     5635  |     15      382
    2048 |   2049     2049  |     12    22541  |     23     6142
    4096 |   4096     4096  |     12    45069  |     13     4096

只算 probe 次數，單純的二分搜尋看起來無敵 —— 不管 p 是多少都是 12 或 13 次。但一次 probe 比的是一整段而 不是一個元素，所以 probe 既不免費也不等價。改成算碰到的 token 數，二分搜尋做的是 n log n 等級的工，galloping 做的是 O(p)：視窗每次加倍，長度加起來大約 2p，而且只有最後一個視窗需要再搜。

要注意 galloping 不是全面比較好。在 p ≈ n/2 附近它的 probe 數大約是二分搜尋的兩倍。它在這裡是對的賭注， 是因為前綴快取的 workload 本來就兩極：新對話幾乎不共用，追問幾乎全共用，中間幾乎沒有東西。（另外注意 linear 碰的 token 最少。它的問題是那些 token 是從 Python 一個一個碰的，而另外兩個是把整段丟給 C 層去比。）

內層迴圈還有一個很漂亮的細節：它寫成 while hi - lo > 1 配 lo = mid，也就是兩節之前我說會掛住的那個賦值。 它在這裡是安全的，正是因為那個迴圈條件保證 mid 嚴格大於 lo。一樣的字元、不一樣的不變式、不一樣的判決 —— 所以「背模板」是壞建議，「講清楚不變式」才不是。

把 prefix sum 倒回去

昨天的 counting sort 用 exclusive scan 把直方圖變成位址表。推論伺服器裡每一個 batched kernel 都帶著那張表， 名字叫 cu_seqlens，而每一個一次處理一個 token 的 kernel 都得把它倒回去：給一個打平的 token index，它屬於 哪一個 request？

seq_of = torch.searchsorted(cu_seqlens, tok, right=True) - 1

讀出來就是「最後一個小於等於 tok 的起點」 —— 也就是 upper_bound(tok) - 1，第二節那個「我在哪一桶」。 right=False 問的是「第一個大於等於 tok 的起點」，而在邊界上那個起點是下一個 request。所以 seq_lens = [3, 5, 2] 的時候，錯的版本錯在 token 0、3、8 —— 每一個 request 的第一個 token，一個不多一個不少 —— 而且 token 0 會拿到 -1，接著 -1 去索引 cu_seqlens 的最後一格，讀到別人的狀態。全程不丟例外。

它的鏡像則是把 batch size 往上進位。CUDA graph 是照固定形狀抓的，所以 37 個 request 的 decode step 必須 在能裝下它的最小捕捉形狀上重播，而 sglang 的 _pad_to_bucket 只有一行：

index = bisect.bisect_left(buckets, raw_size)
return buckets[index]

是 bisect_left，不是 bisect_right。batch 本身就是一個捕捉過的大小時，bisect_left 回傳它自己、完全不用 補；bisect_right 會跳到下一個 bucket，然後為一整個 graph 的空白列付錢。在預設的捕捉清單上、對 1 到 255 的 batch 取平均，這是 4.25% 對 6.07% 的差別 —— 差一個字元 —— 而且在最大的 batch 上，bisect_right 會直接掉出 清單外面。

面試版本

LeetCode 34，找 target 的第一個和最後一個位置，是「該背邊界版本而不是找 x 版本」最好的證據：

def search_range(nums, target):
    lo = lower_bound(nums, target)
    hi = upper_bound(nums, target)
    return [lo, hi - 1] if lo < hi else [-1, -1]

出現次數是 hi - lo，而「找不到」自己從 lo == hi 掉出來，不需要多一個分支、也不需要 sentinel。反過來， 如果從「a[mid] == target 就 return」開始寫，接下來就得從命中的位置往兩邊掃，遇到整條都相等的陣列就退化成 O(n)。

值得順手準備的但書是 LeetCode 33：旋轉過的排序陣列，整體根本不單調。它照樣可以對半砍，因為在每個 mid 上， 左右兩半一定有一半是有序的，而「target 在不在那一半裡」是可以判定的。有序這個條件比二分搜尋需要的還強， 迴圈真正要的只是「每一步都能排除掉一邊」。

這條線通到哪裡

這篇文章裡的五處 sglang 二分搜尋，全部都是邊界搜尋，而且沒有一個長得像課本：把 batch 補到捕捉形狀是 bisect_left；從 token index 反推 request id 是 upper_bound - 1；比對快取前綴是指數搜尋；autotune 請求 速率是在有雜訊的量測上做 bisection；decode kernel 挑 tile 大小又是同一件事。

下一站是 Trie 與 radix tree —— 也就是今天那個 gallop 正在走的那把 key 所屬的結構。再往後是字串匹配，那時 「比的是一整段而不是一個元素」這個成本模型會變成 rolling hash。

LeetCode 33 - Search in Rotated Sorted Array（搜尋旋轉排序陣列）

題目。 一個元素相異的遞增陣列，在某個未知的位置被旋轉過 —— [0,1,2,4,5,6,7] 可能會變成 [4,5,6,7,0,1,2]。給你旋轉後的陣列和 target，回傳 target 的索引，找不到就回傳 -1。

輸入／輸出。 輸入 nums 和 target，輸出一個索引（或 -1）。

範例。 nums = [4,5,6,7,0,1,2]、target = 0 → 4；target = 3 → -1。

限制。 1 <= len(nums) <= 5000、數值在 [-10^4, 10^4]、所有元素相異，且保證是某個 排序陣列旋轉而來。時間複雜度必須是 O(log n)，所以線性掃過去不算解。

LeetCode 34 - Find First and Last Position of Element in Sorted Array（在排序陣列中找元素的第一個與最後一個位置）

題目。 給一個非遞減陣列和 target，回傳 target 出現的第一個與最後一個索引，形式為 [first, last]；如果不存在就回 [-1, -1]。

輸入／輸出。 輸入 nums 和 target，輸出長度為 2 的串列。

範例。 nums = [5,7,7,8,8,10]、target = 8 → [3,4]；target = 6 → [-1,-1]。

限制。 0 <= len(nums) <= 10^5、數值在 [-10^9, 10^9]，陣列非遞減（可以有重複）。 一樣要求 O(log n) —— 這正是「找邊界而不是找元素」那種二分搜尋。

LeetCode 410 - Split Array Largest Sum（分割陣列的最大值）

題目。 把一個非負整數陣列切成剛好 k 段非空的連續子陣列。一種切法的代價是「最大那一段 的和」。回傳所有切法裡最小的那個代價。

輸入／輸出。 輸入 nums 和 k，輸出一個整數。

範例。 nums = [7,2,5,10,8]、k = 2。最好的切法是 [7,2,5] | [10,8]，兩段和為 14 與 18，答案就是 18；其他切法的最大值都更大。

限制。 1 <= len(nums) <= 1000、0 <= nums[i] <= 10^6、1 <= k <= min(50, len(nums))。 答案一定落在 max(nums) 與 sum(nums) 之間，而且「預算 x 夠不夠切成 k 段」對 x 是單調的 —— 這就是為什麼它是一題「對答案做二分搜尋」而不是對陣列做二分搜尋。

LeetCode 875 - Koko Eating Bananas（愛吃香蕉的珂珂）

題目。 有 n 堆香蕉，警衛 h 小時後回來。珂珂會挑一個吃的速度 k（每小時 k 根）。每個 小時她選一堆，從裡面吃掉 k 根；如果那堆剩不到 k 根，她就把整堆吃完，然後*這個小時就結束了* —— 她不會在同一小時內再去吃下一堆。回傳能在 h 小時內吃完所有堆的最小整數 k。

輸入／輸出。 輸入 piles 和 h，輸出最小速度 k。

範例。 piles = [3,6,7,11]、h = 8 → 4。速度 4 需要 1 + 2 + 2 + 3 = 8 小時；速度 3 需要 1 + 2 + 3 + 4 = 10 小時，來不及。

限制。 1 <= len(piles) <= 10^4、len(piles) <= h <= 10^9、1 <= piles[i] <= 10^9。注意 搜尋空間是*數值* k（最大到 10^9），不是陣列 —— 又一題對答案做二分搜尋。
