Binary search is not about finding x

Code: day 23 on GitHub

100 Days of Python - day 23

I can write binary search from memory. So can you. And roughly half the time one of us writes a version that returns an index one too small, terminates cleanly, raises nothing, and is wrong.

That is the interesting thing about this algorithm. It is the first one everybody learns and one of the last one anybody gets right, and the reason is that the version in the textbook - halve the range until a[mid] == x - is almost never the version that ships. Real code asks for a boundary: the first index at or after a key, the smallest batch size a captured CUDA graph can hold, the lowest eating speed that finishes in time, the request that owns a given token. Every one of those is the question "where does false turn into true", and none of them is answered by an equality test.

Yesterday was counting sort, which turned a histogram into an offset table with a prefix sum. Today is the operation that undoes it - and one of the five places sglang runs a binary search is exactly that.

One invariant, and everything follows

Keep two indices, lo and hi, describing a half-open range [lo, hi), and maintain one sentence:

everything in a[:lo] is already known too small, everything in a[hi:] is already known big enough, and the middle is unknown.

Start from [0, len(a)), which is true vacuously because both known regions are empty. Then each step preserves it. If a[mid] < x then mid cannot be the answer, so lo = mid + 1. If a[mid] >= x then mid might be the answer, so hi = mid - not mid - 1, because that would throw away the very element the comparison just proved a candidate.

def lower_bound(a, x):
    lo, hi = 0, len(a)              # half open: hi is a length, not an index
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] < x:
            lo = mid + 1            # answer is strictly right of mid
        else:
            hi = mid                # mid itself may be the answer
    return lo                       # lo == hi is the boundary

There is no early return in that loop. When the range becomes empty the invariant says everything left of lo is too small and everything right of it is big enough, which is the boundary, so lo is the answer - including when the answer is "past the end", which is why hi starts at the length rather than the last index. There is no not-found branch either; lo == hi says it already.

The other one differs by a character

def upper_bound(a, x):
    lo, hi = 0, len(a)
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if a[mid] <= x:             # <= instead of <
            lo = mid + 1
        else:
            hi = mid
    return lo

That is the whole difference: do ties count as "left of the boundary" or not. These two are bisect_left and bisect_right in the standard library, and the pair is more useful than either alone. upper_bound(x) - lower_bound(x) is how many times x occurs. upper_bound(x) - 1 is "the last index at or before x", which is the definition of which bucket does x fall into - keep that one, it comes back before the end of this article.

Three loops that look right

There are exactly two ways to break binary search, and they are not equally visible.

The first is a range that fails to shrink. A closed interval [lo, hi] combined with hi = mid spins forever once lo == hi. Half-open with lo = mid instead of lo = mid + 1 spins as soon as hi - lo == 1, because (lo + hi) // 2 is then lo and the assignment does nothing. Both hang, and a hang gets noticed.

The second is a range that discards the answer:

        else:
            hi = mid - 1            # <-- terminates, and is wrong

On a = [1, 2, 3, 4, 5, 6, 7], looking for the first element at or after 4, that returns 2 where the answer is 3. No exception, no hang, no hint. It stepped over a[mid] at the exact moment the comparison had proved a[mid] was a candidate.

And one more, which cannot happen in Python and absolutely happens everywhere else:

mid = (lo + hi) // 2                # lo = 2_000_000_000, hi = 2_100_000_000

In int32 that sum wraps to -194967296, so mid is -97483648. lo + (hi - lo) // 2 gives 2050000000. Python integers are arbitrary precision so nothing goes wrong here, but the same loop inside a CUDA kernel indexes int32 offsets - and this is the bug that sat inside java.util.Arrays.binarySearch for nine years before Joshua Bloch wrote it up in 2006.

There does not have to be an array

Strip the loop down and what it actually requires is a monotone predicate: a function ok(x) that is false, false, ..., false, true, true, ..., true across the search range. A sorted array is nothing more than the special case ok(i) = a[i] >= x.

def search_first_true(lo, hi, ok):
    while lo < hi:
        mid = lo + (hi - lo) // 2
        if ok(mid): hi = mid
        else:       lo = mid + 1
    return lo

So the recipe becomes: work out what number the answer is, write ok(candidate) - which is usually a simulation rather than a comparison - argue that it is monotone, and run the loop above.

Step three is the entire job. If ok is not monotone the loop still terminates and still returns a number, and the number is meaningless. Nothing complains.

LeetCode 875, Koko eating bananas: given piles and a deadline, find the smallest eating speed that finishes in time. The answer is a speed, so search speeds.

def koko_hours(piles, speed):
    return sum(-(-p // speed) for p in piles)       # ceil division

def min_eating_speed(piles, h):
    return search_first_true(1, max(piles) + 1, lambda s: koko_hours(piles, s) <= h)

Monotone because eating faster can never take longer. For piles = [30, 11, 23, 4, 20] and h = 6 the answer is 23 bananas an hour, found in five probes over a range of thirty:

The row of Ts in that picture is never built. Five simulations is the whole cost. LeetCode 410 is the same shape - the smallest possible largest chunk sum when splitting an array into m pieces - with a range from max(nums) to sum(nums) and a greedy chunking as the predicate.

When the predicate is expensive, and lies

sglang's autotuner binary searches the request rate: it asks "did the server meet the SLA at this qps?", and every answer costs a full benchmark run. Two things change once ok is a measurement.

Termination is no longer lo < hi, because a float interval can always be halved again. The loop ends on a tolerance and a round budget. And a rounded midpoint can land exactly on an endpoint, at which point the interval stops shrinking - the float twin of the integer infinite loop, and it needs its own guard:

        mid = round((lo + hi) / 2, 4)
        if mid <= lo or mid >= hi:
            break                       # midpoint collapsed onto an endpoint

The bigger problem is that the predicate is no longer monotone. With run-to-run noise of ±0.6 qps around a true capacity of 13.7, two probes out of ten disagree with the truth - one run measured 13.256 and failed a qps of 13.55 that should have passed. And binary search never revisits a discarded half, so a wrong answer in the middle of the search is unrecoverable.

That is why the real loop keeps the best value that actually ran and actually passed, rather than reporting a bracket endpoint, and why the tolerance has to be wider than the noise. Converging to three decimal places on a noisy measurement just means treating noise as signal.

What a probe actually costs

sglang's radix cache has to answer "how long a prefix do these two token sequences share?" on every incoming request. It does not walk token by token, and it does not binary search the whole range either. RadixKey.match compares windows of length 1, 2, 4, 8, ... until one differs, then binary searches inside that window alone.

Why not plain binary search? Because of how you count. On two 4096-token sequences:

       p |  linear          |  binary          |  gallop
         | probes   tokens  | probes   tokens  | probes   tokens
  -------+------------------+------------------+-----------------
       0 |      1        1  |     13     4108  |      1        1
      17 |     18       18  |     12     4171  |      9       46
     250 |    251      251  |     12     5635  |     15      382
    2048 |   2049     2049  |     12    22541  |     23     6142
    4096 |   4096     4096  |     12    45069  |     13     4096

Counting probes, plain binary search looks unbeatable - twelve or thirteen no matter what. But a probe compares a slice, not an element, so probes are neither free nor equal. Counting tokens touched, binary search does about n log n work while galloping does O(p): the windows double, so their lengths sum to roughly 2p, and only the last one gets searched.

Note that galloping is not uniformly better. At p ≈ n/2 it makes about twice as many probes as binary search. It is the right bet here because a prefix cache is a bimodal workload - a new conversation shares almost nothing, a follow-up turn shares almost everything, and hardly anything lands in the middle. (And notice linear touches the fewest tokens of all. Its problem is that it touches them one at a time from Python, while the other two hand whole slices to the C-level compare.)

One nice detail in the inner loop: it is written while hi - lo > 1 with lo = mid, which is the assignment I called a hang two sections ago. It is safe here precisely because that loop condition forces mid strictly above lo. Same characters, different invariant, different verdict - which is why "memorise the template" is bad advice and "state the invariant" is not.

Undoing a prefix sum

Yesterday's counting sort ran an exclusive scan over a histogram to get an offset table. Every batched kernel in an inference server carries that table as cu_seqlens, and every kernel that works one token at a time has to invert it: given a flat token index, which request owns it?

seq_of = torch.searchsorted(cu_seqlens, tok, right=True) - 1

Read out loud, that is "the last start at or before tok" - which is upper_bound(tok) - 1, the bucket question from the second section. right=False asks for the first start at or after tok, and at a boundary that start is the next request. So with seq_lens = [3, 5, 2] the wrong version is wrong at tokens 0, 3 and 8 - the first token of every request, no more and no less - and token 0 gets -1, which then indexes the last entry of cu_seqlens and reads another request's state. Nothing raises.

The mirror image rounds a batch size up. A CUDA graph is captured for a fixed shape, so a decode step of 37 requests has to replay on the smallest captured shape that can hold it, and sglang's _pad_to_bucket is one line:

index = bisect.bisect_left(buckets, raw_size)
return buckets[index]

bisect_left, not bisect_right. When the batch already is a captured size, bisect_left returns that size and nothing is padded; bisect_right steps to the next bucket and pays for a whole graph's worth of empty rows. Averaged over batch sizes 1 to 255 on the default capture list that is 4.25% padding versus 6.07% - from one character - and at the largest batch bisect_right runs off the end of the list entirely.

The interview version

LeetCode 34, first and last position of a target, is the best argument for learning the boundary version rather than the find-x version:

def search_range(nums, target):
    lo = lower_bound(nums, target)
    hi = upper_bound(nums, target)
    return [lo, hi - 1] if lo < hi else [-1, -1]

The count is hi - lo, and the not-found case falls out of lo == hi with no extra branch and no sentinel. Start instead from "return as soon as a[mid] == target" and you have to scan outwards from the hit, which is O(n) on an array of equal values.

The caveat worth having ready: LeetCode 33 searches a rotated sorted array, which is not monotone at all. It still halves, because at every mid one of the two halves is sorted and "is the target inside that half" is decidable. Sorted is stronger than binary search needs. All the loop requires is that each step can rule out one side.

Where this goes

The five sglang searches in this article are all boundary searches, and none of them looks like the textbook. Padding a batch up to a captured shape is bisect_left. Recovering a request id from a token index is upper_bound - 1. Matching a cached prefix is exponential search. Autotuning a request rate is bisection over a noisy measurement. And a decode kernel picking a tile size does the same thing again.

Next up is the Trie and the radix tree - the structure that gallop was walking a key of. After that, string matching, where the "compare a slice, not an element" cost model from this article turns into rolling hashes.

LeetCode 33 - Search in Rotated Sorted Array

The task. An ascending array of distinct integers was rotated at some unknown pivot - [0,1,2,4,5,6,7] may arrive as [4,5,6,7,0,1,2]. Given the rotated array and a target, return the index of target, or -1 if it is not there.

Input / output. Input is nums and target; output is an index (or -1).

Example. nums = [4,5,6,7,0,1,2], target = 0 → 4. With target = 3 → -1.

Constraints. 1 <= len(nums) <= 5000, values in [-10^4, 10^4], all distinct, and the array is guaranteed to be a rotation of a sorted array. The runtime must be O(log n), so a linear scan is not an accepted answer.

leetcode.com/problems/search-in-rotated-sorted-array

LeetCode 34 - Find First and Last Position of Element in Sorted Array

The task. Given a non-decreasing array and a target, return the first and the last index at which target appears, as [first, last]. If the target is absent return [-1, -1].

Input / output. Input is nums and target; output is a two-element list.

Example. nums = [5,7,7,8,8,10], target = 8 → [3,4]. With target = 6 → [-1,-1].

Constraints. 0 <= len(nums) <= 10^5, values in [-10^9, 10^9], the array is sorted non-decreasing (duplicates allowed). Again O(log n) is required - which is exactly the "find the boundary, not the element" flavour of binary search.

leetcode.com/problems/find-first-and-last-position-of-element-in-sorted-array

LeetCode 410 - Split Array Largest Sum

The task. Cut an array of non-negative integers into exactly k non-empty contiguous pieces. Each cut has a cost: the largest piece sum. Return the smallest largest-piece-sum achievable over all ways of cutting.

Input / output. Input is nums and k; output is one integer.

Example. nums = [7,2,5,10,8], k = 2. The best cut is [7,2,5] | [10,8] with sums 14 and 18, so the answer is 18 - every other cut has a larger maximum.

Constraints. 1 <= len(nums) <= 1000, 0 <= nums[i] <= 10^6, 1 <= k <= min(50, len(nums)). The answer lives between max(nums) and sum(nums), and "can I do it with a budget of x?" is monotone in x - which is what makes this a binary search on the answer rather than on an array.

leetcode.com/problems/split-array-largest-sum

LeetCode 875 - Koko Eating Bananas

The task. There are n piles of bananas and h hours before the guards come back. Koko picks an eating speed k (bananas per hour). Each hour she chooses one pile and eats k bananas from it; if the pile has fewer than k left she eats the whole pile and then stops for that hour - she never moves on to a second pile within the same hour. Return the smallest integer k that lets her finish every pile within h hours.

Input / output. Input is piles and h; output is the minimum speed k.

Example. piles = [3,6,7,11], h = 8 → 4. At speed 4 the hours needed are 1 + 2 + 2 + 3 = 8; at speed 3 they are 1 + 2 + 3 + 4 = 10, which is too slow.

Constraints. 1 <= len(piles) <= 10^4, len(piles) <= h <= 10^9, 1 <= piles[i] <= 10^9. Note the search space is the value k up to 10^9, not the array - another binary search on the answer.
