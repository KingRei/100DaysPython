100 Days of Python - day 32

Chrome checks every URL you visit against a list of known-malicious sites, without downloading the list and without asking Google about every page you open. Redis can tell you how many distinct users hit your site today out of 16 KB of memory, for any number of users. Neither of those is possible with an exact data structure, and both of them are wrong sometimes - on purpose, in a direction chosen in advance.

Yesterday's skip list used randomness to get a shape without rebalancing. Today randomness buys something bigger: memory that stops growing with the data.

The trade, stated precisely

A Bloom filter sized for 10,000 items at a 1% false positive rate is 11,982 bytes. A Python set holding the same 10,000 strings is 1,103,394 bytes - 92 times larger, and it grows with the length of the strings while the filter does not. A HyperLogLog is 16,384 bytes whether it has seen a thousand distinct users or five hundred thousand.

The part worth internalising is not the size of the error but its direction:

  • A Bloom filter only ever says yes too often. It never loses something you added.
  • A Count-Min sketch only ever over-counts. Its answer is never below the truth.
  • HyperLogLog can miss in either direction. That is why its unions are free and its intersections are worthless.

The size of the error always comes with a knob. The direction never does, and it is what decides whether the code after the answer is still correct.

Bloom filter: k bits switched on, and no way back

def add(self, item):
    h1, h2 = hash_pair(item)
    for i in range(self.k):
        self.bits[(h1 + i * h2 + i * i) % self.m] = 1

def __contains__(self, item):
    h1, h2 = hash_pair(item)
    return all(self.bits[(h1 + i * h2 + i * i) % self.m]
               for i in range(self.k))

An item becomes k positions in an m-bit array and those bits go to 1. A query recomputes the same positions: one zero proves the item was never added, all ones means it probably was. You do not need k real hash functions - the Kirsch-Mitzenmacher trick builds them all from two, with g_i = h1 + i·h2 + i², and one BLAKE2b digest split in half provides both.

Two formulas size it: m = -n ln p / (ln 2)² bits and k = (m/n) ln 2 hashes. For 10,000 items at 1% that is 9.59 bits per item and 7 hashes. Measured over 100,000 lookups of items never added, the false positive rate is 1.03% against a 1.00% design, and the false negative count over the 10,000 real members is zero - not "small", zero, by construction.

That 1% is a promise about a load, not about the structure:

  load    items      fill    expected    measured
  0.5x      500     30.7%       0.03%       0.01%
  1.0x     1000     52.5%       1.00%       1.26%
  2.0x     2000     77.1%      15.74%      16.19%
  4.0x     4000     94.8%      67.86%      69.18%
  8.0x     8000     99.7%      97.99%      97.50%

Past its design size the filter does not degrade gently, it degrades like a power. At eight times the load it says yes to everything, which is not a filter at all.

Delete is not a missing feature, it is an impossible one

A bit set by alpha may also have been set by bravo. In a deliberately tiny filter - 64 bits, k = 3, 14 words - clearing the three bits of alpha takes bravo and india down with it. Two false negatives, in a structure whose whole contract is that false negatives cannot happen. Nothing raises an error; the filter just starts answering no about things that are plainly in the set.

A counting Bloom filter swaps each bit for a 4-bit counter, so a shared slot drops from 2 to 1 instead of to 0 - zero false negatives on the same test. The price is four times the memory and saturation: once a counter hits 15 it stops rising, and every later decrement is wrong.

The more expensive mistake is trusting a yes. Deduplicating 20,000 documents with a 1% filter keeps 13,932 of the 13,954 distinct ones - 22 documents declared "already seen" and dropped. The filter did exactly what it promised. As a pre-filter in front of a real lookup, a false positive costs one wasted read; as the final answer, it costs data that never comes back. Same structure, same error rate, and the difference is entirely in what the code does after the yes.

HyperLogLog: a maximum that counts

Flip a coin repeatedly and a run of r heads shows up about once in 2^r tries, so the longest run you have seen estimates how many tries you made - and a maximum needs one number of storage, not a list.

def add(self, item):
    h = hash64(item)
    idx = h & (self.m - 1)                    # low p bits pick a register
    rho = trailing_zeros(h >> self.p) + 1     # the run of zeros
    self.reg[idx] = max(self.reg[idx], rho)

Because it is a maximum, feeding the same item in a thousand times changes nothing: the sketch deduplicates for free. One register is far too noisy, so the estimate is a harmonic mean across all m registers - harmonic because it damps the ones that got a freakish run - with linear counting taking over at the low end. At p = 14 that is 16,384 one-byte registers and a theoretical error of 1.04/√m = 0.81%:

     true     estimate     error   hll bytes   exact bytes    ratio
     1000         1005     0.52%       16384         64984       4x
    10000         9930    -0.70%       16384        844504      52x
   100000        99924    -0.08%       16384       7394520     451x
   500000       504141     0.83%       16384      32777432    2001x

The memory column does not move. That is the entire point.

The property that makes HLL ship is that merging is a register-wise maximum and it is exact: merging two shards gives byte-identical registers to one machine scanning everything. Keep one sketch per hour and any range of hours rolls up later with no accumulated error.

Intersections are the trap. |A ∩ B| = |A| + |B| - |A ∪ B| is algebraically true and numerically hopeless. With |A| = |B| = 200,000 and a true intersection of 2,000, the union is estimated to within 0.84% and the intersection comes out at 1,681 - a 16% error. Three relative errors on numbers near 200,000 become one absolute error the size of the answer. Inclusion- exclusion subtracts big numbers to get a small one, which is exactly what an estimator with relative error cannot survive.

Count-Min sketch: every row over-counts, so take the smallest

def query(self, item):
    return min(self.rows[i][self._hash(item, i) % self.w]
               for i in range(self.d))

d rows of w counters, each row a complete tally of the stream with its own collisions folded in. A collision can only push a counter up, so the smallest row is the least polluted and the answer is never below the truth. Sizing is w = ⌈e/ε⌉, d = ⌈ln(1/δ)⌉, for an error of at most ε·N with probability 1 - δ.

On 200,000 events over 4,934 distinct keys, a 5 × 5,437 sketch (108,740 bytes, against 443,608 for a Counter) has a guaranteed bound of +100, a worst observed error of 21 and zero under-counts. Where that error lands is the lesson: +0.01% relative on the top ten keys, +150% on the bottom ten. The bound is absolute, so the same 21-count error is rounding noise on a key seen 31,648 times and the entire answer on a key seen once. Excellent at "which keys are big"; useless at "did this key appear exactly once".

The conservative update - only raise the counters currently at the minimum - drops the mean error from 0.3 to 0.1 for free and keeps the guarantee. It makes delete impossible, but delete was never on the menu.

LeetCode 347, with and without enough memory

def top_k_frequent(nums, k):
    counts = Counter(nums)
    return heapq.nlargest(k, counts, key=counts.get)

Counter plus a k-sized heap: O(n) time, memory proportional to the number of distinct keys. In the interview that is the answer. The sketch version is the follow-up when the array becomes a stream with a billion keys: add each item to a Count-Min sketch, query it straight back, keep only k candidates. On a 200,000-event Zipf stream with k = 10 it returns the same ten keys, in the same order, with the same counts, out of 108,740 bytes instead of 443,608.

Then flatten the stream - top key 65 occurrences, tenth 61 - and it drops w-385. Approximate top-k only means something when the head stands clear of the noise floor: the k-th true count has to be comfortably larger than e/w · N. That is the sizing rule, and it is the same rule in all three structures - decide how wrong you can afford to be, and in which direction, then buy exactly that much memory.

Picking one

structure     question             error direction        bytes @1e6
set (exact)   membership + count   none                     60000000
Bloom filter  have I seen x?       false positive only       1198133
HyperLogLog   how many distinct?   relative, both ways         16384
Count-Min     how often is x?      over-count only            108740

All three are mergeable, which is why they survive in distributed systems: Bloom filters with the same m and k OR together, HLL registers take the max, Count-Min rows add. Bloom filters run Chrome Safe Browsing, Cassandra and LevelDB SSTable lookups and SPV wallets - a cheap no that skips an expensive disk or network read. HyperLogLog is Redis PFCOUNT, BigQuery APPROX_COUNT_DISTINCT, Presto approx_distinct. Count-Min runs network flow monitoring, trending topics and per-key rate limiting.

These structures also keep appearing in the parts of an LLM stack that have to stay cheap: sketching which prefixes are hot enough to be worth keeping in a cache, estimating the number of distinct n-grams in a corpus without materialising them, deduplicating a training set - the last one being precisely where a Bloom filter's false positive stops being free and starts deleting documents.

LeetCode 347 - Top K Frequent Elements

The task. Given an integer array and an integer k, return the k most frequent elements. The order of the returned elements does not matter.

Input / output. Input is nums and k; output is a list of k values.

Example. nums = [1,1,1,2,2,3], k = 2 → [1,2]. nums = [1], k = 1 → [1].

Constraints. 1 <= len(nums) <= 10^5, values in [-10^4, 10^4], k is between 1 and the number of distinct values, and the answer is guaranteed to be unique. The problem explicitly demands better than O(n log n), so sorting the whole frequency table is out - a size-k heap or bucket-by-count works. The version worth thinking about is the one the constraints hide: the same question over a stream too large to hold a counter for, which is where a Count-Min sketch plus a small heap takes over and the answer becomes approximate.
