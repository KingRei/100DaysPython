Day 62 — Mixture of Experts：讓模型的參數變多，但每個 token 的成本不變

程式碼：day 62 on GitHub

100 Days of Python - day 62

Day 53 量過一件事，而它其實就是整件事的起點：transformer 三分之二的參數在 feed-forward 那一塊，而每個 token 都要把它們全部跑過一遍。每個 token、每個權重，不管那個權重對這個特定的 token 有沒有話要說。

那就把那一個 FFN 換成 E 份，每個 token 只送去最好的 k 份。參數乘上 E，每個 token 的算術只乘上 k。

                                          參數    每個 token 實際跑的
----------------------------------------  ------  -------------------
一個 dense FFN（dmodel 4096、dff 14336）  176 M   176 M
64 個 expert ＋ 1 個 shared               11.5 B  528 M

參數 65 倍，每個 token 的算術只有 3 倍。 把 61 層加起來就是 699 B 參數、而任何一個 token 只跑 32 B——這兩年所有大型開源 MoE 的形狀都是這樣。換個說法：這一層等於一個寬度 917,504 的 feed-forward，但每個 token 只會啟動其中 28,672。

而這一切當然不是免費的，本文其餘的部分就是那張帳單。

Router，以及它造出來的那個迴圈

probs = softmax(x @ Wg)          # 給每個 expert 打分
idx   = argsort(-probs)[:, :k]   # 離散：沒有梯度穿得過去
w     = probs[idx]               # 這幾個權重才有梯度
y     = sum_j w[:, j] * expert[idx[:, j]](x)

一層 linear 決定哪個 token 去哪個 expert。有兩件事讓 MoE 難訓練，而且兩件都來自同一行。

選 top-k 是離散的。梯度過不了 argsort，所以 router 唯一能學到東西的管道，是它「已經選上的那幾個 expert 的權重 w」。沒被選上的 expert 拿不到梯度、不會變好、於是永遠選不上。早期的贏家會愈滾愈大。

而且 loss 裡面根本沒有任何一項要求 token 要分散。對任務 loss 來說，三個 expert 把所有工作做完完全沒問題——而那正是實際會發生的事。

把「塌掉」量出來長什麼樣

moe.py 真的訓練一個：2048 個 token、8 種 regime（正確答案取決於 token 落在空間的哪一區）、16 個 expert、top-2，router 和 expert 一起手刻訓練。

一個 dense map（被取代掉的那個 FFN）     loss 0.0363
16 個 expert、top-2、沒有平衡             loss 0.0230   （好 37%）

每個 expert 拿到的 token  [579, 554, 550, 475, 461, 405, 352, 323, 293, 84, 14, 3, 1, 1, 1, 0]
最忙 / 平均               2.26
完全沒用到的 expert        16 個裡有 1 個

MoE 的 loss 贏了 37%，然後有一個 expert 一輩子沒看過任何一個 token，另外四個看到的不到十五個。那些參數照樣佔記憶體、照樣被存進 checkpoint、照樣要參加把 token 搬來搬去的 all-to-all——它們不只是沒用，它們很貴。

兩種讓 token 分散開的方法

router                            loss    最忙/平均  死掉  entropy  純度
--------------------------------  ------  ---------  ----  -------  -----
沒有平衡                          0.0230  2.26       1     0.812    0.641
輔助 loss（Switch / GShard）      0.0241  1.98       0     0.922    0.645
只加選擇用的 bias（DeepSeek-V3）  0.0257  1.05       0     1.000    0.568

輔助 loss 加的是 E × Σ(路由到 i 的 token 比例 × i 的平均機率)。兩個因子缺一不可、而且各司其職：比例是「實際發生了什麼」、沒有梯度；機率是可微的；相乘之後，已經很忙的 expert 的機率會被推開。在這裡它讓 loss 退了 5%。

不加 loss 的那個做的事比較細緻。它給每個 expert 一個 bias，只加在挑選用的分數上——絕對不加在乘上 expert 輸出的權重 w 上——然後每一步依照該 expert 負載誤差的正負號去微調它。因為 bias 碰不到 w，它不產生任何自己的梯度，也就不會跟任務 loss 打架，它只是搬動 token。結果是這一頁最平的負載、routing entropy 剛好 1.000，代價是 loss 退 12%、以及一些專一性。

誠實地看這張表：在一個玩具問題上，平衡看起來是個划不來的交易。接下來所有東西都是在說為什麼它不是。

Capacity：buffer 是固定大小的，所以 token 會被丟掉

kernel 要固定形狀，所以每個 expert 有一個 capacity = factor × k × tokens / experts 的 buffer，超過的 token 直接沿著 residual 跳過這一層。

factor  buffer  不平衡時掉的  平衡後掉的  padding
------  ------  ------------  ----------  -------
1.0     256     41.2%         1.1%        +0%
1.25    320     27.8%         0.0%        +25%
1.5     384     17.6%         0.0%        +50%
2.0     512     3.6%          0.0%        +100%

factor 1.0 時 buffer 剛好等於平均負載，所以高於平均的 token 全被丟掉、低於平均的 expert buffer 空一半。把 factor 調大，是把每一個 expert 的 buffer 都撐大來遷就最忙的那一個，所以最後那一欄是整層都要付的無效算術。不平衡的 router 即使到 factor 2.0 還是掉 3.6%；平衡過的在 1.25 就已經是 0。

這是「划不來的交易」開始不成立的第一個地方。

Expert parallelism：experts 放不進一張卡

一層 11.5 B 的參數不可能放在一張卡上。expert parallelism 把 E 個 expert 切給 N 張卡、每張 E/N 個——於是一個 token 如果它的 expert 在別張卡上，就得被送過去、算完再送回來。每一層兩次 all-to-all，每一層、每一步都要。

而 collective 是同步的：所有人都要等最慢的那一個。所以 router 的不平衡就不再是 loss 上的一個數字，而是閒置的晶片。

不平衡的 router、4 張卡：  1582 / 798 / 1361 / 355 個 token
                           最忙/平均 1.54，其他卡閒置 35%
平衡過的 router：          1022 / 1001 / 1032 / 1041
                           最忙/平均 1.02

那為什麼是 expert parallel，而不是把每個 expert 切開給所有卡（tensor parallel）？兩者每張卡放的權重一樣多。差別在每個 token 要搬多少：TP 每層要對整個活化做一次 all-reduce（這個配置下 58.7 MB），EP 是對被路由的 token 做兩次 all-to-all（k=2 時 117.4 MB）。EP 搬的位元組是兩倍——而它仍然是對的答案，因為那是稀疏、不規則、而且可以跟計算重疊的流量，而層末的 all-reduce 是一道屏障。實務上兩個一起用：attention 用 tensor parallel，experts 用 expert parallel。

DeepEP：讓那兩次 all-to-all 付得起

4096 個 token、top-8、d_model 7168 的一次 dispatch 要搬 470 MB，combine 再搬回來一次。節點內走 NVLink，跨節點走 RDMA、速度只有幾分之一，而且大部分目的地都在別的節點。DeepEP 就是為這個 collective 寫的函式庫，裡面有三件事值得理解，即使你永遠不會直接呼叫它。

兩套 kernel，對應兩種階段。 高吞吐那套會先用 NVLink 把 token 轉送到目的節點上，然後每個目的節點只走一次 RDMA，把慢速鏈路上的位元組壓到最低——這是 prefill 與訓練要的取捨。低延遲那套相反：純 RDMA、不轉送，因為在 decode 階段那一跳比它省下來的頻寬更貴。

FP8 dispatch。 把前一天那套東西用在網路線上：token 用 FP8 送出去，470 MB 變 235 MB，在這個模型裡 8.59 ms 變 4.29 ms。而 combine 仍然用 bf16，因為它要把 k 個 expert 的輸出相加，FP8 在那裡掉太多。兩個方向用不同精度，這個不對稱是刻意的。

重疊。 低延遲 kernel 提供一個 hook，讓「收資料」不是一道屏障：attention 可以在 MoE 的 token 還在路上時就先算，而且不會有 SM 在那裡空轉等網路。沒有這個重疊，每層兩次 all-to-all 根本撐不住。

在 PyTorch 裡怎麼寫這一層

整層大概五十行，而有意思的地方是：那個「對 expert 迴圈」正是你要想辦法避開的東西。

class MoE(nn.Module):
    def __init__(self, d_model, d_ff, n_experts, k):
        self.gate = nn.Linear(d_model, n_experts, bias=False)
        # 所有 expert 放成「一個」參數，不是 ModuleList：
        self.w1 = nn.Parameter(torch.empty(n_experts, d_model, d_ff))
        self.w2 = nn.Parameter(torch.empty(n_experts, d_ff, d_model))
        self.k = k

    def forward(self, x):                       # x: (tokens, d_model)
        probs  = self.gate(x).softmax(-1)
        w, idx = probs.topk(self.k, dim=-1)     # (tokens, k)
        w = w / w.sum(-1, keepdim=True)

        flat   = idx.reshape(-1)                # 每個 token 有 k 筆
        order  = flat.argsort()                 # 依 expert 分組
        counts = torch.bincount(flat, minlength=self.w1.shape[0])
        xs = x.repeat_interleave(self.k, 0)[order]

        h  = F.silu(torch._grouped_mm(xs, self.w1, counts))
        ys = torch._grouped_mm(h, self.w2, counts)

        out = torch.zeros_like(x)
        token_of = torch.arange(len(x)).repeat_interleave(self.k)
        out.index_add_(0, token_of[order], ys * w.reshape(-1, 1)[order])
        return out

這裡藏了四個設計決定，而且每個真實實作裡都是同樣這四個。

experts 是一個 tensor，不是一個 list。 用 nn.ModuleList([nn.Linear(...) for _ in range(E)]) 是最自然的寫法，但那代表 E 次 kernel launch、E 次權重載入，而且 expert 的編號沒辦法當索引用。寫成一個 (E, d_model, d_ff) 的 Parameter 之後，「選一個 expert」就變成「選一個索引」——後面三個決定才有可能。

用排序，不要用遮罩。 直覺的寫法是乘上 one-hot 遮罩、讓每個 expert 都算過每個 token；結果是對的，而且算術量變成 E 倍，MoE 的意義整個消失。實務上是：依 expert id 排序 token、對不等長的分組做一次 grouped matmul（torch._grouped_mm，或 Megatron-LM／vLLM 裡的 Triton kernel），最後再排回去。

回填要用 index_add_。 一個 token 出現 k 次、k 份 expert 輸出要相加，所以必須是「加」不是「寫」——而 gate 權重的梯度也正是從這個加法來的。

平衡用的 aux loss 要從 forward 回傳。 它需要 probs 和路由計數，而那兩個只有 layer 裡面才有。每個 MoE 程式庫最後都會有一個「各層把 aux loss 丟進去、訓練迴圈再加總」的清單。

分散式版本的 dispatch 就是一行 collective：

torch.distributed.all_to_all_single(recv, send, out_splits, in_splits)

而那些 splits 就是排序後每個 rank 的 token 數。不平衡的 router 會讓 splits 歪掉，所有人都要等最大的那一個——這就是前面那些負載數字真正變成時間的地方。

在 JAX 裡怎麼寫這一層

同一個演算法，程式碼長得完全不一樣，因為 JAX 要的是固定形狀加上一條 sharding 規則，而不是 gather。

def moe(x, wg, w1, w2, k, capacity):
    probs  = jax.nn.softmax(x @ wg)                   # (T, E)
    w, idx = jax.lax.top_k(probs, k)
    mask = jax.nn.one_hot(idx, n_experts).sum(1)      # (T, E)
    pos  = jnp.cumsum(mask, axis=0) * mask - 1        # buffer 裡的位置
    disp = mask[..., None] * jax.nn.one_hot(pos, capacity)   # (T, E, cap)

    xe = jnp.einsum("tec,td->ecd", disp, x)           # 固定大小 (E, cap, d)
    he = jax.nn.silu(jnp.einsum("ecd,edf->ecf", xe, w1))
    ye = jnp.einsum("ecf,efd->ecd", he, w2)
    return jnp.einsum("ecd,tec,te->td", ye, disp, w)

那串 einsum 就是 dispatch 和 combine 本身。沒有排序、沒有變動長度，而且 capacity 直接出現成陣列的一個維度——這正是 capacity factor 存在的理由：buffer 是固定的，滿出來的 token 沒有地方可以去。

而平行化是一個標註，不是一次呼叫：

mesh = Mesh(devices, ("data", "expert"))
w1   = jax.device_put(w1, NamedSharding(mesh, P("expert", None, None)))
moe  = shard_map(moe, mesh, in_specs=..., out_specs=...)

把 w1 的 expert 軸 shard 掉，這就是 expert parallelism 的全部。einsum 需要住在別的裝置上的資料，所以 XLA 自己插入 all-to-all，沒有人手寫那個 collective。這也是兩個生態系真正的差別：PyTorch 是你呼叫 all_to_all_single 並自己管 splits；JAX 是你標註軸、編譯器產生通訊。

代價也很對稱：排序版本只對真正被路由到的 token 做算術，但要快就需要自訂 kernel；one-hot 版本是純 dense einsum、任何編譯器都能融合，但 buffer 裡每一個空位都要付錢。

上線的時候，簡短版

兩個伺服器開出來的是同樣兩個決定。experts 住在哪幾張卡——SGLang 的 --ep-size 8、vLLM 的 --enable-expert-parallel；以及那兩次 all-to-all 由誰來搬——SGLang 的 --enable-deepep-moe 配 --deepep-mode normal|low_latency|auto，vLLM 底下接 DeepEP 或 pplx-kernels。而兩邊最後都跑成「attention 用 data parallel、experts 用 expert parallel」，因為 attention 沒有 expert 可以分，而 MoE 的權重不切放不下。

除此之外值得知道的是 SGLang 的 --enable-eplb 搭 --ep-num-redundant-experts。訓練時的平衡 loss 壓平的是平均，而真實流量不是平均：某一分鐘的請求可能全都想要同一批 expert。所以伺服器會量線上每個 expert 的負載、把 expert 在 rank 之間搬動、並把最熱的那幾個複製出去。訓練時的塌縮問題，在線上以維運問題的形式回來，然後拿到一個維運上的答案。

這一天之後會在哪裡再出現

「路由」是一個用梯度下降去訓練的離散選擇，而這個困難在強化學習、以及所有「學架構而不是學權重」的嘗試裡都會再出現。另外，load balancing 的那個故事——訓練時壓平平均，上線後再針對真實流量重新平衡——是一個值得認出來的模式：你能事先烤進去的東西，和你必須線上量測的東西之間的分界，在快取、在排程、在任何「工作負載不是穩態」的地方都一樣會出現。
