Mixture of Experts: one feed-forward block becomes many, and each token runs two of them

Code: day 62 on GitHub

100 Days of Python - day 62

Day 53 measured something that turns out to be the whole starting point: two thirds of a transformer's parameters sit in the feed-forward block, and every token pays for all of them. Every token, every weight, whether or not that weight has anything to say about this particular token.

So replace the one feed-forward block with E copies of it, and send each token to the best k. The parameters multiply by E; the arithmetic per token multiplies by k.

                                        parameters  active per token
--------------------------------------  ----------  ----------------
one dense FFN (dmodel 4096, dff 14336)  176 M       176 M
64 experts + 1 shared                   11.5 B      528 M

65x the parameters for 3x the arithmetic per token. Across 61 layers that is 699 B parameters of which 32 B run for any given token, which is the shape of every large open MoE released in the last two years. Another way to say the same thing: the layer is a feed-forward block of width 917,504 that only ever activates 28,672 of it per token.

Nothing about that is free, and the rest of this article is the bill.

The router, and the loop it creates

probs = softmax(x @ Wg)          # score every expert
idx   = argsort(-probs)[:, :k]   # discrete: no gradient flows through this
w     = probs[idx]               # the weights that do get a gradient
y     = sum_j w[:, j] * expert[idx[:, j]](x)

One linear layer decides which expert sees which token. Two things about it make MoE hard to train, and both follow from the same line.

The selection is discrete. No gradient passes through argsort, so the router can only learn through the weights w of the experts it already chose. An expert that is never chosen never receives gradient, never improves, and therefore is never chosen. Early winners compound.

And nothing in the loss asks the tokens to spread out. The task loss is perfectly happy for three experts to do all the work, which is exactly what happens.

What collapse looks like when you measure it

moe.py trains the thing for real: 2048 tokens drawn from 8 regimes (the right answer depends on which region of space the token falls in), 16 experts, top-2, trained jointly with the router by hand.

one dense map (the FFN being replaced)    loss 0.0363
16 experts, top-2, no balancing           loss 0.0230   (37% better)

tokens per expert  [579, 554, 550, 475, 461, 405, 352, 323, 293, 84, 14, 3, 1, 1, 1, 0]
busiest / average  2.26
dead experts       1 of 16

The MoE wins on the loss by 37%, and one expert never sees a token in its life. Four more see fewer than fifteen. Those parameters still occupy memory, still get checkpointed, and still take part in the all-to-all that ships tokens around - they are not merely useless, they are expensive.

Two ways to make the tokens spread out

router                                 loss    busiest / avg  dead  entropy  purity
-------------------------------------  ------  -------------  ----  -------  ------
no balancing                           0.0230  2.26           1     0.812    0.641
auxiliary loss (Switch / GShard)       0.0241  1.98           0     0.922    0.645
selection bias, no loss (DeepSeek-V3)  0.0257  1.05           0     1.000    0.568

The auxiliary loss adds E * sum_i (fraction of tokens routed to i) * (mean probability of i). Both factors are necessary and they do different jobs: the fraction is what actually happened and carries no gradient, the probability is differentiable, and multiplying them pushes probability away from experts that are already busy. It costs 5% of loss here.

The loss-free scheme does something subtler. It gives each expert a bias that is added to the selection score only - never to the weight w that multiplies the expert's output - and nudges it after every step by the sign of that expert's load error. Because the bias never touches w, it adds no gradient of its own and cannot fight the task loss; it just moves tokens. It produces the flattest load on the page, a perfectly uniform routing entropy of 1.000, and costs 12% of loss and some specialisation.

Read that table honestly: on a toy, balancing looks like a bad trade. Everything after this is why it is not.

Capacity: the buffers are fixed, so tokens get dropped

Kernels want fixed shapes, so each expert gets a buffer of capacity = factor * k * tokens / experts, and tokens past it skip the layer through the residual connection.

factor  capacity  dropped, unbalanced  dropped, balanced  padding
------  --------  -------------------  -----------------  -------
1.0     256       41.2%                1.1%               +0%
1.25    320       27.8%                0.0%               +25%
1.5     384       17.6%                0.0%               +50%
2.0     512       3.6%                 0.0%               +100%

At factor 1.0 the buffer is exactly the average load, so every token above average is dropped and every expert below it leaves its buffer half empty. Raising the factor pads every expert to make room for the busiest one, so that last column is arithmetic wasted across the whole layer. The unbalanced router still drops 3.6% at factor 2.0; the balanced one is at zero by 1.25.

That is the first place the "bad trade" stops looking bad.

Expert parallelism: the experts do not fit on one GPU

11.5 B parameters per layer do not live on one card. Expert parallelism splits the E experts over N GPUs, E/N each - so a token whose expert lives elsewhere has to be sent there and its result sent back. Two all-to-all collectives per MoE layer, every layer, every step.

A collective is synchronous: everyone waits for the slowest rank. So the router's imbalance stops being a loss number and becomes idle silicon.

unbalanced router, 4 GPUs:  1582 / 798 / 1361 / 355 tokens
                            busiest / average 1.54, the others idle 35%
balanced router:            1022 / 1001 / 1032 / 1041
                            busiest / average 1.02

Why expert parallelism rather than splitting every expert across all GPUs with tensor parallelism? Both hold the same weights per GPU. The difference is what moves per token: TP all-reduces the whole activation once per layer (58.7 MB in this configuration), EP all-to-alls only the routed tokens, twice (117.4 MB at k=2). EP moves twice the bytes - and is still the right answer, because that traffic is sparse, uneven, and overlappable with computation, while an all-reduce at the end of a layer is a barrier. Real systems use both: tensor parallelism inside the attention, expert parallelism across the experts.

DeepEP: making the all-to-all affordable

One dispatch of 4096 tokens at top-8 routing with d_model 7168 moves 470 MB, and the combine moves it back. Inside a node that is NVLink; between nodes it is RDMA at a fraction of the speed, and most destinations are on another node. DeepEP is the library written for exactly this collective, and three things in it are worth understanding even if you never call it directly.

Two kernel sets, for the two phases. The high-throughput kernels forward a token over NVLink to the destination node and then send it once per destination node over RDMA, which minimises bytes on the slow link - the right trade for prefill and training. The low-latency kernels do the opposite: pure RDMA, no forwarding hop, because in decode that hop costs more than the bandwidth it saves.

FP8 dispatch. The previous day applied to a network cable: send the tokens in FP8 and 470 MB becomes 235 MB, 8.59 ms becomes 4.29 ms in this model. The combine stays in bf16, because it sums k expert outputs and FP8 loses too much there. The asymmetry between the two directions is deliberate.

Overlap. The low-latency kernels expose a hook so the receive is not a barrier: attention can run while the MoE tokens are still in flight, and no SM cycles are burned spinning on the network. Without that, two all-to-alls per layer would not be survivable.

In SGLang

python -m sglang.launch_server --model deepseek-ai/DeepSeek-V3 \
    --tp 8 --ep-size 8 \             # experts split across the 8 GPUs
    --enable-deepep-moe \            # the DeepEP kernels
    --deepep-mode auto \             # normal for prefill, low_latency for decode
    --enable-eplb \                  # rebalance experts across ranks
    --ep-num-redundant-experts 32    # replicate the hot ones

The first three lines are the article so far. The last two are the part that surprised me most when I first saw it.

A training-time balancing loss flattens the average. Real traffic is not the average: one minute of requests can all want the same few experts, because they are all about the same topic. So the server measures the per-expert load and periodically moves experts between ranks (that is EPLB, expert-parallel load balancing), and replicates the hottest ones across several ranks so their tokens have more than one place to go. The collapse problem from training comes back as an operational problem, and gets an operational answer.

In vLLM

vllm serve deepseek-ai/DeepSeek-V3 \
    --tensor-parallel-size 8 \
    --enable-expert-parallel \        # EP for the experts instead of TP
    --data-parallel-size 2            # DP attention, EP experts

vLLM reaches the same place with --enable-expert-parallel, using DeepEP or pplx-kernels underneath for the all-to-all. The combination worth remembering is the last line: attention replicated with data parallelism while the experts are sharded with expert parallelism. The reason is blunt - attention has no experts to spread, and the MoE weights do not fit otherwise. Both servers end up at that configuration.

On either one, the number to watch is not average throughput. It is the per-rank load distribution: if one rank consistently holds the busiest experts, every other rank waits for it twice per layer, and no amount of kernel tuning recovers that.

Where this comes back

The routing decision is a discrete choice trained by gradient descent, which is the same difficulty that shows up in reinforcement learning and in every attempt to learn an architecture rather than a weight. And the load-balancing story - flatten the average at training time, then rebalance for real traffic at serving time - is a pattern worth recognising, because the same split between what you can bake in and what you must measure online turns up in caching, in scheduling, and in anything else where the workload is not stationary.
