Day 65 — Embedding 與向量檢索：把文件變成一個方向，再問「誰的方向最近」

程式碼：day 65 on GitHub

100 Days of Python - day 65

Embedding 做的事情是把一份文件變成空間裡的一個方向，而檢索就是問「誰的方向跟這個問題最近」。剩下的全部都是四個決定——要不要正規化、留幾維、每個數字幾個 bit、一份文件幾個向量——今天我把每一個決定的價錢都量出來，而不是照抄預設值。

這張圖看懂，演算法就講完了。每份文件都是從原點出發的一支箭頭，查詢也是一支箭頭，而分數就是兩者夾角的 cosine——把兩支箭頭都縮放成長度 1 之後，那就只是一次內積。doc B 是同一個主題但寫得比較長：箭頭更長、方向幾乎一樣，所以 cosine 會把它擺在該在的位置，而 raw dot product 會把它推到第一名。青色的點是正規化之後箭頭落在哪裡——檢索就是在單位圓上找最近的點，而這篇剩下的篇幅都在講：存這些點、比較這些點，各要付多少錢。

為了量得出來，這個語料的答案是自己種進去的：20,000 份文件、200 個查詢，每個查詢有 10 份已知正確的文件。於是 recall@10 是一個事實，不是感覺。

                                        recall@10
--------------------------------------  ---------
字詞比對（tf-idf cosine）               0.419
我的 embedding（256 維，二十行 numpy）  0.617
答案本人                                0.825

天花板是 0.825，不是 1.0。 連「照著語料被產生出來的方式去排序」都撈不回全部的正解，因為同主題的背景文件本來就會擠進前十。先找出這個上限，才會知道「我們只有 0.62」其實是可能上限的四分之三。

向量是一個方向，所以長度要除掉

文件向量的長度跟「這份文件有幾個字」的相關係數是 0.92。所以 raw dot product 問的不是「是不是在講同一件事」，而是「是不是在講同一件事而且很長」：

計分方式          recall@10  前十名的平均長度
----------------  ---------  ----------------
cosine（正規化）  0.617      250 字
raw dot product   0.092      1,494 字

文件長度的中位數是 199 字。忘了正規化之後索引沒有壞掉——它只是改成照長度排名，而且不會有任何一行 log 告訴你。這就是每個函式庫都有 normalize_embeddings 這個旗標、而每個人都只會忘記一次的原因。

向量是哪來的

X      = log1p(counts) * idf        # 常見字降權
U,S,Vt = svd(X - X.mean(0))         # 找出重要的方向
vec    = X @ Vt[:dims].T            # 投影成 dims 個數字

整個 embedding 就是這樣：字詞比對 0.419，投影之後 0.617。SVD 不是為了壓縮而壓縮——它用「常常一起出現的字」組出方向，這才是「查詢用了不同的字也找得到」的來源。真正的 encoder 只是把 SVD 換成對比學習，產出的東西形狀一模一樣：每份文件一個稠密方向。所以底下所有的結論在真模型上同樣成立。

兩邊不是對稱的

編碼方式                recall@10
----------------------  ---------
兩邊都正規化（cosine）  0.617
query 沒正規化          0.617
document 沒正規化       0.092
query 沒套 idf          0.629
query 用自己算的 idf    0.609
query 的 idf 套了兩次   0.588

第一件事是精確的、而且值得記住：把 query 正規化不可能改變排名，因為只縮放一邊等於把所有分數乘上同一個數。真正重要的是文件那一邊。

後面三列才是有趣的。兩邊用不同方式編碼，答案會上下都跑、最多差 0.041 recall，而且完全沒有錯誤、沒有任何訊號說有東西變了。在這個語料裡傷害很小；它在實務上危險的原因是：instruction-tuned 的 embedding 模型是用 query prefix 跟 document prefix 訓練的，兩邊真的是不同的函式，弄反了就是這種無聲的位移。

要留幾維

維度  每份文件位元組  每百萬份 GB  recall@10
----  --------------  -----------  ---------
256   1,024           0.95         0.617
128   512             0.48         0.678
64    256             0.24         0.710
32    128             0.12         0.730
16    64              0.06         0.732
8     32              0.03         0.672
4     16              0.01         0.420

SVD 的欄位本來就是排好序的，前 d 欄就已經是同一個 embedding 的最佳 d 維版本，所以截斷不需要重新訓練——這正是 Matryoshka 訓練刻意放進神經 encoder 裡的性質。

這裡的峰值在 16 維而不是 256 維：尾巴那些方向是雜訊，而雜訊也有投票權。 真正訓練過的 Matryoshka 模型曲線是「先平再掉」而不是像這裡先升，但實務結論一樣：維度是一個超參數，不是一種美德；看到向量帳單先試截斷。

每個數字要留幾個 bit

表示法                      256 維   recall  16 維  recall
--------------------------  -------  ------  -----  ------
float32                     1,024 B  0.617   64 B   0.732
int8                        256 B    0.618   16 B   0.732
binary（每維 1 bit）        32 B     0.032   2 B    0.429
binary ＋ 前 40 名 rescore  34 B     0.086   2.1 B  0.522

int8 是免費的：整個語料共用一個 scale，內積只多了捨入誤差，記憶體剩四分之一。真正的陷阱是「每個向量用自己的 scale」——那等於每份文件換一個單位，而單位一致正是索引存在的理由。

但每維 1 bit 在這裡不免費，因為這個 embedding 把資訊都塞在前幾維，而符號位元把每一維當成一樣重要。先截斷再量化就可用了；再把 binary 選出的候選名單用完整向量 rescore 一次又救回一截。這就是標準配方的一句話：用便宜的表示法搜尋，用貴的表示法決定。

「一份文件一個向量」是一個賭注

4,000 份文件，每份由五個不同主題的段落組成，答案只在其中一段；而競爭的文件是整份都「有點像」。

表示法                          向量/文件  位元組/文件  recall@10
------------------------------  ---------  -----------  ---------
整份文件一個向量                1          512          0.100
每段一個向量，分數取最好的那段  5          2,560        0.584

5.8 倍的 recall，換 5 倍的向量數。 五個方向的平均指向其中任何一個都不是，所以「一份長文件一個向量」其實是在主張「這份文件只講一件事」。chunking 就是在修這個主張，而 late-interaction 模型（每個 span 一個向量、取最佳匹配）是把同一招推到極限。

第二個分數不會自動讓結果變好

計分方式                        recall@10
------------------------------  ---------
只用向量分數                    0.617
只用詞彙分數（同一份候選名單）  0.250
倒數排名融合 RRF（k=60）        0.457
加權 80% 向量 / 20% 詞彙        0.629

這些查詢要的是「同時命中兩個主題」，而字詞重疊看不出這件事，所以詞彙分數確實是比較弱的那個。RRF 預設兩張名單一樣可信，結果掉了 0.160 recall；把弱的那個壓到兩成權重，也只是回到原點。結論：第二個訊號要在第一個錯的地方才有用，而融合權重是量出來的、不是預設值。

暴力掃描要多少錢

文件數   記憶體   每次查詢 ms  每秒查詢
-------  -------  -----------  --------
10,000   0.01 GB  0.24         4,235
100,000  0.10 GB  9.07         110
400,000  0.38 GB  23.12        43

暴力掃描就是一次矩陣乘法，所以它能撐的時間比大家以為的久——一萬份文件只要 0.24 ms。但它是嚴格線性的，而線性沒有任何向量化手段救得了。這個缺口就是近似最近鄰索引存在的理由：靠的是拒絕去看大部分的資料。

三個不會報錯的陷阱

近重複文件不是分票，是直接佔位。 加三份幾乎一樣的文件，就吃掉那個查詢前十名的三格。去重要在索引之前做，不是在取回之後。

每個向量各自算 scale 的量化。 那等於每份文件一個單位，分數之間不再可比，但每次呼叫還是乖乖回十筆結果。

cosine 相似度不等於相關性。 它量的是「在講同樣的東西」，而這正是為什麼這裡連答案本人都只有 0.825：主題對的文件，跟能回答這個問題的文件，是兩件事。

sentence-transformers 怎麼寫

model = SentenceTransformer("...", truncate_dim=256)          # Matryoshka
doc_vecs = model.encode(docs, normalize_embeddings=True,
                        prompt_name="document", batch_size=256)
q_vecs   = model.encode(queries, normalize_embeddings=True,
                        prompt_name="query")
from sentence_transformers.quantization import quantize_embeddings
small = quantize_embeddings(doc_vecs, precision="int8",
                            calibration_embeddings=doc_vecs[:50_000])

那一頁上的四個參數就是這篇的四節：normalize_embeddings 是長度偏誤、truncate_dim 是維度曲線、calibration_embeddings 是整個語料共用的 scale，而 prompt 名稱就是兩邊的不對稱。

向量資料庫怎麼寫

index = faiss.IndexFlatIP(dims)        # 就是暴力掃描
faiss.normalize_L2(doc_vecs)           # ...所以內積＝cosine
index.add(doc_vecs)
scores, ids = index.search(q_vecs, 10)

每一個託管的向量資料庫都是這個，加上三個你現在已經有數字的決定：存幾維、每個數字幾個 bit、一份文件一個向量夠不夠。唯一這一天沒有自己做的，是「怎麼避開線性掃描」的索引結構。

我自己的收穫

今天有兩個結果出乎我意料。把 256 維截到 16 維不只是比較便宜，而是比較好——因為 embedding 的尾巴是雜訊，而雜訊照樣有投票權。還有，用最標準的 RRF 把第二個比較弱的分數融進來，掉的 recall 比什麼都不調還多。

串起這一切的是同一件事：上面每一種失敗都照樣回十筆結果、照樣不寫任何 log。我之所以看得見它們，只是因為有一個「答案種進去」的語料——而那是任何檢索專案裡最便宜的東西。先把答案本做出來，再來吵模型。
