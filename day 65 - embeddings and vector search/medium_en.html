Embeddings and vector search: a document becomes a direction, and retrieval asks whose is closest

Code: day 65 on GitHub

100 Days of Python - day 65

An embedding turns a document into a direction in space, and retrieval turns a question into "whose direction is closest". Everything after that is four decisions - normalise or not, how many dimensions, how few bits, how many vectors per document - and today I measured the price of each one instead of quoting defaults.

Read that picture and the algorithm is finished. Every document is an arrow from the origin; the query is an arrow too; the score is the cosine of the angle between them, which is just the dot product once both arrows have been scaled to length one. Doc B is the same subject written at greater length - a longer arrow pointing almost the same way

  • so cosine leaves it where it belongs while a raw dot product promotes it to first place. The cyan dots are where the arrows land after normalising: retrieval is a nearest-neighbour search on the unit circle, and the rest of this article is about what it costs to store and compare those points.

To make measurement possible, the corpus has its answers planted in it: 20,000 documents, 200 queries, and 10 known-correct documents for every query. That turns recall@10 into a fact rather than a judgement.

                                                recall@10
----------------------------------------------  ---------
term matching (tf-idf cosine)                   0.419
my embedding (256 dims, twenty lines of numpy)  0.617
the answer key itself                           0.825

The ceiling is 0.825, not 1.0. Even ranking by the exact recipe the corpus was generated from cannot recover every planted answer, because background documents about the same topic crowd into the top ten. Finding that ceiling first is what turns "we score 0.62" from a disappointment into three quarters of what is possible.

A vector is a direction, so the length has to go

The length of a document vector correlates 0.92 with how many words the document has. So a raw dot product does not ask "is this about the same thing", it asks "is this about the same thing and is it long":

scoring              recall@10  average length of the top 10
-------------------  ---------  ----------------------------
cosine (normalised)  0.617      250 words
raw dot product      0.092      1,494 words

The median document is 199 words. Forget to normalise and the index is still an index - it just ranks by length now, and nothing in any log says so. That is the whole reason every library has a normalize_embeddings flag, and why people forget it exactly once.

Where the vectors come from

X      = log1p(counts) * idf        # down-weight common words
U,S,Vt = svd(X - X.mean(0))         # the directions that matter
vec    = X @ Vt[:dims].T            # project into `dims` numbers

That is the entire embedding: 0.419 for term matching, 0.617 once projected. The SVD is not compression for its own sake - it builds directions out of words that keep appearing together, which is what lets a query match a document that used different words for the same thing. A trained encoder swaps the SVD for a contrastive objective; the output has exactly the same shape, one dense direction per document, which is why everything below carries over to a real model.

The two sides are not symmetric

encoding                               recall@10
-------------------------------------  ---------
both sides normalised (cosine)         0.617
query left unnormalised                0.617
documents left unnormalised            0.092
query encoded without the idf weights  0.629
query encoded with an idf of its own   0.609
query with the idf applied twice       0.588

The first fact is exact and worth keeping: normalising the query cannot change the ranking, because scaling one side multiplies every score by the same number. Only the document side matters.

The last three are the interesting ones. Encoding the query differently from the documents moves the answer by up to 0.041 recall in both directions, with no error anywhere and no signal that anything changed. In this corpus the damage is small; what makes it dangerous in production is that instruction-tuned embedding models are trained with a query prefix and a document prefix, so the two encoders really are different functions - and swapping them is exactly this kind of silent move.

How many dimensions

dims  bytes/doc  GB per million  recall@10
----  ---------  --------------  ---------
256   1,024      0.95            0.617
128   512        0.48            0.678
64    256        0.24            0.710
32    128        0.12            0.730
16    64         0.06            0.732
8     32         0.03            0.672
4     16         0.01            0.420

The columns of an SVD come out ordered, so the first d of them are already the best d-dimensional version of the same embedding. Truncation needs no retraining - which is the property Matryoshka training puts into a neural encoder on purpose.

The peak here is at 16 dimensions rather than 256: the tail directions are noise, and noise still gets a vote. A trained Matryoshka model gives a curve that is flat and then falls instead of rising like this one, but the practical conclusion is identical. The dimension count is a hyperparameter, not a virtue, and truncation is the first thing to try when the vector bill arrives.

How few bits per number

representation               256 dims  recall  16 dims  recall
---------------------------  --------  ------  -------  ------
float32                      1,024 B   0.617   64 B     0.732
int8                         256 B     0.618   16 B     0.732
binary, 1 bit per dimension  32 B      0.032   2 B      0.429
binary + rescore top 40      34 B      0.086   2.1 B    0.522

int8 is free: one scale for the whole corpus leaves the dot product intact up to rounding, at a quarter of the memory. The trap is a per-vector scale - a different unit for every document is exactly the comparison the index exists to make.

One bit per dimension is not free here, because this embedding keeps its information in the first few dimensions and a sign bit treats every dimension as equally important. Truncate first and it becomes usable; rescore the binary shortlist with the full vectors and it recovers further. Which is the standard recipe in one line: search in the cheap representation, decide in the dear one.

One vector per document is a bet about the document

4,000 documents, each five sections about different things, with the answer in exactly one section; the competing documents are vaguely on-topic all the way through.

representation                                vectors/doc  bytes/doc  recall@10
--------------------------------------------  -----------  ---------  ---------
one vector for the whole document             1            512        0.100
one vector per section, score = best section  5            2,560      0.584

5.8x the recall for 5x the vectors. The average of five directions points at none of them, so a single vector for a long mixed document is a claim that the document is about one thing. Chunking is how everyone repairs that claim, and late-interaction models - a vector per span, scored by the best match - are the same idea taken to its limit.

A second score is not automatically better

scoring                              recall@10
-----------------------------------  ---------
vector score only                    0.617
lexical score only (same shortlist)  0.250
reciprocal rank fusion (k=60)        0.457
weighted 80% vector / 20% lexical    0.629

These queries ask for two topics at once and word overlap cannot see that, so the lexical score is genuinely the weaker one. Reciprocal rank fusion assumes both lists deserve equal trust, and costs 0.160 recall; weighting the weaker score down to 20% merely gets back to where we started. A second signal helps where the first is wrong, and the fusion weight is a measurement, not a default.

What brute force costs

documents  memory   ms per query  queries/s
---------  -------  ------------  ---------
10,000     0.01 GB  0.24          4,235
100,000    0.10 GB  9.07          110
400,000    0.38 GB  23.12         43

A full scan is one matrix multiply, which makes it the right answer for longer than people expect - a quarter of a millisecond at ten thousand documents. It is also strictly linear, and no amount of vectorisation fixes linear. That gap is what approximate nearest neighbour indexes exist to close, by refusing to look at most of the data.

Three traps that never raise an error

Near-duplicates take the seats. Three near-identical copies of one answer cost that query 3 of its 10 slots. They do not split the vote; deduplicate before indexing, not after retrieving.

Per-vector quantization scales. A scale computed from each vector on its own is a different unit per document, so the scores stop being comparable while every call still dutifully returns ten results.

Cosine similarity is not relevance. It measures "about the same things", which is exactly why the answer key tops out at 0.825 here: documents about the right topic are not the same as documents that answer the question.

In sentence-transformers

model = SentenceTransformer("...", truncate_dim=256)          # Matryoshka
doc_vecs = model.encode(docs, normalize_embeddings=True,
                        prompt_name="document", batch_size=256)
q_vecs   = model.encode(queries, normalize_embeddings=True,
                        prompt_name="query")
from sentence_transformers.quantization import quantize_embeddings
small = quantize_embeddings(doc_vecs, precision="int8",
                            calibration_embeddings=doc_vecs[:50_000])

Four arguments on that page are four sections of this article: normalize_embeddings is the length bias, truncate_dim is the dimension curve, calibration_embeddings is the corpus-wide scale, and the prompt names are the asymmetry.

In a vector store

index = faiss.IndexFlatIP(dims)        # exactly the brute-force scan
faiss.normalize_L2(doc_vecs)           # ...so inner product = cosine
index.add(doc_vecs)
scores, ids = index.search(q_vecs, 10)

Every managed vector database is this plus three decisions I now have numbers for: how many dimensions to store, how many bits per number, and whether one vector per document is enough. The index type - the part that avoids the linear scan - is the only piece this day did not build.

What I take away

Two of today's results surprised me. Truncating 256 dimensions to 16 made retrieval better, not merely cheaper, because the tail of the embedding is noise that still gets a vote. And fusing in a second, weaker score with the standard reciprocal-rank recipe cost more recall than forgetting to tune anything at all.

The thread connecting all of it: every one of these failures returns ten results and logs nothing. The only reason I could see them is the corpus with planted answers - and that is the cheapest thing to build in any retrieval project. Make the answer key first, then argue about models.
