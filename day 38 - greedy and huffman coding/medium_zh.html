100 Days of Python - day 38

八個人要搶同一間會議室。照結束時間排序，排得進五場；照誰先來排序，只排得進三場；照會議長短排序，排得進四場。三份時間表都完全合法——沒有人被重複預約，程式不會丟例外，測試也不會紅。只是其中兩份比較差，而程式完全沒有辦法告訴你這件事。

這就是今天的全部主題。貪心演算法就是「當下看起來最好的就選，選了不反悔」，所以昨天 Held-Karp 要三十行的東西，今天三行就寫完。難的從來不是寫出來，而是貪心選錯 key 不會 crash——它會交回一個合法但悄悄比較差的答案，而只要你手邊沒有東西可以對照，你永遠不會發現。

Day 33 到 Day 37 花了五天建表，正是因為必須把未來一起算進去。今天剛好相反：有些問題單一個局部規則就已經是最佳解。下面兩個例子都是經典——一個是貪心對了、而兩個很誘人的 key 錯了；另一個是貪心可以被證明為最佳，但只要動一行資料結構，輸出就會安靜地大 55%。

八個請求，一間會議室

區間是半開區間：11:00 結束的會議和 11:00 開始的會議不算衝突。照結束時間排序，掃過一次，只要這場會議的開始時間不早於上一場已接受的結束時間就收下。

def select_by_end(intervals):
    out, last_end = [], float('-inf')
    for s, e in sorted(intervals, key=lambda iv: iv[1]):
        if s >= last_end:            # no clash with what we already took
            out.append((s, e))
            last_end = e
    return out

排進五場：B、C、D、F、G。結束時間之所以是「對的」key 而不只是「其中一個」key，理由是：對後面所有還沒排的會議來說，唯一會限制它們的東西就是「會議室幾點會空出來」。挑最早結束的那一場，等於讓會議室在最早可能的時刻空出來，所以它不可能擋掉任何一個別種選法保得住的機會。

兩個會輸的 key

「誰先來誰先用」是人類實際在管會議室的方式，「先把短的塞進去」是你在整理襪子抽屜的方式。兩個都講得出道理，兩個都只要同樣那四行，兩個都輸：

排序 key               排進幾場  選到誰
---------------------  --------  ---------
照結束時間             5         B C D F G
照開始時間             3         A E G
照會議長度             4         B C E G
暴力枚舉 2^8 個子集合  5         B C D F G

照開始時間排，會議室第一個給了 A——一場兩小時的 design review，把 09:15 到 11:15 整段卡死，底下三場短會一起陪葬。照長度排，先抓走兩場十五分鐘的會議，因為它們看起來很便宜，結果 D 就塞不下了。

重點不是這個排名，而是三份輸出都是不衝突的合法時間表，拿去給人 review 也會過。真實系統裡不會有一份暴力解擺在貪心旁邊，所以憑直覺挑的 key 一旦錯了，就會一直錯下去。

交換論證：把證明跑成實驗

「貪心是最佳解」的證明幾乎都是同一個形狀。主張：最早結束的那個區間，一定屬於某一組最佳解。隨便拿一組不含它的最佳解，把裡面第一場會議換成最早結束的那一場——這個交換不可能造成衝突，因為替換進去的那場結束得不會更晚。於是存在一組同樣大小、而且含有貪心選擇的最佳解，代表這個貪心選擇不花任何代價，接著同一套論證再套用到剩下的部分。

這件事不必用信的。把第一個貪心選擇強制鎖住，剩下的用暴力枚舉，看看答案有沒有變差：

first = min(intervals, key=lambda iv: iv[1])
unrestricted = len(select_bruteforce(intervals))
rest = [iv for iv in intervals if compatible(iv, first) and iv != first]
forced = 1 + len(select_bruteforce(rest))

兩邊都是 5。這是個很便宜的習慣，任何你沒把握的貪心都值得跑一次：跑得出來的證明勝過半記得的證明。

題目稍微換一下，貪心就死了

現在每場會議都值錢，目標變成「總價值最高」而不是「排進最多場」。同一個照結束時間的貪心照跑，把撿到的價值加起來：12。最好的其實是 17，選 A、F、H——三場，不是五場。

換任何 key 都救不回來，因為「現在收下這場會議值不值得」取決於為了它放棄了什麼。這正是表格存在的理由。加權區間排程就是 Day 33 的 DP 配上 Day 23 的 bisect，替每個區間找出「最後一個在它開始前就結束」的區間：

iv = sorted(intervals, key=lambda t: t[1])
ends = [e for _, e in iv]
best = [0] * (len(iv) + 1)
for i, (s, e) in enumerate(iv):
    j = bisect_right(ends, s, 0, i)      # last compatible interval, 0 if none
    best[i + 1] = max(best[i], best[j] + value[(s, e)])

和選錯 key 是同一種失敗模式，只是再往前走一步：現在貪心連工具都用錯了，它還是照樣交回一份真的可以用的時間表，一聲不吭。

Huffman 編碼：可以被證明的貪心

定長編碼花在最罕見符號上的位元數，和花在最常見符號上的一樣多。Huffman 的觀察是：最罕見的那兩個符號，永遠可以被擺成編碼樹最深一層的兄弟節點——把最長的編碼給最少用的符號，不會損失任何東西。這句話直接變成一個完全不需要看未來的演算法：從 min-heap 取出最輕的兩棵子樹、合併、把合併後的節點推回去，重複到只剩一棵。左邊是 0，右邊是 1。

while len(heap) > 1:
    w1, _, n1 = heapq.heappop(heap)
    w2, _, n2 = heapq.heappop(heap)
    heapq.heappush(heap, (w1 + w2, tie, (n1, n2)))   # back into the queue
    tie += 1

拿 53 個字元的句子 'greedy algorithms are easy to write and hard to prove' 來試：裡面有 18 種不同字元，定長編碼每個要 5 bits，共 265 bits。Huffman 壓到 204 bits，小了 23%——出現九次的空白字元拿到 3 bits 的編碼，而整棵樹最長的編碼是 6 bits，落在只出現一次的字母上。

上面那段有兩個細節是真的在撐場面。tie 這個計數器是為了在兩個權重相同時讓順序固定；少了它，Python 會往下去比較節點本身的內容，輸出就會取決於「tuple 巢狀 tuple 剛好怎麼排」。而 heappush 不是形式——合併後的節點比它的兩個小孩都重，必須以新的權重重新排進佇列裡。這就是這裡非得用 heap、而不能用排好序的 list 的唯一理由。

解碼不需要任何分隔符號，這是 prefix code 買到的東西：沒有任何一個編碼是另一個的前綴，所以解碼器一個 bit 一個 bit 讀，讀到的東西一變成某個編碼就馬上吐出那個符號。

改一行，多付 55%

把符號照頻率排序一次，然後從左往右合併，合併後的節點再也不放回佇列：

items = sorted(freqs.items(), key=lambda kv: (kv[1], kv[0]))
node, weight = items[0][0], items[0][1]
for sym, w in items[1:]:
    node, weight = ((node, sym), weight + w)

每次合併一樣是把兩棵子樹接起來，所以結果依然是合法的 prefix code，依然能把原文一字不差地解回來。掉的是那個「重新排序」。合併後的節點權重已經超過旁邊那些符號，本來應該往佇列後面沉下去；這裡它永遠不會沉，於是永遠是最輕的兩個之一，整棵樹垮成一條掛在單邊的梯子。最長的編碼從 6 bits 變成 17 bits。

編碼方式                bits
----------------------  ----
Huffman（用 heap）      204
單純 5-bit 定長編碼     265
排序一次、從左往右合併  316

兩份編碼都是 prefix-free，都能完整還原原文，Kraft sum（把每個編碼的 2 的負長度次方加總）都剛好是 1.000——連「編碼樹有沒有長出一條通往空處的分枝」這個結構檢查都過得去。壞掉的那份只是比正確的那份大 55%，而且比完全不壓縮還糟。

還有這個陷阱最老的版本：用面額 1、3、4 的硬幣付 6 塊。貪心先拿最大的，4 + 1 + 1，三枚；其實兩枚 3 就夠了。這個陷阱之所以活得這麼久，是因為拿真的在錢包裡的面額——1、5、10、25——同一套貪心永遠是最佳解。習慣是在會原諒你的面額上養成的，然後被帶到不原諒你的面額上。

LeetCode 435 - Non-overlapping Intervals（無重疊區間）

題目在問什麼。 給一堆區間，移除盡可能少的區間，讓剩下的彼此都不重疊，回傳移除了幾個。

輸入與輸出。 一個 [start, end] 的清單。回傳一個整數：最少要刪掉幾個。

範例。 [[1,2], [2,3], [3,4], [1,3]] 回傳 1。刪掉 [1,3] 之後剩下 [1,2]、[2,3]、[3,4]，它們只在端點相接，不算重疊。反過來只刪其他三個裡的任何一個，[1,3] 都還是會和兩個倖存者打架，所以刪一個既是必要也是足夠。

限制條件。 最多 100,000 個區間，座標落在 32 位元有號整數範圍內。區間數量決定了演算法：任何需要兩兩比較的寫法都是 10^10 次運算，一定 TLE，所以只剩「排序 + 線性掃一次」這個形狀付得起。另一個限制藏在敘述的用字裡——只在端點相接的區間不算重疊，所以判斷式是 s >= last_end 而不是 s > last_end。

「保留最多」和「丟掉最少」是同一個問題，所以會議室那個貪心原封不動就能解：

class Solution:
    def eraseOverlapIntervals(self, intervals: List[List[int]]) -> int:
        intervals.sort(key=lambda iv: iv[1])        # earliest finishing first
        kept, last_end = 0, float('-inf')
        for s, e in intervals:
            if s >= last_end:                       # fits after what we kept
                kept += 1
                last_end = e
        return len(intervals) - kept

leetcode.com/problems/non-overlapping-intervals

面試時真正會被追問的是它的兄弟題。LeetCode 452, Minimum Number of Arrows to Burst Balloons（用最少數量的箭引爆氣球） 是同一個排序、只差一個字元。氣球是閉區間，所以射在 x = 2 的一箭會同時戳破 [1,2] 和 [2,3]，只有當下一顆氣球的起點嚴格大於上一箭的位置時才需要新的一箭：要寫 if s > last，不是 >=。把 435 寫對之後原封不動搬去解 452，是最常見的翻車方式之一。

這件事之後會用在哪

Huffman 是每個語言模型前面那顆 tokenizer 的直系祖先。BPE（byte-pair encoding）跑的是同一個形狀的反面——不是合併最罕見的兩個符號好給它們長編碼，而是一次又一次合併出現最頻繁的相鄰字元對、給它一個短的代號，掉出來的那張詞彙表就是把文字變成 token ID 的東西。那個由頻率驅動的合併迴圈，以及「優先佇列到底要依什麼重新排序」這個問題，在那裡會原封不動地再出現一次。

而更大的那個教訓比這兩個例子走得更遠。今天每一個失敗——選錯 key、加權版本、沒有重新排序的 heap、那三種硬幣——交出來的都是有效的答案。貪心演算法不會大聲地壞掉，它是以百分比的方式壞掉。如果你要把一個貪心送上線，就把暴力解一起送上去，然後在小輸入上斷言兩邊相等：那一行 assert 是你和那安靜的 55% 之間唯一的東西。
