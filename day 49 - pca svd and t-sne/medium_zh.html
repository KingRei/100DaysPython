Day 49 — PCA、SVD 與 t-SNE：把幾百欄資料壓成兩欄，畫成一張看得懂的圖

程式碼：day 49 on GitHub

100 Days of Python - day 49

我拿 180 個十維的高斯雜訊點去跑 t-SNE。它畫出了三群——用 k-means 把圖切成三塊，三塊分得乾乾淨淨。我換一個隨機種子，它畫出另外三群。silhouette 這個指標在「分群是隨便切的」時會接近 0，而它給原始資料 0.0872，給四張 t-SNE 的圖 0.3689 到 0.3972——是資料裡實際含量的 4.2 到 4.6 倍。

這就是今天的形狀。降維把 d 欄壓成兩欄，而被壓掉的那些不會留下任何痕跡。出來的是一張圖，而圖極容易被過度解讀。

PCA   回答的是：哪些方向的變異最大？
t-SNE 回答的是：誰跟誰是鄰居？

這兩個都不是「哪些方向有用」，也不是「這兩群離多遠」，而那正是大家從圖上讀走的兩件事。下面每一節都在量「被優化的東西」和「被讀走的東西」之間的距離。

PCA 就是對置中後的資料做 SVD

Xc = X - X.mean(axis=0)
U, s, Vt = np.linalg.svd(Xc, full_matrices=False)
components = Vt                       # 每一列是一個方向
explained_variance = s ** 2 / (n - 1)

課本的走法是建共變異數矩陣 XᵀX / (n − 1) 再做特徵分解。這裡兩者吻合到 4.4e-15，而再過幾節它們會完全分家。在那之前有兩件事要先講。

np.linalg.eigh 回傳的特徵值是由小到大的，所以共變異數那條路必須自己反轉一次。忘了這一步，你會得到一個看起來完全正常、卻指向最不重要方向的答案。

另外，特徵值不重複時，特徵向量只定義到正負號：v 和 −v 張出同一條線，兩個都對。（兩個特徵值相等時更糟：它們張出的那個平面裡任何一個旋轉都同樣合法，不只是鏡像而已。）兩個套件、同一個套件的兩個版本，或同一份程式在不同機器上，都可能給你一張翻過來的圖，而且沒有任何東西會提醒你。程式裡比較主成分時要連正負號一起放掉，比 |u · v|；而要給人看的東西則要反過來把慣例釘死，例如畫圖前強制讓每個主成分絕對值最大的那一項為正。

Silent failure #1：忘了減平均

上面第一行就是關鍵那一行。少了它，「變異」是相對於原點量的，於是第一主成分指向的是資料在哪裡，而不是它長什麼形狀。

300 個點，中心在 [7.85, 4.98]，自己的擴散是 2.2：

        PC1                 解釋變異比
------  ------------------  ----------------
有置中  [-0.9521, -0.3059]  [0.9619, 0.0381]
沒置中  [-0.8508, -0.5254]  [0.9950, 0.0050]

沒置中的 PC1 跟平均的方向只差 0.701 度，跟真正的 PC1 差 13.885 度。

危險的是第二欄。壞掉的版本回報一個主成分解釋了 0.9950 的變異，而正確的是 0.9619。它看起來更好，因為它現在量的那個偏移量，比它本來應該量的擴散還大——分母跟著分子一起被灌水了。

大家真的會拿去報告的那個數字，在犯這個錯之後會往上跑。但不是每個數字都被騙，這才是有用的地方：把這 300 個點從一個主成分重建回來，置中版的誤差是 0.093544，沒置中的是 0.230609，重建誤差差了 2.5 倍，它抓得到。它只是不會被放進投影片裡的那個數字。

Silent failure #2：單位決定了軸

Day 47 和 Day 48 都撞到過這件事。PCA 是它最明顯的地方，因為答案本身就是一個方向。兩欄互相獨立的雜訊——prompt_tokens 在幾百的量級，cache 命中率在 [0, 1]：

原始單位 : PC1 [1.00000000 0.00003620]   解釋變異比 0.99999992
標準化後 : PC1 [0.70710678 0.70710678]   解釋變異比 0.56328964

在原始單位下，PC1 跟 token 那根軸只差 0.0021 度，而 PCA 回報「一個主成分解釋了兩欄獨立雜訊的 99.999992% 變異」。這個數字是對的，而且它是關於單位的事實，不是關於資料的。標準化讓兩欄一樣大聲，那是另一個同樣武斷的選擇，不是中立的——但至少那是你做的選擇。

Silent failure #3：解釋變異不等於有用

400 個點、兩個類別。兩類沿著某一個方向分開；另一個方向帶著大得多的變異，而且一點資訊都沒有；整個東西被旋轉過，所以沒有一個方向是座標軸。

主成分  解釋的變異  最好的一刀
------  ----------  ----------
PC1     98.33%      0.5450
PC2     1.67%       1.0000

PC1 握著 98.33% 的變異，而用它做最好的一刀只能分對 0.5450，也就是擲銅板。PC2 只有 1.67%，卻分得完美。兩者的變異比是 59.0 比 1，而排序對「唯一有人會問的那個問題」來說剛好是反的。

注意 PCA 做對了什麼、又做錯了什麼。它找對了那一對方向——旋轉是對的，訊號乾乾淨淨地落在它其中一根軸上。它只是用錯的鍵去排序。「保留 95% 的變異」在這裡會把 PC2 丟掉，而 PCA 沒辦法做得更好：它是非監督的，從頭到尾沒看過標籤。

為什麼用 SVD 而不是共變異數矩陣

兩條路在數學上一樣。做出 XᵀX 會把條件數平方，而 float64 只有大約 16 位數可以花。

奇異值正比於 1、eps、eps/2，放在一組隨機的正交基底裡（基底另外乘了 √(n−1)，所以下表最小奇異值在 eps=1e-4 時讀到的是 7.04e-04 而不是 5e-05）：

eps    cond(X)  cond(cov)  最小奇異值（SVD）  （eigh）    相對誤差
-----  -------  ---------  -----------------  ----------  ---------
1e-04  2.0e+04  4.0e+08    7.0425e-04         7.0425e-04  4.582e-08
1e-06  2.0e+06  4.0e+12    7.0425e-06         7.0416e-06  1.197e-04
1e-08  2.0e+08  4.2e+16    7.0425e-08         0.0000e+00  1.000e+00
1e-09  2.0e+09  6.5e+17    7.0425e-09         0.0000e+00  1.000e+00

到 eps = 1e-8，共變異數那條路對一個真值是 7.04e-08 的奇異值回傳剛好 0。一個真的有變異的方向被四捨五入掉了，而且完全沒有警告。

cond(cov) 那一欄是直接量共變異數矩陣本身算出來的，不是把 cond(X) 自己平方寫上去的，所以最後一列讀到的是 6.5e+17 而不是預測的 4.0e+18：到那個地步，矩陣已經爛到連它自己的 condition number 都算不準了，量測本身成了它要量的那件事的受害者。

同一個地方還有第二個症狀：eigh 對一個共變異數矩陣回傳 -1.435e-16，也就是一個負的變異數。對它開根號會得到 nan，所以從特徵值算標準差的程式必須夾在 0——而夾住正好把問題藏起來。

截斷的 SVD，以及「解釋變異」到底是什麼意思

Eckart–Young：把 SVD 在第 k 個奇異值截斷，就是 Frobenius 範數下最好的 rank-k 近似，而誤差剛好等於「被丟掉的奇異值平方和」開根號。

k   Frobenius 誤差  sqrt(丟掉的平方和)  保住的範數平方比例
--  --------------  ------------------  ------------------
1   425.474593      425.474593          0.1185
5   338.494196      338.494196          0.4421
10  248.372324      248.372324          0.6996
20  122.977998      122.977998          0.9264
40  0.000000        0.000000            1.0000

最後一欄是「保住了多少 Frobenius 範數平方」，而在置中過的資料上，那就正好是 PCA 的 explained variance ratio——同一個比例，只是停在統計之前一步。這裡的 A 沒有置中，所以兩者會差一點點：k = 10 時原始的是 0.6996，置中版是 0.6991。

這個等式就是「解釋變異」的全部內容，也正是這個詞那麼容易被誤用的原因。「保留 95% 的變異」說的是「重建誤差的平方只剩 5%」，它沒有說「我關心的那個東西還留著 95%」——上一節就是這兩件事分道揚鑣的樣子。

t-SNE：留住鄰居，其他全部放掉

P：在原本的空間裡，用高斯把距離變成「鄰居機率」。每一列有自己的寬度，用二分搜尋調到那一列的 perplexity 落在你要的值上。perplexity 是 2 的熵次方，也就是「這個點實際上有幾個鄰居」。在 180 個點、perplexity 30 時，sigma 在各列之間從 0.7827 跑到 1.7242。二分搜尋的容忍值是 1e-5，所以它真正達到的 perplexity 落在 29.9997 到 30.0003 之間——夠近，但不是剛好 30。

Q：在二維的圖上改用自由度 1 的 Student-t。

在距離 3 的地方，Student-t 還給 0.100，而高斯只給 0.01111——小了九倍。那條重尾就是整個招式。在高維度裡幾乎每一對點都是「中等距離」，少了重尾它們會全部擠到紙的中間。

然後用梯度下降最小化 KL(P ‖ Q)：

num  = 1 / (1 + pairwise_sq_dists(Y))        # Student-t kernel
np.fill_diagonal(num, 0.0)                   # 一個點不是自己的鄰居
Q    = num / num.sum()
W    = (P - Q) * num
grad = 4 * (Y * W.sum(1)[:, None] - W @ Y)

600 次迭代把 KL 從 1.6949 降到 0.2499，而每個點原本最近的 10 個鄰居有 0.6206 在圖上還是鄰居。那個 recall 數字是這張圖唯一有資格宣稱的東西。

被優化的東西就是那個嵌入本身。沒有任何函數被配出來，所以 t-SNE 沒有 transform()——新的點只能整份重跑，而那是每一輪 n² 對。

抓到它的測試只要多跑一次：

真的結構換一個隨機種子還在。假的不會：同一份雜訊給出三張彼此幾乎不同意的圖。

Silent failure #5：圖上的大小和距離都沒有意義

三群，中間那群比其他兩群寬十倍：

資料裡的寬度 : [1.025, 10.818, 1.182]   最寬 / 最窄 = 10.56
圖上的寬度   : [2.159,  2.421, 2.155]   最寬 / 最窄 =  1.12

寬十倍的那一群在圖上跟其他兩群一樣大，因為每一列都自己挑了一個 sigma 去湊同一個 perplexity。那個「每列自己的寬度」正是 t-SNE 應付不同密度區域的方法，也正是為什麼輸出沒辦法報告密度。

而群跟群之間的距離，則是整個不見了：

資料裡的距離比  圖上的同一個比
--------------  --------------
2.02            1.04
4.03            1.04
8.05            1.04
26.82           1.02

有一群比另一群遠了將近 27 倍，而圖把它們放在一樣遠的地方。這裡沒有 bug：KL(P ‖ Q) 是在一對一對的點上加總，而整個式子裡沒有任何一項叫做「這群多寬」或「這兩群隔多遠」，所以優化從頭到尾就沒有在試著把它們弄對。

Silent failure #6：損失變好，圖變差

同樣三群，只動一個旋鈕：

perplexity  最後的 KL  留住的鄰居
----------  ---------  ----------
2           0.6008     0.5283
5           0.5849     0.5822
30          0.2499     0.6206
80          0.0010     0.5028
150         0.0025     0.3656

表裡最低的 KL 是 0.0010，出現在 perplexity 80。那看起來是完美的配合，而它只留住 0.5028 的鄰居，相對於 perplexity 30 的 0.6206。

坑在於 P 對每一個 perplexity 都是重新建的，所以這張表的每一列是一個不同的目標函數。KL 的值在不同 perplexity 之間不可比較，而優化器會印出來的那唯一一個數字，剛好對「選那個最關鍵的旋鈕」毫無用處。

LeetCode 719 - Find K-th Smallest Pair Distance（找出第 K 小的數對距離）

題意。 給一個整數陣列 nums 和一個整數 k，回傳所有數對之中第 k 小的距離，其中一對 (a, b) 的距離是 |a − b|。每一對位置只算一次，包含值相同的那些對。

輸入輸出。 nums 是整數串列，k 是整數且 1 ≤ k ≤ n(n−1)/2。回傳一個整數。

範例。 nums = [1, 3, 1]、k = 1 時，三對的距離是 2、0、2，排序後是 0、2、2，所以第 1 小是 0。

限制。 2 ≤ n ≤ 10⁴，0 ≤ nums[i] ≤ 10⁶。n 的上限就是整題的全部：它代表最多有 49,995,000 對，光是把它們生出來就已經做不到，更不用說排序。而值的上限讓「答案」本身可以被二分——它落在 [0, 10⁶]，一個你可以一直對半砍的範圍。

關鍵是去二分答案而不是資料。count(m)（距離不超過 m 的數對有幾組）對 m 單調遞增，所以最小的、滿足 count(m) ≥ k 的那個 m 就是第 k 小的距離。而因為陣列排好序，count 本身是一個滑動視窗：j 只會往右走，所以它是 O(n) 而不是 O(n²)。

class Solution:
    def smallestDistancePair(self, nums: list[int], k: int) -> int:
        nums.sort()
        n = len(nums)

        def count(m: int) -> int:
            total = j = 0
            for i in range(n):
                while nums[i] - nums[j] > m:
                    j += 1
                total += i - j          # [j, i) 裡的每個 index 都和 i 配成一對
            return total

        lo, hi = 0, nums[-1] - nums[0]
        while lo < hi:
            mid = (lo + hi) // 2
            if count(mid) >= k:
                hi = mid
            else:
                lo = mid + 1
        return lo

lo 一定要從 0 開始，不是 1。「距離至少是 1」對每一對不同的值都成立，而只要陣列裡有重複值就不成立。從 1 開始在 5,000 筆隨機測資裡有 316 筆跟正解不同——6.3%——而第一筆是 nums = [0, 0, 0, 1, 4, 5, 6, 8], k = 2，回傳 1 而不是 0。幾個手寫的、值都相異的測資永遠看不到它。

LeetCode 2352 - Equal Row and Column Pairs（相等的列與行對）

題意。 給一個 n × n 的整數矩陣 grid，回傳有幾組 (r, c) 讓第 r 列和第 c 行相等——也就是以同樣的順序含有同樣的元素。

輸入輸出。 grid 是一個方形的二維整數串列。回傳一個整數；同一列可以對上好幾行，每一組都分開算。

範例。 grid = [[3,2,1],[1,7,6],[2,7,7]] 的答案是 1：第 2 列是 (2, 7, 7)，第 1 行也是 (2, 7, 7)。[[3,1,2,2],[1,4,4,5],[2,4,2,2],[2,4,2,2]] 的答案是 3。

限制。 1 ≤ n ≤ 200，1 ≤ grid[i][j] ≤ 10⁵。規模上限代表天真的 O(n³) 三重迴圈也能輕鬆通過，所以這題考的是「寫清楚」而不是「跑得快」。真正會咬人的是值的上限：值到 10⁵ 代表它們是多位數，而那正是下面那個捷徑會壞掉的原因。

一列和一行相等的意思是「同一串數字」，所以 key 必須是那串數字。tuple 保留了元素的邊界，把數字黏成一串字串則把邊界丟掉了。

from collections import Counter

class Solution:
    def equalPairs(self, grid: list[list[int]]) -> int:
        rows = Counter(tuple(r) for r in grid)
        return sum(rows[col] for col in zip(*grid))

改用 ''.join(map(str, row)) 當 key，(1, 2, 34) 和 (1, 23, 4) 就都變成 "1234"。在 [[1, 2, 34], [23, 5, 6], [4, 7, 8]] 上，正確答案是 0，而字串版回傳 1。

這個 bug 有多大？隨機測試又有多大機會找到它？在值落在 1..99 的 9,801 個二元序列裡，只存在 9,072 個不同的字串 key。有 729 個 key 被共用，而且每一個都剛好被兩個序列共用，所以 9,801 個序列裡有 1,458 個（14.9%）沒有唯一的 key。而兩個獨立抽出來、值到 100,000 的三元序列，在 200,000 次抽樣裡撞到 0 次。輸入空間的一成五，而隨機測試幾乎踩不到：這就是會上線的 bug 的形狀。

為什麼這件事重要

這兩個東西到處都是，而且都被用同一種隨便的方式讀。PCA 是一半的 pipeline 的預設前處理，而「我們保留了 95% 的變異」常常被說得像是一句關於資訊量的話；第三節就是訊號小、雜訊大的時候，這句話的代價。白化、以 PCA 為基礎的異常偵測、以及每一張「解釋變異」的圖，繼承的都是同一個落差。

t-SNE 和 UMAP 則是大家看高維資料的方式——embedding、單細胞量測、activation——而大家從那些圖上讀走的兩件事，「這群多大」和「這兩群離多遠」，剛好就是目標函數裡完全沒有對應項的那兩個量。

習慣很小。分解之前先置中，而且確認你的套件真的做了。當一個方向、一欄資料或一張圖讓你意外的時候，先看單位，再去找故事。而當一張圖顯示出群的時候，在相信它們之前先換一個隨機種子重跑一次：那多跑的一次，是分辨「資料裡的結構」和「方法本身的結構」最便宜的方法。
