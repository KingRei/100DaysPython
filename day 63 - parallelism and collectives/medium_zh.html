Day 63 — 集合通訊：把模型切到很多張 GPU 上，而答案不變

程式碼：day 63 on GitHub

100 Days of Python - day 63

一個 70B 模型用 Adam 訓練，每張卡放一份完整副本的話每張卡要 1,043 GB——比任何一張卡實際有的記憶體多一個數量級。同一個模型拿去服務，64 個請求 x 128K token 的 KV cache 是 2,560 GB。兩個都放不下，所以兩個都得切；而每一種切法，都是同一個決定在不同地方被做：哪一個集合通訊會跑、跑幾次、每次多少位元組。

TP、EP、DP、DCP、DDP、FSDP、PP——七個縮寫，底下只有五個原語。今天先把原語做出來，然後訓練那一組、推論那一組分開講，每一種都跟單卡對照驗證。

五個原語

集合通訊        用來做什麼                         每個 rank 送出的位元組  步數
--------------  ---------------------------------  ----------------------  -------
broadcast       一個 rank 有，所有人都要           N                       log2(p)
all-reduce      大家各有部分和，所有人都要總和     2(p-1)/p · N            2(p-1)
reduce-scatter  大家各有部分和，每個人只留 1/p     (p-1)/p · N             p-1
all-gather      每個人有 1/p，所有人都要完整的     (p-1)/p · N             p-1
all-to-all      rank r 手上有要給每個 rank 的一份  (p-1)/p · N             p-1
point-to-point  把一個 tensor 交給下一個 rank      N                       1

這張表最重要的一列是：all-reduce 根本不是原語，它是 reduce-scatter 接 all-gather。這既解釋了它為什麼要付兩倍，也是今天很多段落的全部內容——同一句話套用兩次。

我在模擬的 8 個 rank 上跑了 ring 版本，向量 64 KB：14 步、每個 rank 送出 114,688 個位元組，最後每個 rank 都拿到同一個總和。天真的做法——大家把整份送給 rank 0、rank 0 加完再送回去——會有 917,504 個位元組全部擠在同一條線上。ring 的關鍵是任何時刻沒有任何 rank 握著超過一塊的總和，所以每個 rank 的量不會隨卡數長大，長大的只有步數。

這也就寫出了實作規則。訊息小的時候看跳數，tree 只要 2log2(p) 跳、ring 要 2(p-1) 步；訊息大的時候看位元組，ring 贏。在這個模組用的鏈路模型上交叉點大約在 2 MB。這就是 NCCL／RCCL 會依訊息大小換演算法的原因，也是為什麼 decode 裡那個很小的 all-reduce 一點都不免費——它付的是跳數，不是位元組。

第一部分：訓練——放不下的是權重

DDP 的正確性只有一行數學

DDP（torch.nn.parallel.DistributedDataParallel）是最簡單而且真的會動的做法：每張卡都放一份完整的模型，只是各自讀 batch 的不同一段。一張卡一個 process、一步一次梯度 all-reduce，其他什麼都不共享。

四個 rank、各吃四分之一的 batch、訓練 60 步。一台機器吃完整 batch 的 loss 是 0.014105，四個 rank 的也是 0.014105，權重最大差 1.19e-07。會相等是因為 loss 是平均：各 rank 梯度的平均剛好等於全 batch 的梯度，而 all-reduce 就是在強制這個平均。DDP 的全部內容就這樣。

但要注意它沒有做什麼：模型本身一點都沒被切開，所以每張卡的記憶體完全沒變。這一句話就是下一節存在的理由。

有兩個細節讓那次 all-reduce 不會被看見。第一是 bucket：梯度是從最後一層往前算出來的，所以切成好幾塊之後可以一邊飛、backward 一邊還在跑。

bucket 數  每個大小  每次 all-reduce  總通訊   最後曝露
---------  --------  ---------------  -------  --------
1          1024 MB   4.73 ms          4.73 ms  4.73 ms
4          256 MB    1.20 ms          4.81 ms  1.20 ms
25         41 MB     0.22 ms          5.40 ms  0.22 ms

bucket 愈多總量稍微變大（每個都要再付一次延遲），但真正曝露在 step 時間上的少很多。第二是梯度累積：在 with model.no_sync(): 裡 DDP 會完全跳過 all-reduce、讓梯度在本地堆積，所以 N 個 micro-step 只付一次 all-reduce。這也是全文唯一一個「跳過集合通訊是安全的」場合——因為每個 rank 都跳，而那正是底下第二個無聲 bug 破壞掉的條件。

ZeRO 與 FSDP：能切的就不要複製

Adam 在混合精度下每個參數要 16 個位元組：bf16 權重 2、bf16 梯度 2、fp32 master 4、兩個動量各 4。是權重本身的 8 倍——所以讓訓練塞不下的不是模型，是 optimizer。

階段                       每個 rank GB  線上 GB  相對 DDP  用到的集合通訊
-------------------------  ------------  -------  --------  -------------------------------------------
DDP（完全不切）            1043          228.2    1.00x     all-reduce(grad)
ZeRO-1（切 optimizer）     359           228.2    1.00x     reduce-scatter(grad) + all-gather(param)
ZeRO-2（再切梯度）         244           228.2    1.00x     reduce-scatter(grad) + all-gather(param)
ZeRO-3 / FSDP（再切參數）  130           342.3    1.50x     all-gather(param) x2 + reduce-scatter(grad)

前兩階是免費的，理由就在原語那張表：all-reduce 本來就是 reduce-scatter 加 all-gather。把它拆成兩半、中間只留自己負責的那一段梯度，記憶體省掉一大半而一個位元組都沒多送。要付錢的是第三階：參數本身被切開，所以每一層都要在開跑前 all-gather 回來、算完立刻丟掉，位元組 1.5 倍換記憶體 1/8。Day 62.5 把這個取捨叫「重算 vs 存起來」，這裡是「重抓 vs 存起來」，同一條曲線。

tensor parallel：帳單跟著 token 長

第一個矩陣照 column 切、第二個照 row 切。column 這個方向是挑過的：它讓每個 rank 拿到完整的幾個隱藏單元，所以兩個矩陣之間那個逐元素的非線性完全不用通訊。到第二個矩陣之後，每個 rank 手上是「整個寬度、但只加了自己那一份」的部分和，一次 all-reduce 收尾。跟單卡比：4.77e-07。

8,192 個 token、8-way 時：activation 是 128 MB，每次 all-reduce 每個 rank 搬 224 MB，一次 forward 有 160 次（80 層，attention 之後一次、MLP 之後一次），合計 35 GB。它跟著 token 數長、不是跟著參數長，跟 DDP 剛好相反——所以它是讓長序列訓練得起來的那條軸，也因此必須待在節點內。

sequence parallel 是把原語表再套一次：all-reduce 本來就是 reduce-scatter 加 all-gather，中間那段保持切開的狀態，於是中間的 norm 與 residual 只在 1/p 的序列上跑。位元組一模一樣（兩邊都是 224 MB），而每個 rank 的 activation 從 128 MB 降到 16 MB。

pipeline parallel：線上最便宜，代價付在閒置

只有 stage 邊界的 activation 要過去，而且是點對點、根本不是集合通訊：每個邊界 128 MB、7 個邊界，整趟 forward 896 MB。比 tensor parallel 少三個數量級，所以 stage 可以放在不同節點上。

代價是 bubble——最後一個 stage 要等第一個 micro-batch 走完前面所有站才有事做：

micro-batch 數  bubble  使用率
--------------  ------  ------
1               87.5%   12.5%
4               63.6%   36.4%
16              30.4%   69.6%
64              9.9%    90.1%

bubble =(stages - 1) / (micro-batch 數 + stages - 1)。解法永遠是切更多 micro-batch，直到它們小到每個 matmul 填不滿 GPU 為止——Day 62.5 的 roofline 在底下擋著。

真正的訓練是四條軸同時疊

64 張卡排成 tensor 8 x pipeline 4 x data 2 的 mesh，於是每張卡只拿 80 層裡的 20 層、70 B 參數裡的 2.19 B：


-------------------------------------  ---------------------------
每張卡的 optimizer state（不切）       32.6 GB
同樣的東西加上 ZeRO-3（切在 data 軸）  16.3 GB
TP 每步流量                            8.75 GB（節點內）
PP 每步交接                            0.12 GB（點對點）
梯度 all-reduce                        4.07 GB（一步一次、可重疊）

順序本身就是重點：TP 與 PP 已經先把參數切掉了，所以 ZeRO 表裡那個 1,043 GB 在 ZeRO 還沒出手之前就剩 32.6 GB；ZeRO 只負責切「data 軸還在重複的那一份」。

第二部分：推論——放不下的是 KV cache

少了什麼，又換成什麼卡住

推論沒有梯度，所以訓練那半最大的一列（228 GB 的梯度 all-reduce）根本不會被呼叫。服務端的 data parallel 就是「各自獨立、各有排程器的副本」，成本只有記憶體。而記憶體的大頭是 KV cache：

放法                              每個 rank 的 KV GB  為什麼
--------------------------------  ------------------  ---------------------------
整份快取（64 請求 x 128K token）  2,560               —
TP，MHA/GQA（照 head 切）         320                 head 剛好被 p 整除
TP，MLA（每 token 一個 latent）   2,560               head 這個維度已經不存在
DP attention（照請求切）          320                 每個 rank 擁有 8 個完整請求
context parallel（照位置切）      320                 每個 rank 擁有一段 key

另一半是：decode 一個請求只生一個 token，所以 TP 要搬的 activation 直接塌掉，但跳數一步都沒少：

階段                         真正搬的量  跳數時間  位元組時間  合計      延遲佔比
---------------------------  ----------  --------  ----------  --------  --------
decode（1 token x 64 請求）  1.75 MB     28.0 us   4.6 us      32.6 us   86%
prefill（8,192 token）       224.00 MB   28.0 us   587.2 us    615.2 us  5%

同一個 collective、同樣 2(p-1) 跳、資料少 128 倍。160 次加起來仍然是每個 decode step 5.21 ms，所以服務端會把 all-reduce 跟下一個 norm 融在一起、寧可少而肥不要多而瘦；也因此 tensor parallel 對 decode 的幫助會在頻寬用完之前就先停住。Day 62.5 說 decode 是被記憶體卡住，這裡是同一句話，只是把 HBM 換成了互連。

expert parallel：權重不動，動的是 token

Day 62 的 router 決定每個 token 要去哪幾個 expert；expert parallel 把 expert 分給各個 rank，於是 token 必須飛到擁有那個 expert 的卡上。一層兩次 all-to-all（dispatch 與 combine），跟單卡 MoE 逐位元相同。

8,192 個 token、top-8、8-way 時：每層送出 896 MB、收回 896 MB，整趟 forward 是 140 GB，是同樣 token 數下 tensor parallel 的四倍，因為每個 token 被送去 k 個 expert 而不是一個。把 dispatch 量化成 fp8 直接砍到 70 GB——這正是 DeepEP 會有一條量化 dispatch 路徑的原因，也是為什麼 MoE 的服務效能最後是被網路決定的。訓練 MoE 用的是同樣兩次 all-to-all，再加上 backward 的兩次。

context parallel（DCP）：切 KV，用 log-sum-exp 合併

每個 rank 只擁有一段 key 與 value，算出自己那段的部分輸出與 log-sum-exp，合併時用共同的最大值重新縮放再相加。跟完整 attention 比，2／4／8 個 rank 分別是 1.0e-16、8.0e-17、1.7e-16。

這就是 Day 52 為 FlashAttention 證過的那個恆等式——兩個部分 softmax 只要帶著各自的最大值與總和就能合併——只是當時兩半在不同的暫存器裡，現在在不同的 GPU 上。

誰需要它、誰不需要，這是縮寫沒講出來的部分。切 key 這個技巧對任何 attention 都成立（那叫 Ring Attention），但它只有在「沒有別的東西好切」的時候才是最便宜的選擇。MHA 或 GQA 的 KV cache 本來就能照 head 整除，tensor parallel 早就免費幫你切好了，沒有人會想用 context parallel。MLA 把 KV 壓成每個 token 一個 latent、head 這個維度整個消失，於是每個 TP rank 都得存一整份——而這正是服務端那個叫 DCP 的功能存在的原因。所以 DCP 要讀成「給 MLA 模型用的」，不是一條通用的軸；在那個情境下能選的只有照請求切（DP attention）或照位置切（這一條）。

兩半合起來看

哪一軸該放在哪裡

一個 rank、一步、8,192 個 token、每軸 8-way：

軸                     每步 GB  節點內    跨節點     倍率
---------------------  -------  --------  ---------  ----
tensor parallel        35.00    98.4 ms   774.0 ms   7.9x
expert parallel        140.00   378.1 ms  3017.7 ms  8.0x
context parallel       17.64    48.5 ms   384.3 ms   7.9x
pipeline parallel      0.12     0.3 ms    2.7 ms     8.0x
data parallel（梯度）  228.17   612.5 ms  4900.1 ms  8.0x

看第一欄，部署方式就自己寫好了。tensor 與 expert 每一層都要付幾十 GB，只能待在節點內的短連線上；pipeline 幾乎不送東西，跨網路完全無所謂；data parallel 量最大，但一步只付一次而不是每層一次、藏得進 backward，而且在推論時它根本不存在。

五種不會報錯的壞法

梯度用加的、忘了除以 world size。 學習率被無聲地乘上卡數。第 1／3／5 步，對的那條是 0.6129、0.3251、0.2362，加總的那條是 6.82、70,331、1.76e+10。這個 bug 在單卡上永遠測不出來——world size 是 1 的時候，加跟平均是同一個數。

不同 rank 走到不同分支。 集合通訊是用呼叫順序配對的，不是用名字。「這個 rank 這一步沒有 token 要給任何 expert，那就跳過 all-reduce」會讓 rank 0 停在一個 collective、rank 1 停在另一個，互等到天荒地老。NCCL 不會報錯，它就是停住。所以 MoE 的實作寧可送空 buffer 也不敢跳過——也所以 no_sync() 是安全的，因為每個 rank 都進去。

相加的順序也是答案的一部分。 同一批資料，ring 與 tree 的 all-reduce 結果在 65,536 個值裡有 32,459 個位元不同，最大差 9.77e-04（相對 1.2e-04）。重跑同一種實作是逐位元一樣的，所以這不是亂數：浮點加法不符合結合律，兩種排程只是加的順序不同。同一個 seed、不同的 world size，就是不同的 loss 曲線。

一個慢的 rank 就是整步的時間，因為集合通訊就是 barrier。假設每個 rank 每步有 1% 的機率卡一下：8 張卡時 7.7% 的步會中、整體慢 5.2%；512 張卡時 99.4% 的步都中、整體慢 49.3%。規模放大的是「出事的機會數」，不是每次出事的大小。

少做一次 all-reduce。 把 row-parallel 那層的 all-reduce 拿掉：形狀全對、沒有 NaN，輸出誤差 2.30，大約是輸出尺度的 77%。模型照樣生成文字，只是生得比較爛。所以任何平行化改動的第一個測試永遠是：把 world size 設成 1，答案有沒有變。

PyTorch 怎麼寫

mesh = init_device_mesh("cuda", (2, 4), mesh_dim_names=("dp", "tp"))

DistributedDataParallel(model)              # all-reduce(grad)，自動分 bucket
fully_shard(model, mesh=mesh["dp"])         # FSDP2 = ZeRO-3
parallelize_module(block, mesh["tp"], {
    "w1": ColwiseParallel(), "w2": RowwiseParallel()})

ColwiseParallel 與 RowwiseParallel 就是上面 tensor parallel 那一節：前者把輸出標成 sharded、後者標成 partial，而當一個 partial 的 tensor 被要求變成 replicated 時，DTensor 就插進那次 all-reduce。你標的是 placement，collective 是框架推導出來的——所以 profile 裡冒出一次意料之外的 all-reduce，通常是某個 placement 逼出來的。

JAX 怎麼寫

mesh = jax.make_mesh((2, 4), ("dp", "tp"))
x = jax.device_put(x, NamedSharding(mesh, P("dp", None)))
w = jax.device_put(w, NamedSharding(mesh, P(None, "tp")))

你完全不呼叫集合通訊。你只說陣列放在哪裡，XLA 自己插入需要的 all-reduce、all-gather 或 all-to-all。data parallel 是把 batch 軸切開、tensor parallel 是把特徵軸切開、FSDP 是把參數軸切開再加 jax.remat。自動選得不好時，shard_map 讓你自己寫 jax.lax.psum 與 jax.lax.all_to_all；而 jax.jit(f).lower(x).compile().as_text() 會把 XLA 插進去的每一個 collective 都印出來——在 JAX 裡做平行化 review 是讀 HLO，在 PyTorch 裡是讀 profiler trace。

服務端怎麼開

--tensor-parallel-size 8      --expert-parallel-size 8
--data-parallel-size 2        --pipeline-parallel-size 2
--context-parallel-size 2

同樣五個旗標、不同的算式，理由就是第二部分那幾段：沒有梯度要 all-reduce、KV cache 決定你能怎麼擺、而 collective 付的是跳數不是位元組。

我自己的收穫

訓練那一半的主角是權重、帳單跟著參數；推論那一半的主角是 KV cache、帳單跟著跳數。中間每一個縮寫都只是同一張表用不同方向讀：DDP 跟著參數、tensor 與 context 跟著 token、expert 跟著 token 乘 k、pipeline 不付位元組而是付閒置。底下的集合通訊從頭到尾就那幾個，變的只是數字——而且這些 bug 全部都是無聲的，所以唯一真正的測試是：一個 rank 的答案，跟完全不切的時候還一不一樣。
