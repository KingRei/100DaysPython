Balanced trees in one go: AVL, red-black and the B-tree

Code: day 28 on GitHub

100 Days of Python - day 28

Insert the numbers 1 to 100000 into a plain binary search tree, in order, and the tree you get is 99999 levels deep. Every key goes to the right of the previous one; there is no branching at all. The O(log n) you were promised is now O(n), and the input that caused it - already sorted data - is the single most common input in the world.

That is the whole reason balanced trees exist, and today I want to do all three of the classic ones at once, because they are not three unrelated data structures. They are three answers to the same question, and once you see the shared skeleton the differences stop being trivia and start being engineering decisions you can actually make.

On 2047 keys the numbers make the point better than prose does. Sorted input: height 2046, and an average lookup costs 1024 comparisons. Shuffled input: height 22, average lookup 12.62. Perfectly balanced: height 10, average lookup exactly 10.0. The random case is fine, which is exactly what makes this dangerous - the failure mode is not "sometimes slow", it is "fine in testing, quadratic in production".

The one primitive: rotation

Every self-balancing binary tree is built on a single operation, and it is worth staring at until it is obvious, because everything afterwards is bookkeeping around it.

def rotate_right(y):
    x = y.left
    y.left = x.right      # B changes parent - the only subtree that moves
    x.right = y
    update_height(y)      # y is now the lower node: update it FIRST
    update_height(x)
    return x

Read the shape in order: A x B y C. Before the rotation, y is on top. Afterwards, x is on top. And the in-order reading is still A x B y C - unchanged.

That is the entire trick. A rotation changes the height without changing the sorted order. The search property survives for free, one side gets a level shallower and the other a level deeper, and only one subtree (B) changes parent, so the cost is three pointer writes and O(1) time.

The one line people get wrong is the order of the two update_height calls. After the rotation y sits below x, so y's height has to be recomputed before x reads it. Swap those two lines and every height above the rotation is quietly wrong - the tree is still a perfectly valid BST, it just silently stops being balanced. No exception, no failing assert, just gradually worse performance. I have lost an hour to that exact bug.

AVL: measure the height, keep it tight

An AVL tree stores a height in every node and enforces one rule everywhere:

| height(left) - height(right) | <= 1

After an insert you walk back up the path you came down, and the first node that breaks the rule gets repaired. There are exactly four shapes, and they are the reason people find AVL fiddly - but the rule that picks between them is one line.

LL and RR are straight paths: the new key went left-left, or right-right. One rotation fixes them. LR and RL bend: left, then right. For those, a single rotation is useless - it just produces the mirror image of the same imbalance. So you rotate the child first to straighten the path, which turns it into an LL, and then rotate the parent.

def avl_rebalance(n):
    update_height(n)
    bf = balance_factor(n)              # height(left) - height(right)
    if bf > 1:                          # left heavy
        if balance_factor(n.left) < 0:  # ... but the child leans right: LR
            n.left = rotate_left(n.left)
        return rotate_right(n)
    if bf < -1:                         # right heavy
        if balance_factor(n.right) > 0: # ... but the child leans left: RL
            n.right = rotate_right(n.right)
        return rotate_left(n)
    return n

The sign of the child's balance factor is what decides single versus double. Same sign as the parent means the path is straight; opposite sign means it bends. That is the whole case analysis, and once you phrase it that way you never have to memorise four diagrams again.

There is a nice asymmetry between insert and delete that is worth knowing for interviews. An insert rebalances at most one node: the rotation restores that subtree to exactly the height it had before the insert, so nothing above it can possibly be affected. A delete can shorten a subtree, which can unbalance its parent, which can unbalance its parent - so the repairs cascade, potentially all the way to the root.

On 100000 sorted keys, AVL comes out 16 levels deep with a mean lookup of 15.72 comparisons. log2(100000) is 16.6, so it is essentially at the theoretical floor. It paid 99983 rotations to get there - almost exactly one per insert, which sounds alarming until you remember that a rotation is three pointer writes and an extra level of depth is a cache miss.

Red-black: stop measuring, start colouring

A red-black tree never looks at a height. It colours nodes and maintains five properties:

  1. Every node is red or black.
  2. The root is black.
  3. Every leaf (the NIL sentinel) is black.
  4. A red node has two black children - no two reds in a row.
  5. Every path from a node down to a leaf contains the same number of black nodes.

Properties 4 and 5 are the load-bearing pair. Black nodes are spread evenly, and reds cannot be adjacent, so the longest root-to-leaf path is at most twice the shortest, which gives height <= 2·log2(n + 1). Balance is a side effect of the colour rules, not something the code ever computes - and that indirection is exactly why red-black is looser than AVL.

Insertion paints the new node red. Red cannot change any path's black count, so property 5 is safe by construction; the only thing that can break is property 4. The fixup has three cases:

  • Case 1, red uncle. Paint the parent and uncle black, the grandparent red. No rotation at all - just recolouring. The black height through the grandparent is unchanged, but the grandparent is now red, so the same violation reappears two levels up and the loop continues. This is the case that iterates.
  • Case 2, black uncle, node on the inside. Exactly the AVL LR shape. One rotation straightens the zig-zag, turning it into case 3.
  • Case 3, black uncle, straight path. Recolour the parent black and the grandparent red, rotate the grandparent once. The subtree root is black again, so the loop ends here.

Because cases 2 and 3 both terminate the loop, and case 1 does no rotations at all, an insert costs at most 2 rotations and a delete at most 3, regardless of tree size. I measured it over 4095 random inserts and 2000 random deletes: red-black's worst single operation used 2 rotations for an insert and 3 for a delete. AVL's worst used 2 and 5.

So which one

On 100000 sorted keys:

           height  mean lookup  rotations  recolourings
---------  ------  -----------  ---------  ------------
AVL        16      15.72        99983      -
red-black  30      16.09        99969      499846

On 100000 shuffled keys they converge almost completely: height 19 for both, 15.95 against 16.03 comparisons, 69892 rotations against 58398.

Both are O(log n). The difference lives entirely in the constants and the worst case. AVL is shorter, so lookups are faster. Red-black is taller, but it does fewer structural writes - most of its repairs are recolourings, which are a bit flip rather than a pointer write - and it has a hard per-operation bound.

That bound is why the Linux kernel's CFS scheduler, epoll, the ext3 directory index, std::map and Java's TreeMap are all red-black and not AVL. A scheduler does not care about one extra comparison per lookup; it cares enormously about no single operation ever taking unbounded time. Reads dominate and writes are rare, pick AVL. Writes are frequent and latency must be predictable, pick red-black.

The B-tree: change the cost model, change the shape

Everything above quietly assumes that comparisons are expensive and pointer hops are free. On a disk, or an SSD, that assumption is backwards. A random read costs tens of thousands of cycles, and reading 16 bytes costs exactly the same as reading a full 4096-byte page.

If you are going to pay for a whole page anyway, fill it with keys. That is the entire idea of a B-tree: a node is a page. With minimum degree t, every node except the root holds between t - 1 and 2t - 1 keys.

def degree_for_page(page_bytes, entry_bytes):
    return max(2, (page_bytes // entry_bytes) // 2)

degree_for_page(4096, 16)   # -> 128, so up to 255 keys per node

The consequences are dramatic. One million keys fit in a tree of height 2 with 7874 nodes, and a lookup reads 3 pages. A binary tree over the same keys would be about 20 levels deep - potentially 20 random reads.

Insertion never rotates. Descending toward a leaf, any full child is split on the way down, and its median key moves up into the parent:

parent.keys.insert(i, median)          # median goes UP
parent.children.insert(i + 1, right)

Splitting before descending is the clever part: it guarantees the parent always has room, so a split can never propagate back upward and one downward pass is enough. And when the root itself is full, it splits into a brand-new root - which is the only way a B-tree ever gets taller. It grows upward at the root, never downward at the leaves, which is precisely why all leaves stay at exactly the same depth, forever, with no rebalancing rule needed.

With t = 2 and keys 1 through 10 inserted in order you end up with a root of [4], height 2, 8 nodes and 5 splits. Sorted input - the catastrophic case for a plain BST - is a complete non-event here.

LeetCode 110 and 1382

110, Balanced Binary Tree, asks whether a tree satisfies the AVL invariant. The naive answer calls a height() helper at every node, recomputing the same heights over and over, and is O(n²). The good answer makes one post-order recursion return both the height and the verdict, using -1 as a failure sentinel:

def is_balanced(root):
    def h(n):
        if n is None: return 0
        l = h(n.left)
        if l < 0: return -1              # already failed, stop early
        r = h(n.right)
        if r < 0: return -1
        if abs(l - r) > 1: return -1
        return 1 + max(l, r)
    return h(root) >= 0

-1 works as a sentinel precisely because a real height is always non-negative. Once a subtree reports failure, every level above just forwards it without looking further: one pass, O(n), early exit built in. The same "overload the return value" move solves tree diameter and maximum path sum. Note also that the space is O(h) for the recursion stack - which is itself an argument for caring about height, since a degenerate tree does not merely search slowly, it blows the stack.

1382, Balance a Binary Search Tree, hands you an already-skewed BST and asks you to fix it after the fact. Two steps: flatten with an in-order walk, which is sorted by definition, then rebuild by always taking the middle element as the root (which is LeetCode 108 on its own). The two halves differ in size by at most one, so the height is forced down to ceil(log2(n + 1)). A chain of 63 nodes goes from height 62 to height 5, with the key set untouched.

The price is O(n) extra space for that array. If you cannot spend it, the Day-Stout-Warren algorithm rotates the whole tree into a right-leaning vine and then back into balance in O(1) space - built out of the very same rotation primitive from the top of this article.

Why this matters later

Rotations and the in-order invariant come back the moment a tree carries aggregate data rather than just keys: an interval tree stores a subtree maximum in every node, and a rotation has to recompute it in exactly the same "lower node first" order as update_height. Segment trees and Fenwick trees drop rotations entirely and get their balance from the index arithmetic instead, which is the same trade the B-tree makes - fix the shape up front and you never have to repair it. And the B-tree itself is not a historical curiosity: it is the on-disk index in PostgreSQL, SQLite, MySQL's InnoDB and essentially every filesystem, and its LSM-tree rival makes exactly one different assumption about which is more expensive, reads or writes.
