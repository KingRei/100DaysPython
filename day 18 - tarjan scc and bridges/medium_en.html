Two numbers a DFS already knows

100 Days of Python - day 18

Point at a network diagram and ask three questions. Which cable, if it fails, splits the network in two? Which machine, if it dies, takes half the network with it? Which groups of services can all reach each other, so that a change in one can come back to bite the rest?

These sound like three problems. They are one depth-first search, with two integers written down per vertex.

Day 17 was about the price of an assumption - Dijkstra buys its speed with "no negative weights" and gives a wrong answer, silently, when you break it. Today is the opposite kind of story: a traversal we already know, carrying information we were throwing away.

The two numbers

Run a DFS and keep a clock. The first number is easy:

disc[u]   the clock value when the DFS first arrived at u

The second one is the whole idea:

low[u]    the smallest disc reachable from u's subtree,
          using tree edges plus at most one "back" edge

Read low[u] as an answer to a question: can anything under me climb back above me, without going through me? If it can, low[u] will be smaller than disc[u], because whatever it climbed back to was discovered earlier.

Maintaining it takes three lines. When a child finishes, its low flows up to the parent. When we meet an already-visited vertex, we take its disc:

def dfs(u, in_edge):
    disc[u] = low[u] = clock; clock += 1
    for v, eid in adj[u]:
        if eid == in_edge:          # skip the EDGE, not the vertex
            continue
        if disc[v] == -1:           # tree edge
            dfs(v, eid)
            low[u] = min(low[u], low[v])
        else:                       # back edge to an ancestor
            low[u] = min(low[u], disc[v])

That last line surprises people: why disc[v] and not low[v]? Because the question is which timestamp can I jump back to, not where does that vertex's subtree eventually reach. Using low[v] would credit us with an escape route we cannot actually take.

Reading one: bridges

A bridge is an edge whose removal disconnects the graph. Suppose u-v is a tree edge. Delete it, and the only way for v's side to stay connected is a back edge from somewhere in v's subtree to u or higher. "Or higher" is exactly disc[u] or smaller. So:

if low[v] > disc[u]:
    bridges.append((u, v))

On the example graph - two triangles glued at vertex 2, joined by a single edge to a third triangle - the only bridge is 4-5. Every edge inside a triangle has the other two edges as a backup, and low finds that backup automatically.

Reading two: articulation points

Now delete a vertex instead. The difference is subtle and the code change is one character. If we remove u itself, then u is no longer a valid escape hatch, so the subtree must reach strictly past u:

if u != root and low[v] >= disc[u]:
    cut.add(u)

The root is a special case, and not because of some implementation quirk: it has no parent to climb back to, so the low test is vacuous for it. A root is an articulation point exactly when the DFS gave it more than one child subtree - two subtrees that never found each other means the root is the only thing joining them.

On our graph the articulation points are 2, 4 and 5. Vertex 2 is the instructive one: it sits on no bridge whatsoever. Removing the edge 2-4 leaves the graph connected; removing the vertex 2 tears it in half. Edges and vertices are genuinely different questions, separated in code by one equals sign.

The bug almost every write-up has

Look again at the skip:

if eid == in_edge:      # not:  if v == parent
    continue

Most explanations skip the parent vertex, and it passes essentially every test case anyone writes. Then someone runs two cables between the same pair of routers. Now the second cable is a perfectly good back edge - but the parent-vertex test swallows it too, low never drops, and the code reports a bridge that physically does not exist. It does not crash, and the answer looks entirely reasonable.

Tracking the edge id costs one extra field in the adjacency list and makes the whole class of bug disappear. The demo page has both versions side by side on the same doubled edge, which is more convincing than any paragraph.

Reading three: strongly connected components

Directed graphs break an assumption we did not notice we were using: "u can reach v" no longer means "v can reach u". A vertex we have already visited might be an ancestor we can genuinely loop back to - or it might sit in a component we finished long ago, one-way, no return.

Tarjan's fix is a stack. Every visited vertex waits on it until its component is decided, and low may only be relaxed against a vertex that is still there:

for v in adj[u]:
    if disc[v] == -1:
        dfs(v)
        low[u] = min(low[u], low[v])
    elif on_stack[v]:               # only an unfinished ancestor counts
        low[u] = min(low[u], disc[v])
    # else: v's component is closed - it cannot come back, so ignore it
if low[u] == disc[u]:               # u is the root of a component
    pop the stack down to u

low[u] == disc[u] means nothing under u found a way above u, so u is the top of its component and everything pushed after it belongs with it. Pop down to u and you have an SCC.

Drop the elif guard and watch what happens on the example: one edge, 5->2, points into a component that closed three steps earlier. Without the guard low[5] drops to 2, low[4] follows, 4 never recognises itself as a root, and {4,5} gets merged with {0} - a "strongly connected component" whose first vertex has no incoming edges at all. Nobody can get back to 0. Again: no crash, just a wrong answer.

The DAG hiding underneath

Contract each component to a single node and the result is always acyclic - a cycle between two components would mean they could reach each other, which would have made them one component. That collapsed graph is called the condensation, and Tarjan hands the components back in reverse topological order of it, for free.

This is why the SCC step shows up in so many places that have nothing to do with graph theory homework: 2-SAT solves an implication graph by checking whether x and not x land in the same component; compilers and bundlers find circular imports this way; dataflow analyses run over the condensation because it can be processed in one pass. Day 13's topological sort was waiting on the other side of this traversal the whole time.

LeetCode 1192 - Critical Connections in a Network

The paired problem is "find the bridges", relabelled as servers and cables. The interview wrinkle is not the algorithm - it is that n goes up to 10^5 while CPython stops recursing at depth 1000. A single long chain crashes the elegant version.

Rewriting a DFS iteratively is mostly bookkeeping, with one insight: each stack frame has to carry a cursor into the neighbour list, because that is what the language was quietly remembering for us - where to resume after a call returns.

stack = [(0, -1, iter(adj[0]))]
while stack:
    u, in_edge, it = stack[-1]
    descended = False
    for v, eid in it:               # the iterator resumes where it stopped
        if eid == in_edge:
            continue
        if disc[v] == -1:
            disc[v] = low[v] = clock; clock += 1
            stack.append((v, eid, iter(adj[v])))
            descended = True
            break                   # this break is the function call
        low[u] = min(low[u], disc[v])
    if not descended:               # and this pop is the return
        stack.pop()
        if stack:
            p = stack[-1][0]
            low[p] = min(low[p], low[u])
            if low[u] > disc[p]:
                out.append([p, u])

Everything that used to happen "after the recursive call" now happens on the pop. Storing an iterator per frame is the Python-specific trick; the general one is that an explicit stack needs to remember how far through the loop each frame was, not just which vertex it was on.

Why this matters later

low is a small, sharp idea: propagate one number upward and a global property becomes a local test. That shape - a bottom-up pass that summarises a subtree into a value the parent can use in constant time - is the same shape as tree DP, as backpropagation through a computation graph, and as the segment-tree merges coming later in this series. Learning to recognise "what single value would the parent need from me?" pays for itself repeatedly.

And the practical version is even simpler: whenever someone asks which component of a system is a single point of failure, they are asking for a bridge or an articulation point, and the answer is one traversal away.
