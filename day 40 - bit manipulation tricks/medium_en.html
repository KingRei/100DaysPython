Bit tricks: masks and popcount, and where Python's endless integers break them

Code: day 40 on GitHub

100 Days of Python - day 40

Store a set of numbers as the bits of one Python integer, and "how many members do these two sets share?" gets about sixty times faster than asking two set objects, while the set shrinks to a thirty-first of the memory. Count the ones in that integer with int.bit_count() and it beats every clever popcount formula from C, by four to thirty-five times.

That is the good half of today. The other half is what happens when a bit trick copied from C or Java meets a Python integer. bin(-5).count('1') returns 2, where C says 31. The textbook answer to "add two numbers without +" never returns on -1 + 1. A standard answer to LeetCode 137 passes both of its examples and then fails on every test whose answer is negative. None of them raises an error.

Yesterday's bitmask N-Queens picked its next column with free & -free and moved on without saying why that works. Today is the why - and the one property of Python integers that decides which bit tricks you can trust.

Python integers have no width

In C, an int is 32 bits. -5 is stored as 32 bits: twenty-nine ones and then 011 at the bottom. A Python int has no 32. It behaves as if it had infinitely many bits, so -5 is a 1 in every position from bit 3 upward, forever.

That one fact splits every bit trick into two groups.

Tricks that look at each column on its own are safe. &, |, ^ and ~ compute bit k of the answer from bit k of the inputs and nothing else. They give the same answer at every width, so they work on negative Python integers exactly as in C.

Tricks that ask "how many bits?" need a width, and Python never stores one. That covers popcount of a negative number, "which is the top bit?", and any loop that waits for a carry to fall off bit 31. On a Python integer there is no bit 31 to fall off.

Two tiny functions pin the width back on, and they fix every trap in this article:

M32 = (1 << 32) - 1

def u32(x):           # keep the low 32 bits - what a C uint32_t would hold
    return x & M32

def s32(u):           # read 32 bits as signed: bit 31 is worth -2**31, not +2**31
    u &= M32
    return u - (1 << 32) if u >> 31 else u

u32(-5) is 4,294,967,291, and s32 turns that back into -5.

The toolkit, on x = 180

Testing, setting, clearing and toggling bit k are one shift and one operator each: x >> k & 1, x | 1 << k, x & ~(1 << k), x ^ 1 << k. The three worth memorising work on the lowest bit:

They all come from one fact. Subtracting 1 turns the lowest 1 into a 0 and every 0 below it into a 1, and everything above it stays. So x & (x - 1) wipes out exactly the lowest 1: 180 becomes 176. -x is ~x + 1, which flips everything above the lowest 1 and leaves the lowest 1 alone, so x & -x keeps only that bit: 4. And x | (x + 1) turns on the lowest 0: 181.

x & -x is the step a Fenwick tree takes to jump between the ranges it stores (Day 29), and it is how yesterday's N-Queens pulled one free column out of a mask. (x & -x).bit_length() - 1 gives the number of trailing zeros, 2 for 180.

One precedence trap before moving on. Arithmetic binds tighter than a shift, so 1 << n - 1 means 1 << (n - 1). For n = 4 that is 8 (1000), not the four ones you wanted (15). Write (1 << n) - 1. The opposite trap from C, x & 1 == 0, does not exist in Python, because & binds tighter than == here.

popcount five ways

Counting the 1s in a number (its "popcount") has a whole folklore of methods:

def popcount_shift(x):          # one round per bit, up to the top 1
    count = 0
    while x:
        count += x & 1
        x >>= 1
    return count

def popcount_kernighan(x):      # one round per 1
    count = 0
    while x:
        x &= x - 1              # drop the lowest 1
        count += 1
    return count

The shift loop looks at every bit. Kernighan's loop uses x & (x - 1) to jump straight from one 1 to the next, so it runs once per 1:

On 200,000 random 32-bit numbers that is 3,199,046 rounds against 6,200,129 - half, because a random 32-bit number has about 16 ones but about 31 bits up to its top 1.

The cleverest of the classic methods adds all 32 bits at once without any loop, a technique called SWAR ("SIMD within a register"):

def popcount_swar32(x):
    x = x - ((x >> 1) & 0x55555555)                   # 16 two-bit counts
    x = (x & 0x33333333) + ((x >> 2) & 0x33333333)    # 8 four-bit counts
    x = (x + (x >> 4)) & 0x0F0F0F0F                   # 4 byte counts
    return ((x * 0x01010101) & 0xFFFFFFFF) >> 24      # add the 4 bytes

The first line turns each pair of bits into the count of 1s in that pair. The second adds neighbouring pairs into 4-bit counts, the third adds those into byte counts, and the multiply adds all four bytes into the top byte. In C this is the fast one. In Python:

The builtin int.bit_count() (Python 3.10 and later) wins by five times over SWAR. Every &, >> and + in Python is a separate trip through the interpreter, so the fastest method is the one with the fewest Python-level operations, and bit_count() runs its whole loop in C. It also works on integers of any size: on a single million-bit integer it takes about 70 microseconds, while bin(x).count('1') takes about 6 milliseconds because it first builds a million-character string.

Silent failure: popcount of a negative number

Now ask all of them about -5. C's __builtin_popcount and Java's Integer.bitCount say 31. Python says:

bin(-5).count('1')     -> 2          bin(-5) is '-0b101': it counts the digits of 5
(-5).bit_count()       -> 2          documented as the popcount of abs(x)
Kernighan / shift loop -> never returns
(-5 & M32).bit_count() -> 31

Kernighan never returns because x & (x - 1) of a negative number is still negative. The values go -5, -6, -8, -16, -32, ..., and after 40 rounds x is about minus 2.2 trillion. There is always another 1 further up. The fix is to pin the width before counting.

LeetCode 338 - Counting Bits

The task. For every whole number from 0 up to n, report how many 1s its binary form contains.

Input / output. One integer n; return a list of n + 1 integers where entry i is the number of 1 bits in i.

Example. n = 5 gives [0, 1, 1, 2, 1, 2]: 0 is 0, 1 is 1, 2 is 10, 3 is 11, 4 is 100, 5 is 101.

Constraints. 0 <= n <= 100,000. Calling popcount on every number is already fast enough. The follow-up asks for a single linear pass with no builtin popcount, and that is what turns it into a DP problem.

leetcode.com/problems/counting-bits

class Solution:
    def countBits(self, n: int) -> list[int]:
        ans = [0] * (n + 1)
        for i in range(1, n + 1):
            ans[i] = ans[i >> 1] + (i & 1)   # i without its last bit, plus that bit
        return ans

i >> 1 drops the last bit, so it is a smaller number whose entry is already in the table, and i & 1 is the bit that was dropped. The same table also falls out of the lowest-bit trick: ans[i] = ans[i & (i - 1)] + 1, because i has exactly one more 1 than i with its lowest 1 removed.

A Python int as a set of a million members

Bit v being set means "v is in the set". Then intersection is &, union is |, and the size is bit_count(), each one a single loop in C over machine words. Two random 100,000-member sets drawn from the numbers 0 to 999,999 share 9,955 members. Asking two set objects takes about 5 ms; (a & b).bit_count() takes about 0.08 ms. The set weighs 4,194,520 bytes; the integer weighs 133,360.

This is the same move as Day 34's subset sum (bits |= bits << x updated a whole row of the DP table at once), Day 32's Bloom filter, and Day 27's Jaccard similarity.

There is one slowdown that never shows up in small tests. x |= 1 << v looks like a constant-time "add one member", but a Python integer cannot be changed in place, so every |= builds a brand-new integer as long as the whole set. Adding 20,000 members to a million-bit set that way takes about 220 ms. Filling a bytearray and converting once takes about 3 ms:

def to_bitset(values, universe):
    buf = bytearray((universe + 7) // 8)
    for v in values:
        buf[v >> 3] |= 1 << (v & 7)       # byte v // 8, bit v % 8
    return int.from_bytes(buf, 'little')

LeetCode 136 / 137 - what XOR can and cannot cancel

LeetCode 136 - Single Number

The task. In a list where every value shows up exactly twice except one, find the one that shows up once.

Input / output. A non-empty list of integers nums; return the lone value.

Example. [4, 1, 2, 1, 2] gives 4: the two 1s pair up, the two 2s pair up, and 4 is left over.

Constraints. Up to 30,000 values between -30,000 and 30,000, linear time and constant extra space. The space rule is what forbids a Counter or a set and forces a bit trick.

leetcode.com/problems/single-number

LeetCode 137 - Single Number II

The task. The same, except every other value shows up exactly three times.

Input / output. A non-empty list of integers nums; return the value that appears once.

Example. [0, 1, 0, 1, 0, 1, 99] gives 99, since 0 and 1 each appear three times.

Constraints. Up to 30,000 values anywhere in the signed 32-bit range, linear time and constant extra space again. The signed range is the trap: the answer can be negative, and in Python that decides whether the column-counting answer is right.

leetcode.com/problems/single-number-ii

class Solution136:
    def singleNumber(self, nums):
        return reduce(xor, nums, 0)       # every pair cancels, column by column

class Solution137:
    def singleNumber(self, nums):
        ones = twos = 0                   # per column: seen once / seen twice
        for x in nums:
            ones = (ones ^ x) & ~twos
            twos = (twos ^ x) & ~ones
        return ones

XOR cancels pairs, so 136 is one line. It cannot cancel triples, so 137 keeps a counter that goes 0, 1, 2, 0 in every column, stored across the two integers ones and twos. Both answers use only ^, & and ~, so both work on negatives with no width at all: [-7, 3, 3] gives -7.

The other well-known answer to 137 counts how many numbers have bit k set, for each of the 32 columns, and keeps the columns whose count is not a multiple of 3. Leave off the final s32 and this is what happens:

nums                      ones/twos   count + s32   count, no s32
[2, 2, 3, 2]                      3             3               3
[0, 1, 0, 1, 0, 1, 99]           99            99              99
[-2, -2, -3, -2]                 -3            -3   4,294,967,293

The rebuilt number has bit 31 set. Without s32, Python counts that bit as plus 2.1 billion instead of minus 2.1 billion, and -3 comes back as 4,294,967,293. Both examples pass. On 1,000 random tests over the full range it is wrong on 502 - exactly the ones whose answer is negative.

LeetCode 371 - Sum of Two Integers

The task. Add two integers without using the + or - operators.

Input / output. Two integers a and b; return their sum.

Example. a = 2, b = 3 gives 5. 2 ^ 3 = 1 is the sum if you ignore carries, (2 & 3) << 1 = 4 is the carry, and 1 ^ 4 = 5 leaves no carry.

Constraints. -1000 <= a, b <= 1000. Small, but negative numbers are allowed, and in Python that is the whole problem.

leetcode.com/problems/sum-of-two-integers

The C answer, typed into Python, is:

while b:
    a, b = a ^ b, (a & b) << 1
return a

It passes both examples. Then try -1 + 1. The pair becomes (-2, 2), (-4, 4), (-8, 8), ... The carry moves one place to the left each round. In C it would reach bit 31, shift out of the word and vanish after 32 rounds. In Python there is nowhere for it to go: after 40 rounds the carry is 1,099,511,627,776 and still growing, and the loop never ends.

Masking both values to 32 bits every round makes the carry fall off, and -1 + 1 stops at 0 after 32 rounds. But masking alone gives -1 + -1 = 4,294,967,294, because the answer comes back as an unsigned 32-bit number. The last line reads bit 31 as the sign:

class Solution:
    def getSum(self, a: int, b: int) -> int:
        a, b = a & M32, b & M32
        while b:
            a, b = (a ^ b) & M32, ((a & b) << 1) & M32   # carry falls off bit 31
        return a if a < 1 << 31 else a - (1 << 32)       # bit 31 is the sign

This is the interview caveat for 371 in Python. The algorithm is three lines, and all the difficulty is in putting back the width that C gives you for free.

Complexity

operation                                   time               space
test / set / clear / lowbit (fixed width)   O(1)               O(1)
popcount, shift loop                        O(bit length)      O(1)
popcount, Kernighan                         O(number of 1s)    O(1)
int.bit_count() on an n-bit int             O(n / 64)          O(1)
Counting Bits (LeetCode 338)                O(n)               O(n)
bitset &, |, bit_count over a universe U    O(U / 64)          O(U / 8) bytes
bitset built by x |= 1 << v, m members      O(m * U / 64)      O(U / 8) bytes
Single Number I / II (136 / 137)            O(n)               O(1)
Sum of Two Integers (371), 32-bit           32 rounds at most  O(1)

Every O(1) in the first row assumes a fixed width. On a million-bit Python integer each of those operations costs time proportional to its length, which is why building a bitset one bit at a time is quadratic.

Why this matters later

Bitsets come back wherever a large set needs fast intersections: a graph stored as one integer per node turns "common neighbours" into one &, and HyperLogLog estimates how many distinct items it has seen from the number of leading zeros in their hashes, which in Python is bit_length(). On the AI side, int4 quantization stores two 4-bit weights per byte, and reading them back is nothing but shifts and masks - with the same question of whether bit 3 is a sign bit. Hashing functions and random number generators are built from XOR and shifts too, and they always work at a fixed width, so a Python port of one needs & M32 or & M64 after every step.

And the habit carries everywhere: when a bit trick from another language gives you a strange number in Python, check whether it asked "how many bits?".
