Day 59 — 取樣策略：怎麼讓模型不要每次都講同一句話，又不會開始胡說

程式碼：day 59 on GitHub

100 Days of Python - day 59

同一個模型、同一個開頭，三種用法。每一步都取機率最大的字元：它會寫出一句話——而且永遠是同一句，儘管它的文法允許 1,250 句。把 temperature 調到 2.0 照機率抽：100 個樣本裡，合文法的有 0 句。保持同樣的 2.0，只多加一條過濾規則：100 個樣本裡有 96 句不重複的話，而且每一句都合文法。

這三次模型本身完全沒變。變的是「怎麼把模型的輸出變成一個 token」這條規則，也就是今天的主題。

這一天在系列裡的位置

前面幾天先把會產生 logits 的東西蓋出來，然後讓它跑得便宜：KV cache、共用前綴的 radix tree、管顯存的分頁配置器。這些工作最後都停在同一個地方——一個長度等於詞彙表大小的分數向量。取樣是它之後的那一步，也是這份清單裡唯一一個會改變模型說什麼、而不是說得多快的旋鈕。

為了讓「說什麼」可以被量，今天的模型是一個字元 8-gram，訓練語料是用一個小文法產生的 1,500 句：冠詞 ＋（可選的）形容詞 ＋ 五個名詞之一 ＋ 五個動詞之一 ＋ 五個地點之一。這個文法剛好允許 1,250 句，所以任何一行生成結果都可以用 parser 檢查。於是底下每個數字都是 100 個樣本的比率：幾句合文法、出現了幾句不重複的話——不是靠感覺。

一步看起來很乾淨，一句話就不是了

context 是 'the small cat ' 的時候，模型給 s 0.61、r 0.22、w 0.16，剩下 21 個字元加起來 0.31%。entropy 是 1.39 bits，而「機率加起來到 0.9 的最小集合」只有 3 個字元。

問題就在那 0.31%，而且它要乘開來才看得出來。一句話大約 30 步，所以「中途至少踩到一次不可能的字元」的機率是 1 − 0.9969³⁰ ＝ 9.0%。而且踩到一次就夠了：接下來模型得從一個它沒看過的前綴繼續寫，後面整句都是亂猜。真實模型的尾巴不是 21 個字元，是十幾萬個 token，每一個都不可能。

最直覺的解法是乾脆不要抽——每一步都取最大值。這確實有效：100 個 greedy 樣本 100% 合文法。但它們是 1 句不重複的話。greedy 不是「比較差的取樣」，是完全沒有取樣。

greedy 連「最可能的那句話」都不是

在把 greedy 放下之前，值得看一下它在「它看起來正在做的那件事」上做得多差。文法只允許 1,250 句，少到可以全部列出來、而且每一句都精確算出機率——一句話的 log 機率就是它每一步 log 機率的總和。

整句機率最高的   'a small dog sat in the garden.'   log p = -6.244
greedy 給的      'the red cat sang in the garden.'  log p = -6.717，1,250 句裡排第 44

greedy 每一步都取機率最高的字元，結果落在第 44 名，比最好的那句低 1.61 倍。原因是結構性的、不是這個模型的怪癖：某個在當下很有吸引力的字元會把你帶進一個「之後沒有好結尾」的前綴，而逐步規則回不了頭。逐步 argmax ≠ 序列 argmax。 這個落差就是「在序列上搜尋」會是另一種 decoding 策略、而不是在這裡調個參數就好的全部理由。

全部列舉還順便買到兩個免費的驗證。這 1,250 句佔掉模型「句子層級」機率的 90.9%，而 t = 1.0 實際抽樣量到的合文法率是 90%。另外，從這個分佈抽 100 句、期望會有 87.3 句不重複，實測是 88。理論跟抽樣對得上，所以本文其餘的比率可以信。

temperature

temperature 在 softmax 之前把 logits 除掉。小於 1 會放大分數之間的差距、讓分佈變尖；大於 1 會縮小差距、讓分佈變平；等於 0 的時候所有實作都走另一條 argmax 的路，不是真的去除以零。

兩欄要一起看。t = 0.7 時 100 個樣本給出 98 句不同的話，而且每一句都合文法——這就是實務上預設值大多落在 0.6～0.9 的原因：在這個區間，多出來的隨機性幾乎都落在模型本來就覺得差不多的分岔點上。t = 1.3 剩 55%，t = 1.7 剩 5%。

有趣的是紫色那一欄也跟著掉。亂到一個程度之後就不再換到多樣性了——壞掉的句子不算另一種說法——所以這不是「用正確性換多樣性」，是兩個一起輸。而且崩得很快：t 從 1.0 到 1.7，entropy 只從 0.34 漲到 1.18 bits，正確率卻從 90% 掉到 5%。

截斷：熱度留著，尾巴剪掉

所以把 temperature 釘在最糟的 2.0，只改「哪些 token 可以被抽到」。

規則                 合文法      不重複句數
不截斷                    0%          0
top-k 1（＝greedy）     100%          2
top-k 3                   0%          0
top-p 0.9                 2%          2
top-p 0.7                89%         85
top-p 0.5               100%         80
min-p 0.1               100%         96
typical 0.9               2%          2
typical 0.5              94%         84

隨機性從來不是問題。被拿掉的是裡面「本來就不可能對」的那一部分。

這張表有兩個要誠實講的地方。top-k 1 是 greedy 換個名字，所以它那個滿分沒有意義。另外我們的詞彙表只有 24 個字元、不是 15 萬個 token，所以門檻值不能照搬——p = 0.5 對真模型來說是很兇的設定。能搬的是這張表的形狀：會自己調整的規則贏過只會數數的規則。

為什麼是質量，不是數量

掃過整份語料，下一個 token 的分佈分成兩種。249 步裡有一個字元機率超過 90%——模型很有把握，因為文法沒給它別的選擇。另外 61 步沒有任何字元超過 90%——模型站在分岔點上，四五個選項幾乎一樣高。

現在同一個 k 套在兩種步上。k = 1 時，有把握的那一步只丟掉 0.45% 的質量，那純粹是平滑造成的雜訊，無所謂；沒把握的那一步丟掉 54%，那是模型真正的意見被丟掉。把 k 調大到讓後者滿意，前者就開始把垃圾放進來——而那些垃圾就是前面講的尾巴。

top-p 問的是另一個問題：留下「機率加起來剛好到 p」的最小集合。數量於是自己跟著分佈的形狀跑——上圖有把握的那一步留 2 個、沒把握的那一步留 5 個，整份語料平均是 1.0 對 3.46。這就是 nucleus sampling 這個名字的意思：核心有多大是分佈決定的，不是你決定的。

min-p 站第三個位置：留下所有「至少值最佳 token 某個比例」的 token。它跟 top-p 一樣會自己鬆緊，而且實作上只是每個 token 比較一次——不用排序、不用累積和——這也是它在上面那張表裡撐過 temperature 2.0 的原因。

第三種問法：typical sampling

top-k 問的是數量，top-p 問的是質量。locally typical sampling 兩個都不問：它留下「意外程度 −log p 最接近這一步熵值」的 token。背後的主張是，自然語言並不是每個位置都挑最好猜的那個詞——它每個詞攜帶的資訊量大致固定——所以一個「比這一步的平均還要理所當然」的 token，跟一個「比平均還要意外」的一樣不典型。

在這份語料上，兩條規則其實從來沒分開過。1,875 個步驟裡，typical 0.9 每一次都跟 top-p 留下同樣數量的 token，而且一次都沒有把最可能的那個丟掉——這也是上面那張表裡 typical 兩列幾乎貼著 top-p 兩列的原因。這件事要講出來而不是藏起來：24 個字元的詞彙表根本沒有空間讓兩條規則不一致，而這正是玩具模型照不出來的那種差別。

所以這裡刻意造一個會讓它們分開的分佈——一個獨大的 token、一個中間群、一條很長的平尾，熵 2.28 nats：

獨大的, p=0.60      意外程度 0.51    離熵 1.77
中間群, p=0.03      意外程度 3.51    離熵 1.23
尾巴,   p=0.0001    意外程度 9.21    離熵 6.93

跟兩條規則都要 0.25 的質量：top-p 留 1 個，就是那個獨大的。typical sampling 留 9 個——而且把最可能的那個整個丟掉，因為中間群才是攜帶典型資訊量的那一組。top-p 用機率排序，typical sampling 用「離預期意外程度多遠」排序。在 15 萬個 token 的詞彙表上這是真的會造成行為差異的；而它跟本文其他東西用的是同一個掛鉤：一個判斷式，在 softmax 之前作用在 logits 上。

順序會改變答案

同時設 temperature=2.5 和 top_p=0.9，有兩種跑法，而它們給的是不同的分佈：

  • 先 temperature 再 top-p：18 個候選，最高機率 0.394
  • 先 top-p 再 temperature：2 個候選，最高機率 0.545

先壓平的話，要湊滿 0.9 就得收更多 token，所以 nucleus 跟著熱度一起變寬。先截斷的話，候選集合是用「冷的」形狀決定的，加熱只是在裡面重新分配。兩者的 total variation distance 是 0.276——不是小數點後的差別，是不同的 sampler。

我看過的伺服器一律是 penalties → temperature → top-k → top-p。這是慣例不是定理，而且它正好解釋了上面那張表：top-p 0.9 救不回 t = 2.0，就是因為 nucleus 是在壓平之後才量的。

一個不會報錯的錯

截斷會把一些 token 設成 0，而原本在它們身上的質量總得有個去處：

cut = np.partition(p, -k)[-k]
q = np.where(p >= cut, p, 0.0)      # 只剩 0.9969
# q /= q.sum()                      <- 忘了這一行

把沒有重新正規化的 q 丟給累積和取樣器，0.27% 的抽樣會掉到陣列尾端之外。在 C++ 裡那是讀到界外；在 Python 裡它會無聲地變成夾到的那個索引，也就是對某一個特定 token 的偶發、而且不可重現的偏誤。每一條過濾規則最後都必須除以留下來的質量。

在 GPU 上，top-p 根本不排序

真實詞彙表大約 15 萬個 token，而取樣是「每個序列每一步」都要做一次，所以最直覺的作法——排序、累積和、切——是落在伺服器吐出的每一個 token 的關鍵路徑上。完整排序大約 2.6M 次元素比較，部分的 top-50 選擇大約 0.15M。

但 top-p 其實不需要順序。把它改寫成：找一個機率門檻，讓門檻以上的質量剛好超過 p。這在一維上是單調的，所以可以二分：

lo, hi = 0.0, p.max()
for _ in range(24):
    mid = (lo + hi) / 2
    mass = p[p >= mid].sum()        # 一次對整個詞彙表的 reduction
    lo, hi = (mid, hi) if mass >= thr else (lo, mid)

24 輪「比較 ＋ 加總」，全程沒有任何排序，而留下來的集合跟排序版完全一樣。

在 vLLM 裡

上面所有東西就是一個物件：

from vllm import LLM, SamplingParams

out = LLM("Qwen/Qwen3-8B").generate(prompts, SamplingParams(
    temperature=0.8, top_k=50, top_p=0.95, min_p=0.0,
    repetition_penalty=1.1, seed=1234,
    n=4, logprobs=5, max_tokens=256, stop=["\n\n"]))

temperature=0 走 argmax 那條路，不是真的去除。repetition_penalty 在 temperature 之前改 logits，把已經出現過的 token 的分數除掉。seed 給這個請求自己的亂數產生器——收到客訴要重現問題時，通常就只剩這個把手可以抓。logprobs=5 回傳的就是本文第一張圖的前五列。n=4 是同一個 prompt 抽四次——KV 那一半前一天已經用 refcount 和 copy-on-write 解決了，今天加的只是四顆不同的骰子。

SamplingParams 是 per-request 的，但 sampler 本身是每一步跑一次、整個 batch 一起：所有在跑的序列進同一個 kernel，各自帶著自己的 temperature 和門檻。

在 SGLang 裡

同樣的旋鈕、同樣的順序，只是走 HTTP：

curl localhost:30000/generate -d '{
  "text": "...",
  "sampling_params": {"temperature": 0.8, "top_k": 50, "top_p": 0.95,
                      "min_p": 0.0, "repetition_penalty": 1.1,
                      "frequency_penalty": 0.2, "n": 4}}'

這一邊值得看的是 kernel。--sampling-backend pytorch 是參考實作，會真的排序；--sampling-backend flashinfer 用的是融合過的 top-k/top-p kernel，底下就是上面那個門檻搜尋。同一個分佈、不同的成本——而且因為 decode 每一步都要取樣，這個差別會直接進到 ITL（token 之間的延遲），不是出現在某張 benchmark 上而已。

SGLang 另外開了 custom logit processor 這個掛鉤，而它比聽起來有意思。本文每一條規則本質上都是同一個動作：在 softmax 之前把某些 logit 設成 −inf。把判斷式從「機率太小」換成「這個 token 會讓 JSON 不合法」，那就是 structured output；換成「這個詞被禁用」，那就是內容過濾。同一個掛鉤，不同的條件。

這一天之後會在哪裡再出現

「對一組價值做帶 temperature 的 softmax，用來決定要選最好的還是去試試看比較差的」——這正是多臂拉霸機（multi-armed bandit）裡的 Boltzmann exploration。而 temperature 那張表裡的 entropy 欄位，就是 policy gradient 目標函數裡那個 entropy 項的同一個量，理由也一樣：避免策略塌縮到單一動作，就像 greedy decoding 塌縮到單一句話那樣。

Speculative decoding 要的東西比今天更強：draft 模型一次提好幾個 token，真模型逐個接受或拒絕，而那條接受規則必須讓今天這個分佈完全不變——抽得更快，但不能抽得不一樣。
