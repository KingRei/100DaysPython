100 Days of Python - day 27

Deduplicating a corpus of 10 million documents is 5 × 10¹³ pairs. Even at one microsecond per pair that is over a year of compute, so the interesting question is never "how do I compare two documents faster" - it is "how do I avoid comparing most pairs at all". Today is about both halves: the exact, expensive answer, and the sketch that makes the pair count go away.

The last three days all asked exact questions. A trie answers "is this a prefix", KMP answers "does this pattern occur", a suffix array answers "what repeats verbatim". Real text does not cooperate with any of them. A user types recieve, an ASR model drops a word, two crawled pages differ only by a cookie banner - and every one of those is a near match that an exact structure reports as no match at all.

Levenshtein: three predecessors, and each one is an operation

The exact answer is edit distance: the smallest number of single-character deletions, insertions and substitutions that turns one string into the other. Let d[i][j] be the distance between the prefixes a[:i] and b[:j]. Every path into that cell must have come from one of exactly three places, and each one is a named operation:

d[i][j] = min(d[i-1][j]   + 1,                    # delete a[i-1]
              d[i][j-1]   + 1,                    # insert b[j-1]
              d[i-1][j-1] + (a[i-1] != b[j-1]))   # substitute, or match for free

The first row and column are the base cases - turning a prefix into the empty string costs one deletion per character - and the answer is the bottom-right corner. kitten to sitting fills a 7 × 8 table and comes out at 3.

The number is usually the less useful half

min throws away which predecessor won, and that is the part a user sees. Walk backwards from the corner, re-test the three candidates at each cell, and the table becomes an edit script: substitute k with s, substitute e with i, insert g. A spell checker needs that to explain itself, a diff tool prints it, and an ASR error report is made of nothing else.

If you do not need the script, the table is wasteful. Row i only ever reads row i-1, so two rows suffice:

prev = list(range(m + 1))
for i in range(1, n + 1):
    cur = [i] + [0] * m
    for j in range(1, m + 1):
        cur[j] = min(prev[j] + 1, cur[j-1] + 1, prev[j-1] + (a[i-1] != b[j-1]))
    prev = cur

Memory drops from O(nm) to O(min(n, m)) - swap the arguments so the shorter string indexes the row - and the price is exactly the thing above: with the table gone, there is nothing to walk backwards through. Hirschberg's algorithm buys the script back in linear space by divide-and-conquer, for about twice the time. Pick two of {distance, script, linear space}; the third costs something.

Bounded k: most of the table can never matter

The optimisation that actually changes the constant is not a code change, it is a question change. Spelling correction, fuzzy joins and dedup filters almost never ask "how far apart are these". They ask "are these within k". Once k is fixed, any path that strays more than k cells from the main diagonal has already spent more than k operations, so only the band max(0, i-k) <= j <= min(m, i+k) can hold the answer. Width 2k+1, so the work is O(k · n).

Two guards do most of the work in practice. Length difference is a lower bound on the distance, so abs(n - m) > k is answered before a single cell is filled. And if every cell in a row already exceeds k, no later row can come back under it, so the loop exits early. On a 132-character pair that differs by 3 substitutions, k = 3 fills 912 cells out of 17424 - 5.2% of the table - k = 1 gives up after 152, and a pair whose lengths differ by 5 is rejected with 0 cells filled.

The same recurrence over words, and without substitution

Nothing in that recurrence knows it is comparing characters. Feed it word tokens and the distance becomes word error rate, the standard ASR metric: edit distance divided by the length of the reference, with the backtrace splitting it into substitutions, deletions and insertions. My example scores (2S + 1D + 0I) / 8 = 0.375, and the breakdown is the part an error analysis lives on - a system that mostly deletes has a very different problem from one that mostly substitutes.

Delete one branch and you get a different classic. Forbid substitution, and the cheapest alignment is to keep the longest common subsequence and edit everything else: distance = n + m - 2 · LCS. That is why diff shows a changed line as a deletion plus an insertion rather than as a modification - substitution is not in its vocabulary.

Jaccard: make a document a set, so it can be sketched

Everything so far is O(nm) per pair, and the pair count is the enemy. Scaling needs a similarity that can be indexed, not merely computed quickly.

Cut each document into overlapping k-word shingles and treat it as the set of them. Order inside a shingle is preserved, order between shingles is thrown away, and the document becomes a set - which is the whole point, because sets have cheap fixed-size sketches and strings do not.

J = len(A & B) / len(A | B)

On my corpus, a document with one phrase swapped scores 0.773, one with a clause appended 0.830, an unrelated one 0.000. Still n(n-1)/2 comparisons, though: 8 documents is 28, 10 million is 5 × 10¹³.

MinHash: collisions are the estimate

Hash every element of a set and keep the minimum. For two sets, the smallest hash across A ∪ B lands in A ∩ B with probability exactly |A ∩ B| / |A ∪ B|, and their min-hashes agree in precisely that case - so P(equal) = J, on the nose. Do it with K independent hash functions and the fraction of agreeing slots is an unbiased estimate of the Jaccard, with standard error about sqrt(J(1-J)/K).

A document of any length is now K integers, and a comparison is O(K) no matter how long the documents were. Accuracy improves at the usual quarter-rate: on a pair with true J = 0.773, K = 16 estimates 0.688, K = 64 gives 0.828, K = 256 gives 0.766, K = 1024 gives 0.771 - and the mean error across all pairs falls 0.083 → 0.038 → 0.017 as K goes 16 → 64 → 256.

One trap deserves to be said out loud, because it passes every test on one machine and then breaks in production: Python's built-in hash() on str is randomised per process. Signatures written today will not match signatures computed tomorrow, and nothing that runs in a single process will ever show you that. Use a seeded hashlib hash:

def _hash(item, seed):
    h = hashlib.blake2b(item.encode(), digest_size=8,
                        key=seed.to_bytes(8, 'little'))
    return int.from_bytes(h.digest(), 'little')

LSH: turning "compare all pairs" into "look in a bucket"

MinHash made each comparison O(K), but there are still n(n-1)/2 of them. Locality-sensitive hashing removes the pairs themselves. Split the K slots into b bands of r rows, hash each band, and call two documents candidates if any band matches exactly. A band matches with probability J^r, so

P(candidate) = 1 - (1 - J^r)^b

which is an S-curve whose steep part sits near (1/b)^(1/r). That is the design knob: b = 32, r = 4 puts the threshold near 0.42, b = 16, r = 8 near 0.71, b = 8, r = 16 near 0.88. Choose it just under the similarity you care about and the curve does the filtering for you - the middle setting fires with probability 0.001 at J = 0.3 and 0.947 at J = 0.8.

The point that makes this safe to deploy: LSH is a filter, not an answer. It proposes candidates, and the exact Jaccard is then computed on those few pairs, so a false positive costs a little work and nothing else. On my 8-document corpus the pipeline verifies 4 pairs instead of 28 - 14.3% of the work - and returns exactly what brute force returns. At corpus scale that ratio is the difference between a job that finishes and one that does not, which is why MinHash-LSH is the standard dedup pass behind datasets like C4 and RefinedWeb.

The LeetCode problems

LC 72 (Edit Distance) is the table, unchanged. The interview value is in naming the three predecessors as operations, then offering the rolling-row version and saying out loud what it loses.

LC 1143 (Longest Common Subsequence) is the same table with the substitution branch deleted. Solving it right after 72 makes the structure visible: one branch removed, one different algorithm.

LC 161 (One Edit Distance) is the interesting one, because the right answer builds no table at all:

def is_one_edit_distance(s, t):
    if len(s) > len(t):
        s, t = t, s
    if len(t) - len(s) > 1 or s == t:
        return False
    for i in range(len(s)):
        if s[i] != t[i]:
            return s[i+1:] == t[i+1:] if len(s) == len(t) else s[i:] == t[i+1:]
    return len(t) == len(s) + 1

O(n) time, O(1) space. The general algorithm is the wrong tool once k is nailed down to 1 - the bounded-band idea taken to its limit.

Why this matters later

Edit distance is the shape of every alignment problem: sequence alignment in bioinformatics is the same recurrence with a scoring matrix, dynamic time warping is it with a different step set, and beam-search rescoring in ASR is it with a language model bolted on. MinHash and LSH point the other way - toward approximate nearest neighbour search, where embeddings replace shingles, cosine similarity replaces Jaccard, and the same "cheap filter, exact verify" contract shows up in HNSW graphs and IVF/PQ indexes. When a vector database says it is "approximate", this is the trade it is describing.

Both stories also converge on the same engineering discipline: know what your filter's false-negative rate is, and verify the survivors exactly.
