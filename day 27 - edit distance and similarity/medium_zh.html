100 Days of Python - day 27

一千萬份文件要去重，就是 5 × 10¹³ 個 pair。就算一個 pair 只花一微秒，也要跑一年以上。所以真正的問題從來不是「怎麼把兩份文件比得更快」，而是「怎麼讓大部分的 pair 根本不用比」。今天兩件事都要講：精確但昂貴的那個答案，還有讓 pair 數量消失的那個 sketch。

前三天問的都是精確問題。Trie 回答「這是不是某個前綴」，KMP 回答「這個 pattern 有沒有出現」，suffix array 回答「哪一段一字不差地重複了」。但真實的文字不配合：使用者打成 recieve、ASR 模型漏掉一個字、兩個爬下來的網頁只差一條 cookie 橫幅 — 這些全都是接近的匹配，而精確結構會一致回報「不匹配」。

Levenshtein：三個前驅，每一個都是一種操作

精確的答案是編輯距離：把一個字串變成另一個所需的最少單字元刪除、插入、替換次數。令 d[i][j] 是前綴 a[:i] 和 b[:j] 之間的距離，那麼走進這一格的路徑只可能來自三個地方，而每一個都對應一種有名字的操作：

d[i][j] = min(d[i-1][j]   + 1,                    # delete a[i-1]
              d[i][j-1]   + 1,                    # insert b[j-1]
              d[i-1][j-1] + (a[i-1] != b[j-1]))   # substitute, or match for free

第一列和第一行是 base case — 把一個前綴變成空字串，每個字元要刪一次 — 答案在右下角。kitten 到 sitting 填滿一張 7 × 8 的表，結果是 3。

那個數字通常是比較沒用的那一半

min 把「是哪個前驅贏的」丟掉了，而那正是使用者會看到的部分。從右下角往回走，每一格重新測那三個候選，這張表就變成一份編輯腳本：把 k 換成 s、把 e 換成 i、插入 g。拼字檢查要靠它才能解釋自己在做什麼，diff 工具印的就是它，ASR 的錯誤分析報告更是整份都由它組成。

如果不需要腳本，整張表就是浪費。第 i 列只會讀第 i-1 列，所以兩列就夠了：

prev = list(range(m + 1))
for i in range(1, n + 1):
    cur = [i] + [0] * m
    for j in range(1, m + 1):
        cur[j] = min(prev[j] + 1, cur[j-1] + 1, prev[j-1] + (a[i-1] != b[j-1]))
    prev = cur

記憶體從 O(nm) 掉到 O(min(n, m))（把兩個參數交換一下，讓比較短的字串當列的索引），代價就是上面那件事：表沒了，就沒有東西可以往回走。Hirschberg 演算法用分治法把腳本在線性空間裡買回來，代價是大約兩倍的時間。{距離、腳本、線性空間} 這三樣，你挑兩樣，第三樣要付錢。

有上界 k 時，大部分的表格根本不可能有答案

真正會改變常數的優化不是改程式，是改問題。拼字修正、fuzzy join、去重過濾器幾乎從來不問「這兩個差多遠」，它們問的是「這兩個是不是在 k 以內」。k 一旦固定，任何偏離主對角線超過 k 格的路徑就已經花掉超過 k 次操作了，所以只有 max(0, i-k) <= j <= min(m, i+k) 這條帶狀區域可能裝著答案。寬度 2k+1，工作量是 O(k · n)。

實務上出力最多的是兩個守門條件。長度差是距離的下界，所以 abs(n - m) > k 連一格都不用填就能回答；而如果某一列的每一格都已經超過 k，後面的列不可能再降回來，迴圈可以直接早退。在一對相差 3 個替換的 132 字元字串上，k = 3 只填了 17424 格裡的 912 格（5.2%），k = 1 填到 152 格就放棄，長度差 5 的那一對則是 0 格。

同一個遞迴式，換成字詞；再拿掉替換

這個遞迴式並不知道自己在比字元。餵它 word token，距離就變成 word error rate，ASR 的標準指標：編輯距離除以 reference 的長度，而 backtrace 會把它拆成替換、刪除、插入三種。我的例子是 (2S + 1D + 0I) / 8 = 0.375，而那份拆解才是錯誤分析真正在看的東西 — 一個大量刪字的系統，跟一個大量替換的系統，問題完全不一樣。

拿掉一個分支就變成另一個經典題。不准替換的話，最省的對齊方式就是保留最長共同子序列、其他全部編輯掉：distance = n + m - 2 · LCS。這就是為什麼 diff 把一行的修改顯示成一次刪除加一次新增，而不是「修改」— 替換根本不在它的字彙裡。

Jaccard：把文件變成集合，才能做 sketch

到目前為止全都是每一對 O(nm)，而 pair 的數量才是敵人。要 scale，需要的是可以被索引的相似度，不只是算得快的相似度。

把每份文件切成重疊的 k 字 shingle，然後把它當成這些 shingle 的集合。shingle 內部的順序保留了，shingle 之間的順序丟掉了，文件變成一個集合 — 而這正是重點，因為集合有便宜的固定大小 sketch，字串沒有。

J = len(A & B) / len(A | B)

在我的語料上，換掉一個片語的文件是 0.773，多接一個子句的是 0.830，完全無關的是 0.000。不過還是 n(n-1)/2 次比較：8 份文件是 28 次，一千萬份是 5 × 10¹³ 次。

MinHash：碰撞本身就是估計值

把集合裡每個元素都 hash 過，只留最小值。對兩個集合來說，A ∪ B 裡最小的那個 hash 值落在 A ∩ B 裡的機率剛好是 |A ∩ B| / |A ∪ B|，而兩邊的 min-hash 相等也正好是在這種情況 — 所以 P(equal) = J，不多不少。用 K 個獨立的 hash function 做 K 次，相同 slot 的比例就是 Jaccard 的無偏估計，標準誤大約是 sqrt(J(1-J)/K)。

於是不管文件多長，它現在就是 K 個整數，比較是 O(K)。精度照老規矩四倍換一半：真值 J = 0.773 的那一對，K = 16 估 0.688、K = 64 估 0.828、K = 256 估 0.766、K = 1024 估 0.771；所有 pair 的平均誤差則隨 K 從 16 → 64 → 256 而 0.083 → 0.038 → 0.017。

有個坑一定要講明白，因為它在單一台機器上會通過所有測試，然後在 production 爆掉：Python 內建的 hash() 對 str 是每個 process 隨機化的。今天寫進資料庫的簽章，明天算出來的對不上，而任何跑在單一 process 裡的測試都不會告訴你。用有 seed 的 hashlib：

def _hash(item, seed):
    h = hashlib.blake2b(item.encode(), digest_size=8,
                        key=seed.to_bytes(8, 'little'))
    return int.from_bytes(h.digest(), 'little')

LSH：把「比對所有 pair」變成「看同一個桶子」

MinHash 把每次比較變成 O(K)，但還是有 n(n-1)/2 次。Locality-sensitive hashing 直接把 pair 本身拿掉：把 K 個 slot 切成 b 個 band、每個 band r 列，每個 band 各自 hash，只要任何一個 band 完全相同就把這兩份文件列為候選。一個 band 相同的機率是 J^r，所以

P(candidate) = 1 - (1 - J^r)^b

這是一條 S 曲線，陡峭處大約落在 (1/b)^(1/r)。這就是設計旋鈕：b = 32, r = 4 門檻大約 0.42，b = 16, r = 8 大約 0.71，b = 8, r = 16 大約 0.88。把它調到你在意的相似度稍微下面一點，曲線就會幫你過濾 — 中間那組在 J = 0.3 只有 0.001 的機率被撈出來，在 J = 0.8 則是 0.947。

而讓這整套敢上線的關鍵是：LSH 是過濾器，不是答案。它只負責提名候選，接著在那少數幾對上算精確的 Jaccard，所以 false positive 只會多花一點點工，不會算錯。在我那個 8 份文件的語料上，整條 pipeline 只驗證 4 對而不是 28 對（14.3% 的工作量），結果跟暴力法完全一樣。放大到語料規模，這個比例就是「這個工作跑得完」跟「跑不完」的差別 — 這也是為什麼 MinHash-LSH 是 C4、RefinedWeb 這類資料集標準的去重步驟。

LC 161（One Edit Distance）才是有趣的那題，因為正確答案根本不建表：

def is_one_edit_distance(s, t):
    if len(s) > len(t):
        s, t = t, s
    if len(t) - len(s) > 1 or s == t:
        return False
    for i in range(len(s)):
        if s[i] != t[i]:
            return s[i+1:] == t[i+1:] if len(s) == len(t) else s[i:] == t[i+1:]
    return len(t) == len(s) + 1

O(n) 時間、O(1) 空間。k 一旦被釘死成 1，通用演算法就是錯的工具 — 這就是有上界的帶狀 DP 推到極限的樣子。

這些之後會用在哪

編輯距離是所有 alignment 問題的形狀：生物資訊的序列比對就是同一個遞迴式配一張 scoring matrix，dynamic time warping 是換一組 step，ASR 的 beam search rescoring 是再掛上一個語言模型。MinHash 和 LSH 則指向另一邊 — approximate nearest neighbour 檢索：embedding 取代 shingle、cosine 相似度取代 Jaccard，而「便宜過濾、精確驗證」這份同樣的合約會再出現在 HNSW 圖和 IVF/PQ 索引裡。向量資料庫說自己是「近似」的時候，講的就是這個 trade。

兩條線最後也收在同一個工程紀律上：知道你的過濾器漏掉多少（false negative），然後把活下來的那些精確驗證一次。

LeetCode 72 - Edit Distance（編輯距離）

題目。 給兩個單字，回傳把第一個變成第二個所需的最少操作次數。可用的操作有三種，每種算一次： 插入一個字元、刪除一個字元、替換一個字元。

輸入／輸出。 輸入兩個字串，輸出一個整數。

範例。 word1 = "horse"、word2 = "ros" → 3：horse -> rorse（把 h 換成 r）、 rorse -> rose（刪掉 r）、rose -> ros（刪掉 e）。

限制。 0 <= len(word1), len(word2) <= 500，小寫英文字母。500 x 500 的表也才二十五萬格， 所以有趣的不是速度，而是你能不能只用 O(min(m, n)) 的空間做完。

leetcode.com/problems/edit-distance

LeetCode 161 - One Edit Distance（相隔為 1 的編輯距離）

題目。 若兩個字串剛好差一次編輯（插入一個、刪除一個或替換一個字元），回傳 True。 完全相同的兩個字串差零次，所以要回傳 False。

輸入／輸出。 輸入兩個字串，輸出布林值。

範例。 s = "ab"、t = "acb" → True（插入 c）；s = ""、t = "" → False； s = "abc"、t = "abc" → False。

限制。 0 <= len(s), len(t) <= 10^4。長度差超過 1 就直接 False，剩下的只要掃一遍 —— 這題正好說明：當你只需要一個「有沒有超過固定門檻」的是非題時，*不必*把整張編輯距離表算出來。

leetcode.com/problems/one-edit-distance

LeetCode 1143 - Longest Common Subsequence（最長共同子序列）

題目。 回傳兩個字串的最長共同子序列長度。子序列保持原來的順序但可以跳過字元，不需要連續； 如果沒有任何共同子序列，答案是 0。

輸入／輸出。 輸入兩個字串，輸出一個整數。

範例。 text1 = "abcde"、text2 = "ace" → 3，子序列是 "ace"；text1 = "abc"、 text2 = "def" → 0。

限制。 1 <= len(text1), len(text2) <= 1000，小寫英文字母。它和編輯距離是同一張 O(m * n) 的表、只是遞迴式不同 —— 這也正是這兩題該放在同一天的原因。
