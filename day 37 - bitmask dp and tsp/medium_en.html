Bitmask DP and Held-Karp: indexing a DP table by a set of visited cities

Code: day 37 on GitHub

100 Days of Python - day 37

I once wrote a route optimiser that returned a number about 25% below anything the drivers could actually achieve. It did not crash, it did not warn, and the number was stable across runs. It took me two days to work out that my DP state was missing one field, and that what I had written was a perfectly correct algorithm - for a different problem.

That bug is today's subject.

From Day 33 to Day 36 the index of the DP table kept changing shape: a prefix length, a remaining capacity, an interval, a subtree. Today it becomes a set. A set of up to about twenty elements fits in one machine integer, one bit per element, which means it can be used directly as an array index. Once a subproblem can be keyed by "which things are already done", a family of problems that look hopelessly permutational turns into a table fill.

A set is an integer

Five operations carry the whole day:

def has(mask, i):    return (mask >> i) & 1
def add(mask, i):    return mask | (1 << i)
def remove(mask, i): return mask & ~(1 << i)
def members(mask):   return [i for i in range(mask.bit_length()) if mask >> i & 1]
def popcount(mask):  return bin(mask).count('1')

Two precedence notes, because both are worth saying out loud. In C, mask & 1 == 0 parses as mask & (1 == 0) and is a classic bug; in Python & binds tighter than ==, so the expression means what it looks like. And ~mask in Python is negative - ~0b0101 is -6 - which is fine as a value but treacherous as an index into a list, because dp[~mask] quietly reads from the other end. For a table of exactly 2**n entries, the complement you want is mask ^ full.

Enumerating every subset of a mask is a two-line idiom that looks like a typo:

sub = mask
while True:
    yield sub
    if sub == 0:
        break
    sub = (sub - 1) & mask

Subtracting one borrows through the low zero bits; the & mask throws away the borrowed bits that do not belong to the set. Written as while sub: instead of the do-while above, it skips the empty subset - which is exactly the subset that usually carries the base case.

And the total work of "for every mask, for every submask" is not 4^n. Every element is either in the submask, in the mask but not the submask, or outside, so the sum is 3^n: 59,049 for n = 10, not 1,048,576.

This time the fill order is free

Day 36's entire difficulty was the order the table was filled in: an interval DP has to go by increasing length, and the instinctive for i: for j: loops read cells that have not been written yet. Bitmask DP hands you that for free. mask | (1 << nxt) is always numerically larger than mask, because nxt was not in mask, so a plain for mask in range(1 << n) can never read an unfilled cell, whatever the transition happens to be.

Which means all of today's difficulty sits somewhere else: in the state.

Held-Karp

The instance is eight stops in Taiwan - Taipei, Hsinchu, Taichung, Sun Moon Lake, Tainan, Kaohsiung, Taitung, Hualien - and one closed tour through all of them. There are 5,040 orderings. Brute force checks them all and reports 689 km.

Held-Karp keys the table on a pair: which cities have been visited, and which one I am standing on.

dp[1 << 0][0] = 0
for mask in range(1 << n):
    for last in members(mask):
        if dp[mask][last] == INF:
            continue
        for nxt in range(n):
            if has(mask, nxt):
                continue
            nm = add(mask, nxt)
            cand = dp[mask][last] + D[last][nxt]
            if cand < dp[nm][nxt]:
                dp[nm][nxt] = cand
                parent[nm][nxt] = last
best = min(dp[full][last] + D[last][0] for last in range(1, n))

The last field is the entire point. Two prefixes that have covered the same set of cities and finish in the same city are interchangeable for everything that comes after, so only the cheaper one needs to survive. Twenty-four prefixes of length four over five cities collapse into twelve states; in general (n-1)! orderings collapse into 2^n · n states.

parent is what turns a number back into an itinerary. Nothing in the recurrence needs it, which is why it is so often left out and so painful to add back later.

The bug that cost me two days

Suppose the state is only dp[mask]. The recurrence still compiles, still terminates, still returns a number. But without knowing where the previous prefix ended, the only cost you can write for the next hop is the distance to the nearest already visited city:

hop = min(D[i][nxt] for i in members(mask))
dp[mask | 1 << nxt] = min(dp[mask | 1 << nxt], dp[mask] + hop)

That is not a broken recurrence. It is a correct recurrence for a different problem: it attaches each new city to whichever visited city is closest, and what that grows is a tree, not a tour. Nobody ever comes home.

For the eight-city instance it returns 502 km. The minimum spanning tree of the same instance also weighs 502 km - because that is precisely what has been computed. A classic TSP lower bound: always below the true optimum of 689, always plausible, never flagged.

The other way to be wrong

Skip the DP entirely and hop to the closest unvisited city every time. Nearest neighbour runs in O(n²), produces a genuine closed tour, and returns 795 km - 15.4% over the optimum, and it looks like a reasonable itinerary.

The damage is done at one step. Standing at Sun Moon Lake, the closest unvisited city is Hualien at 74 km, nearer than Tainan at 116 km. Taking it strands the whole south - Tainan, Kaohsiung, Taitung - to be collected later, and that detour costs far more than the 42 km just saved. Greedy cannot see it, because its state has no record of what is left.

The two failures bracket the right answer, which is why they are worth remembering as a pair: the tree is always below the optimum, the greedy tour always above it, and neither raises anything. "It ran" is not evidence that a TSP implementation is correct.

Complexity, and where the wall moves to

2^n · n² is still exponential. Held-Karp does not make the TSP tractable; it moves the wall. Measured in this module, brute force takes 8.6 ms at n = 8, 98.8 ms at 9, 890 ms at 10. Held-Karp takes 1.2 ms at 8 and 614 ms at 15 - where brute force would need roughly 42 hours.

Past roughly twenty cities the table stops fitting in memory and the answer has to come from elsewhere: a heuristic that gives up on optimality, such as a genetic algorithm or simulated annealing, or a branch-and-bound solver that prunes with the very lower bound the broken recurrence above accidentally computes.

LeetCode 847 - Shortest Path Visiting All Nodes

The task. Given a connected undirected graph, find the length of the shortest walk that visits every node at least once. The walk may start anywhere, end anywhere, and revisit nodes and edges as often as it likes.

Input / output. graph is an adjacency list: graph[i] lists the neighbours of node i. Return the number of edges in the shortest such walk.

Example. For graph = [[1,2,3],[0],[0],[0]] the answer is 4. Node 0 is a hub joined to three leaves, so a walk like 1 - 0 - 2 - 0 - 3 uses four edges, and the hub has to be passed through twice.

Constraints. n is at most 12, which is the whole hint: 2^12 · 12 states is small, 12! is not. Revisiting is allowed, so this is not a Hamiltonian path problem, and every step costs exactly one edge.

Because every edge costs the same, this is a BFS rather than a table fill - but the state is exactly today's: (mask of visited nodes, current node). Seed the queue with (1 << i, i) for every i, since any node may be the start, and stop the first time mask is full. The one thing to get right is that "seen" is per (mask, node) pair, not per node. Marking per node is what makes an implementation overshoot on graphs that require walking back through a hub.

LeetCode 943 - Find the Shortest Superstring

The task. Arrange all of the given strings into one string that contains each of them as a substring, as short as possible. Any one of the shortest answers is accepted.

Input / output. words is a list of strings; return a single string.

Example. For words = ["catg","ctaagt","gcta","ttca","atgcatc"] one shortest answer is gctaagttcatgcatc, 16 characters. The five inputs total 25 characters, and the order gcta, ctaagt, ttca, catg, atgcatc overlaps away 9 of them.

Constraints. At most 12 words, each at most 20 characters, and no word is a substring of another - that last clause is what makes "concatenate in some order" the entire search space, and 12 is the bitmask hint again.

This is the TSP with two substitutions: distance becomes overlap, min becomes max. Precompute ov[a][b], the number of characters of b's head that a's tail already supplies, then run the same dp[mask][last] fill maximising total overlap. Minimising the final length and maximising the overlap are the same objective, because the sum of the input lengths is constant.

The trap is the seeding, and it is the exact mirror of the TSP's. In a closed tour any city may be called the start, so seeding only dp[1][0] costs nothing. Here the answer is an open chain and the first word is a real decision. Seed one start and you still get a valid superstring - on this input catgcatcgctaagttca, 18 characters instead of 16. Longer, legal, and easy to miss on small test cases.

LeetCode 526 - Beautiful Arrangement

The task. Count the permutations of 1..n in which every element is compatible with its position: for each 1-based position i, either the number placed there divides i, or i divides the number.

Input / output. An integer n; return the count.

Example. For n = 2 the answer is 2. [1,2] works because 1 divides 1 and 2 divides 2; [2,1] works because 2 is divisible by position 1 and 1 divides position 2.

Constraints. 1 <= n <= 15. Fifteen factorial is 1.3 trillion; 2^15 · 15 is about half a million.

Here the state is only the mask - and that is the interesting part. popcount(mask) already tells you which position is being filled, so a second field would be redundant: dp[mask] = sum(dp[mask without i]) over every i compatible with position popcount(mask). Which is precisely why the missing last in the TSP is so easy to overlook. Sometimes the extra field really is recoverable from the mask. The question to ask every time is not "does this state look small enough" but "can the cost of the next step be written using only what the state remembers".

Why this matters later

The same (mask, last) table reappears wherever a small set has to be ordered: assignment problems, bitonic tours, register allocation over a handful of live values. And the two wrong answers from today have a long afterlife - the spanning-tree bound is what branch-and-bound TSP solvers prune with, and nearest neighbour is the standard way to seed a heuristic search, which then spends its time repairing exactly the mistake we watched it make at Sun Moon Lake.
