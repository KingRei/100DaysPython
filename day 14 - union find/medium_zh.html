100 Days of Python — day 14

昨天的拓樸排序需要先拿到整張圖。今天這個結構幾乎什麼都不需要：它不存邊、不走路徑， 只回答一個問題——這兩個東西是不是同一組？——而且回答的時間幾乎是常數。

聽起來窄到沒什麼用，但你會發現這常常是你唯一想問的問題。這兩個帳號是不是同一個人？ 那條線斷掉之後還剩幾個獨立網路？加上這條邊會不會形成環？哪些像素屬於同一個色塊？

那片森林其實就是一個陣列

Union-Find（也叫 disjoint set union，DSU、併查集）把 0 .. n-1 分成好幾組。 每一組是一棵樹，每個元素只存自己的 parent，而樹根存自己。樹根就是這個集合的 id： 兩個元素同組，等價於它們往上爬會爬到同一個根。

上面的圖跟下面那排數字是同一個東西。沒有節點物件、沒有指標、沒有 adjacency list， 就一個整數陣列，其他全是索引上的算術。

parent = [0, 0, 0, 2, 4, 4, 6]

def find(x):
    while parent[x] != x:
        x = parent[x]
    return x

union(x, y) 一樣短：找出兩邊的根，不同就把其中一個指向另一個。

def union(x, y):
    rx, ry = find(x), find(y)
    if rx == ry:
        return False          # 早就同一組了
    parent[ry] = rx
    return True

正確，但很糟。這裡完全沒有人管樹長什麼形狀，而形狀就是效能的全部。

會出什麼事

用最壞的順序合併——union(1, 0)、union(2, 1)、union(3, 2)…… 每一次合併都把整棵舊樹再往下壓一層。n 次 union 之後，你得到的是一條假扮成樹的 linked list， 對最深的那個元素做 find 要走 n 步。你寫出了一個 O(n) 的「是否同組」查詢， 那還不如一開始就用 list 掃一遍。

兩個補丁可以徹底解決，而且各只有三行左右。

按秩合併：高的那棵留在上面

rank[r] 是以 r 為根的那棵樹高度的上界。合併時，把矮的掛到高的下面。

看清楚這買到了什麼：如果兩邊 rank 不同，高的那棵把矮的吞進去，樹高完全沒變—— 矮的那棵剛好塞得進既有的深度裡。只有兩邊 rank 一樣時，結果才會多長一層， 而這種情況最多發生 log₂(n) 次，因為 rank 為 r 的樹至少含有 2^r 個元素。

def union(self, x, y):
    rx, ry = self.find(x), self.find(y)
    if rx == ry:
        return False
    if self.rank[rx] < self.rank[ry]:
        rx, ry = ry, rx                    # taller tree stays on top
    self.parent[ry] = rx
    if self.rank[rx] == self.rank[ry]:
        self.rank[rx] += 1                 # only a tie grows the height
    self.count -= 1
    return True

改成記 size[r]（集合裡的元素個數）效果一樣好，還順便送你「這一組有多大」。 我兩個都留著，因為 size 每次 union 只多一個加法，卻常常被問到。

另外注意那個回傳值。False 代表兩個元素本來就同組，也就是說——這條邊會形成環。 先記著這句話：Kruskal 最小生成樹幾乎就只是把邊排序，然後留下 union 回傳 True 的那些。

路徑壓縮：同一條路不走第二次

find 反正已經從 x 爬到根了。那就再爬一次，把路上每個節點直接改指到根。

def find(self, x):
    root = x
    while self.parent[root] != root:       # 1st pass: locate the root
        root = self.parent[root]
    while self.parent[x] != root:          # 2nd pass: re-point the path
        self.parent[x], x = root, self.parent[x]
    return root

第二趟讓這一次呼叫的成本變兩倍，卻讓之後對這條路徑上任何節點的呼叫都變成一步。 這就是攤還分析的精神：現在多付一點點，換那個昂貴的情況不會發生第二次。

大家第一次都會寫的遞迴版本——self.parent[x] = self.find(self.parent[x])——做的事一樣， 但遞迴深度就是樹高，而這整件事的重點正是：你第一次碰到它時，那棵樹可能是一條鏈。

我把兩個版本都跑過，20,000 個元素、最壞的合併順序：

naive   :  199,990,000 pointer hops for 20,000 finds
rank+pc :       19,999 pointer hops for 20,000 finds

少了一萬倍，代價是六行程式碼。

α(n)，以及為什麼沒人在意它

兩個優化都加上之後，每個操作的攤還成本是 O(α(n))，α 是反 Ackermann 函數。 Ackermann 函數長得太兇殘，導致它的反函數長得慢到難以想像：對所有 n ≤ 2^2^2^2^16， α(n) 都不超過 4——那個數字的位數比宇宙的原子還多。對任何真實存在的輸入來說， Union-Find 就是常數時間；而且這個界是緊的，Tarjan 與 van Leeuwen 在 1984 年證明了。

LeetCode 547 — 省份數量

isConnected[i][j] == 1 代表城市 i 與城市 j 直接相連，而一個省份就是一個連通分量。 把每一對相連的城市 union 起來，最後剩幾個集合就是答案。

def find_circle_num(is_connected):
    n = len(is_connected)
    uf = UnionFind(n)
    for i in range(n):
        for j in range(i + 1, n):        # symmetric -> upper triangle only
            if is_connected[i][j]:
                uf.union(i, j)
    return uf.count

面試時值得替它辯護的是 range(i + 1, n) 這一行。矩陣是對稱的、對角線全是 1， 所以下三角是你已經用過的重複資訊，對角線則在說「城市 i 跟自己相連」。 掃完整個 n² 不算錯，只是做了兩倍的工。

更有意思的是追問：那為什麼不直接 BFS？ 對這一題來說完全沒差，兩個都是 O(n²)， 因為光是讀完矩陣就要 O(n²)。Union-Find 真正贏的場合是邊陸續進來的時候： 走訪每來一條新邊就得整個重跑，Union-Find 只要用 α(n) 把那條邊吸收掉，答案立刻更新。 題目裡出現「online」「串流」「每次查詢後」這種字眼，就是在提示你用它。

看它跑一遍

一步一步的版本放在 repo 裡的 demo.html： 單檔、離線可開，把按秩合併、路徑壓縮、naive 版本建出來的那條鏈，還有 LeetCode 547 都動畫化了，右上角可以切中英文。看著 parent 陣列在森林底下跟著變， 是最快意識到「它們是同一個東西」的方法。

這東西之後會用在哪

Union-Find 是 Kruskal 最小生成樹的引擎：把邊照權重排序，留下每一條 union 成功的邊， 湊滿 n-1 條就停。它也是滲流模擬判斷流體有沒有穿過格子的方法、Hoshen–Kopelman 替影像標連通分量的方法、type checker 統一型別變數的方法，以及編譯器合併等價運算式的方法。

判斷的訣竅是這樣：只要你發現自己每加一條邊就要重跑一次走訪，只為了問「這兩個還連著嗎」， 你要的其實是這個結構。
