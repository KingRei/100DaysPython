LIS and LCS: the longest subsequence you keep, and the table you throw away

Code: day 35 on GitHub

100 Days of Python - day 35

There is an O(n log n) algorithm for the longest increasing subsequence, it is nine lines long, and the array it spends all its time maintaining is not the answer. On [2, 6, 8, 3, 4, 5, 1] it finishes holding [1, 3, 4, 5] — a correct length of 4, and a list that is not a subsequence of the input at all, because 1 is the last element of the array. That is today's trap, and it is the good kind: it never fires on the textbook example.

Yesterday's knapsack ended on a table you fill and then walk back up to recover which items were taken. Today is the same shape with a sharper edge. LIS has a fast algorithm whose working array must not be trusted, and LCS has a table whose only purpose is to be thrown away.

First, the word. A subsequence is not a substring. [2, 3, 7, 18] is a subsequence of [10, 9, 2, 5, 3, 7, 101, 18] even though the four numbers are scattered across it: order is preserved, adjacency is not required. That single relaxation is what makes diff, ROUGE-L and DNA alignment possible, and it is also what makes both of today's problems harder than they look.

LIS the obvious way

Let dp[i] be the length of the longest increasing subsequence ending at i. That phrasing is the whole design decision. The natural one — "the LIS of the first i elements" — is not enough state, because to decide whether the next element can be appended you need to know what the subsequence currently ends with, and that phrasing has thrown it away.

def lis_dp(a):
    n = len(a)
    dp = [1] * n
    parent = [-1] * n
    for i in range(n):
        for j in range(i):
            if a[j] < a[i] and dp[j] + 1 > dp[i]:
                dp[i] = dp[j] + 1
                parent[i] = j
    best = max(range(n), key=lambda i: dp[i])
    out = []
    while best != -1:
        out.append(a[best])
        best = parent[best]
    out.reverse()
    return max(dp), out

O(n²), and because parent remembers the predecessor at the moment it was chosen, reconstructing the actual subsequence is free: (4, [2, 5, 7, 101]).

Patience sorting

Deal the numbers as a game of patience. Each card goes on the leftmost pile whose top card is greater than or equal to it; if there is no such pile, it starts a new one on the right. When the deck runs out, the number of piles is the length of the LIS. The pile tops are sorted by construction, so finding the pile is a binary search — the lower_bound from day 23:

from bisect import bisect_left

def lis_patience(a):
    tails = []
    for x in a:
        k = bisect_left(tails, x)
        if k == len(tails):
            tails.append(x)        # x extends the longest run so far
        else:
            tails[k] = x           # x is a cheaper ending for length k+1
    return len(tails), tails

Nine lines and O(n log n). The invariant is the thing to remember: tails[k] is the smallest value that can end an increasing run of length k + 1 among everything seen so far. Overwriting can never lose anything, because a smaller ending is at least as extensible as a larger one, and the length it stands for does not change.

The array that lies

On the textbook input [10, 9, 2, 5, 3, 7, 101, 18], tails finishes as [2, 3, 7, 18], which really is a valid LIS. Every tutorial that stops there teaches the wrong lesson. Run the same function on [2, 6, 8, 3, 4, 5, 1]:

tails = [1, 3, 4, 5]        the real LIS = [2, 3, 4, 5]

1 is the final element of the input, so [1, 3, 4, 5] cannot be a subsequence of it. tails is a scoreboard, not a route: the length is always right, the contents usually are not. If you need the subsequence itself, record where each value landed and who preceded it:

def lis_patience_reconstruct(a):
    tails, idx, parent = [], [], [-1] * len(a)
    for i, x in enumerate(a):
        k = bisect_left(tails, x)
        if k:
            parent[i] = idx[k - 1]
        if k == len(tails):
            tails.append(x); idx.append(i)
        else:
            tails[k] = x; idx[k] = i
    out, i = [], idx[-1]
    while i != -1:
        out.append(i); i = parent[i]
    out.reverse()
    return len(tails), out, [a[i] for i in out]

parent[i] is frozen at insertion time, so it points at whoever ended a length-k run at that moment — the predecessor that was genuinely valid then, even if tails[k-1] gets overwritten by something smaller five steps later. The scoreboard keeps changing; the history does not.

One function name is the whole difference

find = bisect_left if strict else bisect_right

bisect_left places an incoming value on the pile whose top equals it, so equal values cannot chain, and you get a strictly increasing subsequence. bisect_right puts it on the next pile, so they can, and you get a non-decreasing one. On [1, 3, 3, 3, 5] that is 3 versus 5. "Increasing" is ambiguous in English and precise in code — ask which one the problem means before typing anything.

LeetCode 300 - Longest Increasing Subsequence

The task. Given an integer array, return the length of its longest strictly increasing subsequence.

Input / output. Input is nums; output is one integer.

Example. nums = [10,9,2,5,3,7,101,18] → 4, from [2,3,7,101] (or [2,3,7,18]). nums = [0,1,0,3,2,3] → 4. nums = [7,7,7,7,7] → 1, because strictly increasing rules out repeats.

Constraints. 1 <= len(nums) <= 2500, -10^4 <= nums[i] <= 10^4. At 2500 the O(n²) DP passes comfortably, which is precisely why the follow-up — "can you do it in O(n log n)?" — is where the interview actually happens.

leetcode.com/problems/longest-increasing-subsequence

Since only the length is asked for, the scoreboard is enough:

def length_of_lis(nums):
    tails = []
    for x in nums:
        k = bisect_left(tails, x)
        if k == len(tails):
            tails.append(x)
        else:
            tails[k] = x
    return len(tails)

The sort key that is secretly the algorithm

LeetCode 354 - Russian Doll Envelopes

The task. Each envelope is a [width, height] pair. One envelope fits inside another only if both its width and its height are strictly smaller. Return the largest number of envelopes that can be nested one inside the next.

Input / output. Input is envelopes; output is one integer.

Example. envelopes = [[5,4],[6,4],[6,7],[2,3]] → 3, nesting [2,3] → [5,4] → [6,7]. envelopes = [[1,1],[1,1],[1,1]] → 1: equal widths are not strictly smaller, so nothing nests.

Constraints. 1 <= len(envelopes) <= 10^5, 1 <= w, h <= 10^5. The 10^5 is the entire hint: a pairwise O(n²) check is 10^10 operations and will not finish, so the intended solution has to be the O(n log n) LIS.

leetcode.com/problems/russian-doll-envelopes

Sort by width, and the second dimension becomes a plain LIS on heights. Except that equal widths must not be allowed to chain — and that is handled entirely inside the sort key:

def max_envelopes(envelopes):
    envelopes.sort(key=lambda e: (e[0], -e[1]))      # width asc, height DESC
    return length_of_lis([h for _, h in envelopes])

Sorting heights descending within the same width turns them into a decreasing run, and a decreasing run can contribute at most one element to an increasing subsequence. Delete the minus sign and [[1,1],[1,2],[1,3]] returns 3 — three envelopes of identical width, supposedly nested inside each other. No exception, no warning. This is the whole problem, and it lives in one character of a lambda.

LeetCode 673 - Number of Longest Increasing Subsequence

The task. Given an integer array, return how many distinct longest strictly increasing subsequences it has. Two subsequences are different if they use different positions.

Input / output. Input is nums; output is one integer count.

Example. nums = [1,3,5,4,7] → 2: the LIS length is 4, reached by [1,3,5,7] and [1,3,4,7]. nums = [2,2,2,2,2] → 5: the LIS length is 1 and each of the five positions is its own subsequence.

Constraints. 1 <= len(nums) <= 2000, -10^6 <= nums[i] <= 10^6, and the answer fits in a 32-bit integer. That 2000 matters: it permits the O(n²) DP, which you need here, because the patience version has nowhere to keep the counts.

leetcode.com/problems/number-of-longest-increasing-subsequence

Carry a second array alongside dp:

def count_lis(a):
    n = len(a)
    dp, cnt = [1] * n, [1] * n
    for i in range(n):
        for j in range(i):
            if a[j] < a[i]:
                if dp[j] + 1 > dp[i]:
                    dp[i] = dp[j] + 1
                    cnt[i] = cnt[j]          # a longer route: replace
                elif dp[j] + 1 == dp[i]:
                    cnt[i] += cnt[j]         # an equally long route: add
    best = max(dp)
    return sum(c for d, c in zip(dp, cnt) if d == best)

= when the length improves, += when it ties. Swapping those two lines is the standard way to fail this problem, and both versions return a perfectly plausible integer.

LCS: the table, and the path

The longest common subsequence gets none of this. dp[i][j] is the LCS length of x[:i] and y[:j]; a matching pair of characters extends the diagonal, and otherwise the better of dropping one character from either side wins:

def lcs_table(x, y):
    dp = [[0] * (len(y) + 1) for _ in range(len(x) + 1)]
    for i in range(1, len(x) + 1):
        for j in range(1, len(y) + 1):
            if x[i - 1] == y[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1
            else:
                dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])
    return dp

AGGTAB against GXTXAYB gives 4, and walking back from the bottom-right corner — diagonally on a match, otherwise towards the larger neighbour — spells GTAB.

Row i only ever reads row i - 1, so two rows are enough for the number. And exactly as with yesterday's rolling knapsack, the rolling version cannot reconstruct the path: the cells the backtrack would have walked through no longer exist. Number or path, pick one. (Or use Hirschberg's algorithm, which gets the path back in linear space by running the DP twice per recursive split — a good trick, and a much longer one.)

LeetCode 1035 - Uncrossed Lines

The task. Two rows of integers are written down, one above the other. Draw straight connecting lines between equal numbers, one from each row, such that no two lines cross and no number is used twice. Return the maximum number of lines.

Input / output. Input is nums1 and nums2; output is one integer.

Example. nums1 = [1,4,2], nums2 = [1,2,4] → 2: connect the two 1s, then either the 4s or the 2s, but not both, since those two lines would cross. nums1 = [2,5,1,2,5], nums2 = [10,5,2,1,5,2] → 3.

Constraints. 1 <= len(nums1), len(nums2) <= 500, 1 <= nums[i] <= 2000. The 500 × 500 is the point — exactly the size the O(n·m) table wants.

leetcode.com/problems/uncrossed-lines

"No lines cross" means the matched positions increase in both rows, which is the definition of a common subsequence. It is LCS with the vocabulary changed, and the skill being tested is noticing that instead of deriving a fresh recurrence under time pressure.

When LCS is secretly LIS

Here is the connection that makes today one article instead of two. If both sequences are permutations of the same set — all elements distinct, both drawn from the same alphabet — the table is unnecessary. Replace each element of q by its index in p. A common subsequence is then a set of positions that increase in p and appear in order in q, which is exactly an increasing subsequence of the mapped array:

def lcs_of_permutations(p, q):
    pos = {v: i for i, v in enumerate(p)}
    mapped = [pos[v] for v in q if v in pos]
    length, seq, _ = lis_patience_reconstruct(mapped)
    return length, [p[i] for i in seq]

p = [1,2,3,4,5,6] and q = [2,4,1,5,6,3] map to [1,3,0,4,5,2], whose LIS [1,3,4,5] reads back as [2,4,5,6]. On two random permutations of size 1200, the O(n·m) table takes 1.300 s and this takes 0.0018 s for the same answer of 67 — about 700x, from the same O(n²) → O(n log n) jump, now applied to a problem that looked like it had nothing to do with LIS.

That is the core of the Hunt-Szymanski algorithm, and it is why diff is fast on real files: source lines are mostly unique, so the input is close enough to a permutation for this to bite.

What it is actually for

LCS is the engine inside diff. The common subsequence is the set of unchanged lines; everything not in it is a deletion or an insertion.

     def f(x):
   -     y = x + 1
   +     # bump
   +     y = x + 2
         return y

git diff, patch, every code review tool and every merge-conflict detector rests on that. ROUGE-L, the standard summarisation metric, is the F-measure of the LCS length between a candidate and a reference — it rewards the right words in the right order without demanding adjacency, which is why "the cat sat on the mat" scores 0.769 against "the cat was sitting on the mat". Needleman-Wunsch in bioinformatics is the same table with a scoring matrix in place of the +1. And LIS shows up as the fast path for patience-sorting-based diffs, and in scheduling as the longest chain in a partial order.

Why this matters later

The reflex worth keeping from today is not either algorithm. It is the question "is this working array the answer, or just a summary of it?" — because tails is the cleanest example of a data structure that carries the right number and the wrong contents, and the parent pointers are the price of getting the contents back. Interval DP and tree DP have exactly the same split between a value and a reconstruction, and so does every Viterbi decode and beam search you will ever write.
