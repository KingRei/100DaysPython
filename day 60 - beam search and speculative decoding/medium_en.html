Beam search and speculative decoding: finding a better sentence, and getting the same one faster

Code: day 60 on GitHub

100 Days of Python - day 60

The previous day ended on a number I have not stopped thinking about. Greedy decoding - take the highest-probability character at every step - produces the 44th most likely sentence out of the 1,250 the grammar admits. Every step is optimal and the result is not. No temperature, top-k or top-p setting fixes that, because it is not a sampling problem.

Today is two answers to it, pulling in opposite directions. Beam search changes the output to find a more probable sentence, and costs more. Speculative decoding changes nothing at all about the output and costs less. Both get checked against the enumeration, so neither gets to be plausible instead of correct.

The ground truth

The grammar is small enough to enumerate: 1,250 sentences, each scored exactly by summing its per-step log probabilities.

most likely    'a small dog sat in the garden.'    log p = -6.244
greedy gives   'the red cat sang in the garden.'   log p = -6.717,  rank 44
least likely   'a cat slept on the mat.'           log p = -9.173

Greedy walks into a prefix from which no very good ending exists and cannot go back. Worth noticing the scale too: best to worst spans 2.9 log units, about 18x in probability, and greedy sits 0.47 below the top. There is a ceiling on what search can buy here, and everything below is climbing inside it.

Beam search

Instead of keeping one prefix alive, keep width of them. At every step expand all of them, score all the candidates, keep the best width again.

width       rank found  log p
----------  ----------  ------
1 (greedy)  44          -6.717
2           44          -6.717
4           10          -6.502
8, 16, 32   5           -6.407

Two things in that table deserve more than a glance.

The first is that width 1 is greedy - which took me a debugging detour to reproduce. This model has exact ties: two characters with identical probability to the last bit. np.argmax returns the first; np.argsort with the default quicksort does not promise to. The sort has to be stable, or the two algorithms disagree for no reason anyone would ever guess from the output.

The second is that it stops at rank 5. Widening further never reaches rank 1, because the best sentence's prefix was pruned early and nothing brings it back. Beam search is a heuristic, not a maximiser - the asserts in the file only check that no beam beats the enumerated optimum, not that it finds it. And the cost is linear in the width: width 8 runs the model on 8 sequences at every step, which is 8 KV caches and 8 times the attention work from the previous days.

Two things beam search gets wrong

Wider is not monotonically better. On a model trained on a smaller corpus, scanning the width one value at a time:

width  1   log p  -6.188
width  2   log p  -6.188
width  3   log p  -6.422   <- worse than the narrower beam
width  4   log p  -6.224

Not an implementation bug. A wider beam keeps more prefixes alive, and a prefix that looks mediocre early can survive long enough to crowd out the one that would have won later. Translation papers call the version of this that shows up in quality scores the beam search curse: past a width of roughly 5 to 10, BLEU falls while model probability keeps rising - which says something uncomfortable about the model, not just the search.

Highest total probability means shortest. Every character multiplies the score by something below 1, so a total-probability search is partly a search for short outputs. Here the effect is mild because every sentence is 21 to 38 characters (the correlation is 0.061), but the direction is visible: the top 10 sentences by total log probability average 28.8 characters, against 36.5 for the top 10 by log probability per character. In translation, where candidates differ by tens of tokens, an uncorrected beam truncates. The standard patch is dividing by length ** alpha, which has a convention behind it and no derivation - which is why papers report the alpha they used as a hyperparameter. It is one.

And asking a beam for n answers gives n neighbours. Its 16 best sentences are all different strings, so counting distinct sentences says nothing. Counting subjects does: those 16 share only 8 distinct determiner-adjective-noun subjects, against 12.8 for 16 sentences sampled from the same model. That is not a flaw to fix. A beam searches for the most probable output, and the most probable outputs resemble each other by construction. Beam search belongs where exactly one answer is correct - translation, speech recognition, constrained extraction - and a chat model needs the previous day's sampling.

Speculative decoding: changing nothing, faster

Decode is slow for a reason that has nothing to do with arithmetic: every step re-reads the entire model from memory to produce one token. So the question is not "how do we compute faster" but "how do we get more tokens out of one pass over the weights".

A cheap draft model proposes gamma tokens, one at a time - fine, it is cheap. Then the expensive model verifies all of them in a single forward pass, because scoring gamma positions is one pass while generating them would have been gamma. Each proposal is accepted with probability min(1, p(x) / q(x)): if the target likes the token at least as much as the draft did, it is always kept; if less, it is kept with probability p/q. The first rejection ends the round, and the rejected token is replaced by a draw from the normalised positive part of p - q. If nothing was rejected, the round emits a free bonus token, because the verification pass already produced the distribution for the next position.

Why that is free rather than usually fine

acc   = minimum(1, p / q)
kept  = q * acc                      # mass that survives the coin flip
rest  = 1 - kept.sum()               # probability of rejecting
resid = maximum(p - q, 0); resid /= resid.sum()
out   = kept + rest * resid          # == p

Measured on three contexts, the maximum difference between out and p is 1e-16. That is floating point, not approximation: the model you deployed is the model that answers, token for token, at any draft quality.

Two shortcuts sound equivalent and are not.

Trusting the draft - "it is a good model, just take its tokens" - moves the distribution by up to 0.367. Obviously wrong once written down.

Dropping the coin flip - accept whenever the target likes the token at least as much as the draft did, reject otherwise - does not look wrong at all, and still moves the distribution by up to 0.043. The randomised accept is what makes the accepted mass come out as min(p, q) at every token, and the residual draw is what puts the remainder back in the right places. Both halves are load-bearing, and getting it wrong raises no exception anywhere. The model just quietly becomes a slightly different model.

The two knobs

How good the draft is:

draft order  accept rate  tokens / round  grammatical
-----------  -----------  --------------  -----------
1            0.173        1.69            93%
2            0.605        3.42            93%
3            0.837        4.35            90%
5            0.929        4.72            88%

Read the last column first: it does not move, and it is not supposed to. The output distribution does not depend on the draft at all, so a terrible draft costs speed and never correctness. That property is what makes speculative decoding something you can turn on by default rather than an accuracy trade to negotiate.

How far ahead to guess:

gamma  accept  measured tokens/round  iid theory  speedup
-----  ------  ---------------------  ----------  -------
1      0.911   1.91                   1.91        1.74x
2      0.910   2.82                   2.74        2.35x
4      0.842   4.37                   3.65        3.12x
8      0.760   7.08                   3.82        3.94x

The theory column is the textbook (1 - a^(gamma+1)) / (1 - a), the expected tokens per round if every proposal were accepted independently with probability a. At gamma=8 the measurement is 7.08 against a predicted 3.82. The formula is not wrong; its assumption is. Acceptances are strongly correlated - the draft is right through a whole predictable stretch (...in the gar|den.) and wrong only at branch points - so long runs of acceptance are far more common than a coin with the same average would give. This is exactly why deployments report accepted length per round rather than an acceptance rate.

In vLLM

Beam search is no longer a sampling parameter. It was moved out of SamplingParams into its own call:

llm.beam_search(prompts, BeamSearchParams(beam_width=4, max_tokens=64))

and the reason is the cost line above: it is a search over sequences that forks and frees w KV caches, not a per-token rule, so it does not belong in the same object as temperature.

Speculative decoding is server configuration:

vllm serve meta-llama/Llama-3.1-70B-Instruct \
  --speculative-config '{"model": "meta-llama/Llama-3.1-8B-Instruct",
                         "num_speculative_tokens": 5}'

# or with no draft model at all:
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 4,
                         "prompt_lookup_max": 4}'

The ngram method is this article's draft model in production, and it runs no network whatsoever: it finds a matching span in the prompt and proposes whatever followed it last time. On summarisation, code editing and RAG - anywhere the answer repeats long spans of the input - it is close to free and works startlingly well. EAGLE and Medusa are the other end of the range: a small head trained on the target model's own hidden states, which buys a much higher acceptance rate without a second full model.

In SGLang

python -m sglang.launch_server --model ... \
    --speculative-algorithm EAGLE3 \
    --speculative-draft-model-path <eagle head> \
    --speculative-num-steps 3 \        # draft depth
    --speculative-eagle-topk 4 \       # branches kept per step
    --speculative-num-draft-tokens 8   # nodes verified per round

The flag worth understanding is --speculative-eagle-topk. It means the draft is a tree, not a chain: several branches per level, all verified in one target pass using an attention mask that lets every node attend only to its own ancestors. The same single expensive forward carries more candidates - the trade above with a better shape. And --speculative-algorithm NEXTN is the same mechanism for models that ship their own extra prediction head, like the MTP layers in DeepSeek-V3 and GLM: the draft is built into the target.

One thing the tables here cannot show. On a real server the number to watch is the accepted length per round against the batch size. Speculation spends compute to save memory bandwidth, so it wins when decode is bandwidth-bound - small batches, long contexts - and can lose at large batch sizes, where the GPU was already saturated and every rejected proposal is compute that bought nothing.

Where this comes back

Beam search over sequences is the same shape as the search problems from the graph days: expand the frontier, score it, prune it, and accept that pruning is where the errors live. And the accept/reject rule in speculative decoding is rejection sampling, which will turn up again whenever an algorithm needs samples from a distribution it can only evaluate pointwise - reinforcement learning is full of them.
