Day 21 — 選擇問題與 Top-K：從來就不需要先排序

程式碼：day 21 on GitHub

100 Days of Python - day 21

LLM 每吐出一個 token，都要跑一次 top-k。模型對十萬多個 vocabulary entry 各給一個分數， 取樣之前得先挑出最好的那幾個。這顆 kernel 執行的次數大概是整個 stack 裡數一數二頻繁的， 所以被優化得很兇。而當我去讀我自己最常用的兩份實作 —— flashinfer 的 topk.cuh 和 SGLang 的 topk_impl.cuh —— 讓我意外的是難的地方跑到哪裡去了：幾乎沒有一點難度在「選擇」本身。 難的是誰負責把一個計數器歸零，以及平手的時候誰贏。

昨天講排序。今天要講的是：排序回答的問題，比我們真正問的大太多了。

排序算出來的東西，遠超過你要的

排序會把所有元素兩兩之間的順序全部算出來。但「給我最大的八個」要的只是一個集合， 連順序都不用，而且是從 200,000 個裡面挑。這中間的差距是可以量的 —— 直接數比較次數：

n = 200,000   k = 8
heap sort the lot       6,439,409 comparisons, and
                          199,992 of the 200,000 results get thrown away
size-k min-heap           200,000 comparisons, 8 floats of memory
quickselect               244,798 comparisons  (n + n/2 + n/4 + ... = 2n)
median-of-medians         653,431 comparisons  (O(n) worst case, and it shows)

四種演算法、同一個答案、26 倍的差距。而且四個算出來的 top-8 完全一致。

要記在腦子裡的是 quickselect。它跟 quick sort 一樣繞著 pivot 做 partition， 但接下來只往一邊遞迴 —— 答案在的那一邊。平均每輪砍掉一半， 所以總量是 n + n/2 + n/4 + … = 2n。一個看起來像平方的演算法，其實是線性的。

def quickselect(a, k):
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        p = a[randint(lo, hi)]        # random pivot
        lt, i, gt = lo, lo, hi
        while i <= gt:                # Dutch national flag
            if a[i] > p:
                swap(lt, i); lt += 1; i += 1
            elif a[i] < p:
                swap(i, gt); gt -= 1  # i does NOT advance
            else:
                i += 1
        if k <= lt - lo:
            hi = lt - 1               # the answer is all in the > side
        elif k <= gt + 1 - lo:
            break                     # the k-th is one of the ties
        else:
            k -= gt + 1 - lo          # drop > and ==, keep hunting
            lo = gt + 1
    return a[:k]

有兩個細節是有價值的。pivot 是隨機挑的 —— 隨機化不是為了變快，是把「最壞情況」 從輸入決定改成骰子決定。另一個是三路 partition，一整排相同的值可以一輪退場， 而不是一輪只處理掉一個。

另外三種各值得一段。大小為 k 的 min-heap 只留目前最好的 k 個， 新元素只跟裡面最小的那個比：O(n log k) 時間、O(k) 記憶體， 而且 —— 這才是重點 —— 它從來不需要一次擁有整份資料。所以四個裡面只有它能跑在串流上。 median-of-medians 用五個一組取中位數的中位數當 pivot，保證切得不會太爛， 所以最壞情況也是 O(n)；代價是 quickselect 的 2.7 倍，這也是為什麼幾乎沒有人真的用它。 而 reservoir sampling 是同一個「一趟、O(k) 記憶體」的形狀，只是問的問題不同： 先留前 k 個，第 i 個元素以 k/(i+1) 的機率留下來，不需要事先知道 n，就得到均勻抽樣。

以上是 CPU 的故事。這篇文章剩下的部分，是同一列資料放到 GPU 上之後會發生什麼事。

用 bit 取代浮點數

radix 類的演算法需要整數。浮點數可以轉成「unsigned 整數順序等於浮點數順序」的 key： 正數翻轉 sign bit，負數整個取反。

def to_ordered(bits):
    return bits ^ (0x80000000 if bits >> 31 == 0 else 0xFFFFFFFF)
     value          float32 bits    ordered key
      -inf      0xff800000     0x007fffff
      -3.5      0xc0600000     0x3f9fffff
      -0.0      0x80000000     0x7fffffff
       0.0      0x00000000     0x80000000
       3.5      0x40600000     0xc0600000
       inf      0x7f800000     0xff800000

這個對應是雙射的，什麼都沒有損失 —— 而這正是「數數」可以取代「比較」的前提。 順帶一提 -0.0 和 +0.0 會拿到不同的 key，這不是 bug：我們排的是 bit pattern。

Radix select：用數的，不用比的

取 key 的最高 8 個 bit，數一數每個元素落在 256 個 bin 的哪一格。 從最高的 bin 往下累加，累積超過 k 的那個 bin 就是答案所在。 比它高的全部進榜，比它低的全部淘汰，只有它裡面的還沒定案。 然後對這些倖存者用下一個 8 bit 再來一次。

4000 attention-like scores, k = 32
  round  shift  bucket   candidates left   still to find
    0     24     192            4,000             32
    1     16     150              611             32
    2      8     169                2              2
    3      0      12                1              1

注意什麼在變小：候選清單。注意什麼從頭到尾沒動過：資料本身。 一輪搬的是 256 個計數器，不管那一列有 4,000 個元素還是 200,000 個 —— 而「數數」是可以完全平行的，每個 thread 數自己那一份，最後 atomic 加起來就好。 這就是這個結構適合 GPU 的全部理由。

還有一件事：k 會變。一輪之後，k 是相對於倖存者算的，不是原本那一列。 忘記這件事就是 radix select 最經典的 bug。

平行版 A：一個 block 處理一列

如果 k 不大，根本不需要開整個 grid。flashinfer 把這條路叫做 FilteredTopK， 一個 block、兩趟掃描。

第一趟建粗直方圖。第二趟需要一個便宜的分類方式，而技巧是不要再想 bin 這件事： 把邊界 bin 的上下界各投影回浮點數空間一次，得到 v_lo 和 v_hi。 這兩個數字整趟迴圈都不會變，所以會被留在暫存器裡， 內層迴圈就變成兩次浮點比較 —— 沒有位元運算，也不用每個元素做一次轉型。

for v in row:
    if v >= v_hi:   winners.append(v)     # certainly in
    elif v >= v_lo: cand.append(v)        # undecided -> shared memory
n = 20,000, k = 64, coarse histogram over 109 occupied bins
  v_hi = 5.998047   (everything above this is a guaranteed winner)
  v_lo = 4.998047   (everything below this is out)
  guaranteed winners             28
  candidates kept                98   (0.49% of the row)

一趟 global memory 就把 20,000 個元素壓到 98 個。之後全部在晶片上， 第二趟再也不用碰 DRAM。不需要 grid barrier、不需要第二次 launch， 而且整顆 kernel 可以被 CUDA graph 抓起來。

如果你真的去讀這段程式碼，有個細節值得先知道：因為收窄成 fp16 是四捨五入到最近， 真正的邊界是相鄰兩個 fp16 值的中點，不是 bin 的邊界本身。 另外，ground truth 是 collect 的計數而不是直方圖的計數 —— remaining 來自直方圖， winners 卻來自浮點比較，捨入有可能讓邊界上的元素在兩邊之間跑掉。

為什麼 fp32 要四輪 refinement，bf16 只要一輪

flashinfer 那幾張 traits 表看起來像調參數的結果：fp32 是 4 輪、從 shift 24 開始， fp16 和 bf16 是 1 輪、shift 0。它們不是調出來的，是從一件事推出來的。

  dtype      exact bits   rounds   first shift   coarse key is a prefix?
  float32          32        4            24           no
  float16          16        1             0          yes
  bfloat16         16        1             0          yes

對 16-bit 的 dtype 來說，粗 bin 就是精確 key 的最高位元組。 粗掃那一趟已經決定了 16 個 bit 裡的 8 個，所以 shift 0 再一輪就結束。 而 fp32 的粗 key 是從收窄過的副本取的 —— 它活在另一個 key space —— 所以它對 fp32 的 key 一個 bit 都沒決定，refinement 只能從最高位重來。

那就會冒出一個很自然的問題：為什麼要收窄？直接對 fp32 的最高位元組做直方圖不行嗎？ 不行，因為 fp32 的最高位元組是符號加 7 個指數 bit，而一列 attention logits 本來就是一堆數量級相近的數字，它們會全部擠進少數幾格。同一批 20,000 個值，三種 key：

  dtype        coarse bins used   candidates after filter   rounds
  float32               109                      98        4
  float16               109                      98        1
  bfloat16               19                   3,197        1

同一列資料，bf16 留下來的候選是 fp16 的 32 倍 —— 它的尾數少 3 個 bit， 所以它的粗 key 是一把比較鈍的尺。收窄之所以安全，是因為它是單調非遞減的： 它可以把值合併，但永遠不會把順序弄反，而合併正是後面 refinement 要拆開的東西。

平行版 B：好幾個 block 分擔同一列

當一列長到一個 block 裝不下，就得讓整個 grid 一起做。 這會多出一個單一 block 從來不需要的東西：跨 grid 的 barrier。 CUDA 沒有跨 block 的 __syncthreads()，所以只能自己用一個計數器兜一個出來。

def barrier(phase):
    old = atomic_add(counter, 1)
    target = (phase + 1) * num_ctas
    while load_acquire(counter) < target:
        pass

裡面有三個細節是撐著正確性的：

計數器從不歸零。 每個 CTA 自己記住 phase，等的是 (phase + 1) * num_ctas。 單調遞增的狀態，比「需要有人清乾淨」的狀態好寫得多，因為那個「清」本身就是一段臨界區。

等待條件是 >= 不是 ==。 被 deschedule 的 CTA 醒來時， 計數器可能已經被推過它的 target 了，用 == 會直接錯過釋放條件，然後永遠自旋下去。

直方圖是三重緩衝的。 第 r 輪累加進 hist[r % 3]，同時 CTA 0 清空 hist[(r + 1) % 3]， 所以一次 barrier 同時證明了「所有的加法都落地了」和「下一份 buffer 是乾淨的」。 只有一份的話，每輪要兩次同步，少一次就死鎖；兩份的話，清空會跟累加撞在一起。 第三份是留給還在讀第 r 輪的落後者的緩衝。

我用 Python 的 threading 把整套模擬了一遍，1、2、4、8、16 個 CTA 各跑五次，全部正確。

失敗案例：flashinfer issue #3610

kernel 結束的時候，總得有人把計數器歸零，好讓下一次 launch 從乾淨的狀態開始。 最直覺的選擇是「誰先做完誰清」。這是個死鎖。

  reset policy   slow CTA   deadlocked   who reset
  last               CTA3        False        CTA3
  first              CTA3         True        CTA0

CTA 0 離開 barrier，順手把計數器設成 0，還卡在最後一次等待裡的 CTA 讀到 0 < target， 於是永遠出不來。這顆 kernel 不會 crash、不會印任何東西，它只是永遠不會結束。

修法是把離開 barrier 這件事本身變成一次選舉：每個 CTA 再加一次， 而那個看到自己的增量正好落在 target 上的 CTA，可以證明它是最後一個出來的， 所以所有同儕都已經停止讀取了。在我的模擬裡那永遠是 CTA3 —— 我故意讓它跑最慢的那一個。

我很喜歡這個 bug，因為寫出壞版本的那個人是比較細心的那個。 「用完自己收乾淨」在任何地方都是好習慣，只有在 barrier 裡面不是。

平手：兩個一直被搞混的旋鈕

這是關於 top-k、但沒什麼人會先告訴你的事：有平手的時候，答案不是唯一的。

拿一列有三個 9、十二個 5、十個 1 的資料，問 k = 8。三個元素贏過 pivot， 剩下五個名額要從十二個平手的 5 裡面挑。挑哪五個？演算法沒有規定。

race (the default)      6 different answers over 8 runs, all of them correct
deterministic, 2 CTAs   stable over 6 runs -> (0, 1, 2, 4, 6, 8, 10, 12)
deterministic, 4 CTAs   stable over 6 runs -> (0, 1, 2, 4, 5, 8, 9, 12)
deterministic, 8 CTAs   stable over 6 runs -> (0, 1, 2, 3, 8, 9, 10, 11)
tie_break = small       one answer across every launch shape -> (0, 1, 2, 3, 4, 5, 6, 7)
tie_break = large       one answer across every launch shape -> (0, 1, 2, 10, 11, 12, 13, 14)

中間那三行值得再看一次。deterministic 完全做到了它承諾的事 —— 跑幾次結果都一樣 —— 但它還是給出三個不同的答案，因為 grid-stride 的迴圈把 num_ctas 烙進了「誰看到哪一個平手元素」。改一下 batch size，grid 寬度就跟著變。

所以 deterministic 釘住的是某一種 launch 形狀下的輸出順序， tie_break 釘住的才是誰進榜。這是兩個互相獨立的旋鈕， 而且只有後者是「列本身的性質」而不是「grid 的性質」。 這也是為什麼一個 block 的 filtered kernel 不提供 tie_break： 要跨整列比 index，需要只有 multi-CTA 那條路才有的全域視角。

實務上：如果同樣的 prompt、同樣的 seed，換個 batch size 就吐出不同的 token， 先來這裡看，不要急著怪 sampler。

第三條路：不砍 bit，直接猜值

前面兩顆平行 kernel 都是在「把資料變小」——數一輪、縮小範圍、活下來的進下一輪。flashinfer 還有第三顆 kernel 做的是完全相反的事。GVR（guess, verify, refine）直接猜那個門檻值， 數一次有幾個元素過關，然後解出下一個更好的猜測。四個階段：P1 生出初始 threshold，P2 用割線 搜尋修正它（全程只數不排），P3 把活下來的收集起來，P4 在這個小很多的集合上做一次精確的 histogram。

P1 是最值得偷的部分，因為它根本不掃這一列。

它讀的是這顆 kernel 自己在上一個 decode step 吐出來的 index 清單，往後位移一個 token， 然後在今天的 logits 上取 min / max / mean。這是 k 次讀取，不是 n 次。它賭的是「token t 的 前 k 名，位置跟 token t-1 差不多」——在 decode 裡，這個賭注幾乎每一步都贏。而搭配這個區間的 兩個 count 根本沒有被量過：P1 直接填 cnt_lo = k + k/4、cnt_hi = 1，等第一次真的數出來的 數字去修正它們。

P2 接著把「有幾個元素過得了這個門檻」當成一個函數，假設它隨門檻線性下降，於是不像 binary search 那樣每次取中點，而是直接解出下一個猜測：

f = (cnt_lo - kFTarget) / (cnt_lo - cnt_hi)
f = clamp(f, 0.05, 0.95)
threshold = val_lo + (val_hi - val_lo) * f

只要落在 accept window [k, kC] 裡就算夠好，因為精確的選擇本來就是 P4 在做。門檻猜壞了只 會慢，不會錯——也正因為如此，下面這件事才有趣，而不是可怕。

在 n = 20,000、k = 512 的那一列上，冷啟動 3 次修正就收工；而那個資訊更充分的暖啟動跑了 15 次然後放棄。比較好的猜測反而比較慢。

原因是一個常數。kFTarget 是 384，而 accept window 的下緣是 k = 512——割線一路收斂到一個 「window 一定會退貨」的數量。更慘的是 P1 憑空填的 cnt_lo = 640 剛好離真實的 629 很近， cnt_lo - cnt_hi 小到不行，f 被夾在 0.95 的上限，於是每一輪只把區間削掉 5%，而不是一步 跨過去。

這件事 kernel 自己的 tuning 表就寫了。它在某一組設定裡把 kFTarget 設成 kK，註解是 「aligns kFTarget with kK to avoid upper-clamp saturation on tight-sigma layers (1.5-2.2x fewer P2 iters on swe-bench)」。同樣的比較在這裡的 200 列隨機資料上：平均修正次數 從 15.00 次（200 列全部放棄）降到 8.38 次（只有 18 列放棄），1.8 倍，落在作者量到的區間裡。 而不管哪一邊，每一列回傳的都是完全正確的 top-k。

還有第二個省法，只有在好幾個 block 共用一列時才看得到。前面那個 grid barrier 必須放在 global memory，因為任意兩個 block 不保證同時在線上。但 thread block cluster 定義上就是 同時在線上的，所以同一個 cluster 裡的 CTA 可以直接讀彼此的 shared memory——mapa.shared::cluster 把本地位址翻譯成 peer 的 shared address，ld.shared::cluster 用接近讀自己 shared memory 的 延遲讀過去。每一輪的 count 聚合完全不離開 GPC：global atomics 是 0，往返也是 0。而 P2 每一次修正都要聚合一次 count，所以「少跑幾次迭代」跟「每次迭代更便宜」其實是同一個最佳化 的兩面。

代價是可攜性。cluster 是 CUDA 的功能，SGLang topk v2 裡對應的那條路在 CDNA 上會被整段編掉， 因為它沒有 distributed shared memory。另外還有一個 load balance 的變體：先把長的列排到前面， 讓它們各自吃掉一整個 cluster，短的列一個 CTA 就好——但那個「有幾列是長的」的計數器是 device 寫的、launch 時要讀，這正好是 CUDA graph 沒辦法捕捉的相依性。三顆 kernel，三種各自不肯讓步的 東西：資料搬移、可攜性、可被 graph 捕捉。

那到底會 launch 哪一顆 kernel？

n=  4,096 k=    8 float32  rows=512   -> filtered   : fits in shared memory, single block
n=200,000 k=   64 float32  rows=1     -> multi-CTA  : one row would leave 131 of 132 SMs idle
n=  4,096 k= 8192 float32  rows=512   -> multi-CTA  : k exceeds the 4096-element smem budget
n=  4,096 k=   64 float32  rows=512   -> multi-CTA  : tie_break needs a row-global rule
n=  4,096 k= 3000 float16  rows=512   -> multi-CTA  : k is past where a per-block sort pays

大部分條件問的是「單 block 這條路可不可能」—— shared memory、tie_break —— 只要可能，它就是預設贏家。例外是第二列：它完全塞得下， 問題只在於「一個 block 一列」就真的只有一個 block，還有 131 個 SM 在發呆。 occupancy 不是正確性的限制，但它照樣決定了答案。

GVR 不在這張表裡，而這正是重點：它不是一顆你可以對任意一列 dispatch 的通用 top-k kernel。 它需要「上一步的 index 存在」，而這件事只有 decode 保證得了。 叫它去選一列它從沒看過的資料，它最大的優勢 —— 那個只花 k 次讀取而不是 n 次的種子 —— 就沒了。

LeetCode 215 - Kth Largest Element in an Array

def find_kth_largest(nums, k):
    return quickselect(nums, k)[k - 1]

[3,2,1,5,6,4]、k = 2 得到 5。[3,2,3,1,2,4,5,5,6]、k = 4 得到 4 —— 「第四大」數的是位置，不是相異值。

真正決勝負的是追問。給它 50,000 個一模一樣的值： 兩路 partition 會把 [7,7,7,…] 切成一邊空、一邊 n-1，一輪只處理掉一個， O(n²)，大約十億次操作。三路 partition 一輪就把所有平手丟掉，0.006 秒結束。 如果面試官再說「資料是串流進來的」，就換成大小為 k 的 min-heap： O(n log k) 時間、O(k) 記憶體，而且不需要隨機存取。

這篇文章的兩半其實在講同一件事。平手在選擇問題裡不是邊角案例， 它是選擇問題最沒有能力回答的那件事，而每一份實作都必須決定要怎麼辦 —— CPU 上靠慣例，GPU 上靠約定。

這條線會接到哪裡

radix select 是 radix sort 的小弟，而 radix sort 的平行骨架就是 prefix sum —— 同一個 scan 會出現在 counting sort、stream compaction， 以及 GPU 上每一個「在我前面有幾個元素滿足這個條件」的問題裡。 barrier 和三重緩衝則會在任何「kernel 需要對 grid 裝不下的資料做多個階段」的地方重現。 GVR 則指向完全不同的方向：它其實是穿著 kernel 外衣的牛頓法， 而它之所以成立，是因為「數量」隨著門檻單調變化。 任何時候只要你手上有一個便宜的單調量測、和一個昂貴的精確答案， 解出那個切點都會比一步步逼近它划算。 而保序 key 這件事本身就值得記住：只要你能把值映射成不損失順序的整數， 比較就變成數數，而數數是可以平行的。
