100 Days of Python - day 15

Seven sites have to be wired together. Every possible cable has a price, and the only requirement is that any site can reach any other - nobody cares how many hops it takes. Which cables do you buy?

Yesterday I built Union-Find and said it was the structure that answers "are these two things already connected?" in near-constant time. Today that question turns out to be the entire algorithm.

The answer is always a tree

Connecting n sites needs at least n - 1 cables. Any cable beyond that closes a cycle, and a cycle means there is an edge you could delete without disconnecting anybody - so the cheapest solution never contains one. A subset of edges that touches every vertex and has no cycle is a spanning tree; the one with the smallest total weight is a minimum spanning tree (MST).

That is the example graph I use throughout, with its MST highlighted: total weight 39.

Kruskal in one sentence

Sort every edge by weight, walk the list from cheapest to most expensive, and keep an edge whenever its two endpoints are not yet connected.

Reading that strip left to right: AD(5) and CE(5) join two isolated vertices each, so both are kept. DF(6) and AB(7) grow the component around A. BE(7) merges the A-group with the C-E group. Then BC(8) and EF(8) and BD(9) are all inside one component already, so each would close a cycle and each is skipped. EG(9) brings in the last vertex, we have 6 edges for 7 nodes, and the rest of the list is dead weight.

The code

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))
        self.rank = [0] * n
        self.count = n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path compression
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                                    # already together
        if self.rank[ra] < self.rank[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra
        if self.rank[ra] == self.rank[rb]:
            self.rank[ra] += 1
        self.count -= 1
        return True

That is yesterday's structure, unchanged. The one detail that matters here is that union returns False when the endpoints already share a root. Kruskal is then this:

def kruskal(n, edges):
    """edges: list of (weight, u, v). Returns (chosen edges, total weight)."""
    uf, chosen, total = UnionFind(n), [], 0
    for w, u, v in sorted(edges):
        if uf.union(u, v):
            chosen.append((w, u, v))
            total += w
            if len(chosen) == n - 1:
                break
    return chosen, total

There is no cycle detection code anywhere, because the disjoint set structure is the cycle detector. An edge whose endpoints already have the same root is, by definition, an edge whose endpoints are already joined by a path - adding it would close a cycle. That is the whole reason these two days sit next to each other.

The early break is not just an optimisation. Once n - 1 edges are in, the tree is complete and every remaining edge is guaranteed to be rejected, so on a dense graph you often stop after reading a small prefix of the sorted list.

Why greedy is safe here

Greedy algorithms are usually wrong. Taking the locally cheapest option and never reconsidering fails on almost every optimisation problem you can name, so it is worth knowing why it does not fail here.

The cut property. Split the vertices into two non-empty groups, any way you like. The cheapest edge with one endpoint in each group belongs to some MST.

The proof is an exchange argument. Suppose some MST T does not contain that cheapest crossing edge e. Add e to T anyway: you now have n edges on n vertices, so there is exactly one cycle. That cycle leaves one side of the split and comes back, so it must use some other crossing edge f. Since e was the cheapest crossing edge, weight(f) ≥ weight(e). Remove f: the cycle is broken, the graph is connected again, and the total weight did not go up. So there is an MST containing e.

Every edge Kruskal accepts is the cheapest edge crossing the cut between the component it is attaching to and everything else - all the cheaper crossing edges were scanned earlier and, had they crossed, would have been taken. So every acceptance is safe.

The cycle property is the mirror image: the heaviest edge of any cycle is in no MST. If a tree contained it, deleting it splits the tree into two halves, and the rest of the cycle reconnects those halves at a cost no greater than what you removed. Every edge Kruskal rejects is the last edge of its cycle to be scanned, therefore the heaviest, therefore safe to throw away.

The two properties together say: everything Kruskal takes belongs in some MST, and everything it drops belongs in none. That is the correctness proof.

When the graph is disconnected

Kruskal never asks whether the graph is connected. If it is not, the scan just runs out of edges with fewer than n - 1 chosen, and what you get is a spanning forest: a minimum spanning tree of each component.

In the example, detaching G leaves 5 edges totalling 30 instead of 6 totalling 39. That is not a failure, it is the right answer to a different graph - but if your caller assumed a tree, it will quietly do the wrong thing. Check len(chosen) == n - 1 and you know which case you are in.

Complexity

step                    time              space
---------------------   ---------------   -------
sort the edges          O(E log E)        O(E)
scan with Union-Find    O(E α(V))         O(V)
total                   O(E log E)        O(V + E)

Since E ≤ V², log E ≤ 2 log V, so O(E log E) is the same as O(E log V). The sort dominates completely: the scan itself is effectively linear, because α - the inverse Ackermann function from yesterday - is at most 4 for any input that will ever exist. If the weights are small integers you can counting-sort them and the whole algorithm becomes near-linear.

LeetCode 1584 - Min Cost to Connect All Points

Given points on a plane, connect them all at minimum total cost, where the cost of joining two points is their Manhattan distance.

There is no edge list in the input, so build one:

from itertools import combinations

def min_cost_connect_points(points):
    n = len(points)
    edges = []
    for i, j in combinations(range(n), 2):
        (x1, y1), (x2, y2) = points[i], points[j]
        edges.append((abs(x1 - x2) + abs(y1 - y2), i, j))
    _, total = kruskal(n, edges)
    return total

That is the whole solution. The interesting part is the caveat I would say out loud in an interview: this builds a complete graph with n(n-1)/2 edges, so sorting costs O(n² log n) and memory is O(n²). For a dense graph like this one, Prim's algorithm - which grows a single tree and only ever looks at edges touching it - does the job in O(n²) with O(n) memory, and that is tomorrow's post. Kruskal earns its keep on sparse graphs, where E is close to V and the sort is cheap.

Why this matters later

Minimum spanning trees are not just a networking story. Single-linkage clustering is literally Kruskal with an early stop: run it until k components remain and you have clustered your data. The same structure shows up in image segmentation, in approximation algorithms for the travelling salesman problem, and - closer to where this series is heading - in the "which shards do I connect, and how expensive is each link?" question that collective communication libraries answer when they build a ring or tree topology across GPUs.
