Day 45 — 梯度下降家族：SGD、momentum 與 Adam，以及學習率失效的那個精確臨界點

程式碼：day 45 on GitHub

100 Days of Python - day 45

在一個二次碗上，學習率有一個精確的上限。對 f(w) = 0.5(w0² + 20w1²) 來說是 2 / 20 = 0.1：lr = 0.0999 會收斂，lr = 0.1001 會一路飛到無限大。過程中不會丟出任何例外。用 lr = 0.11 跑 400 步之後，我的參數向量是 [5.7e-21, 4.7e+31]——一個座標解得完美，另一個已經飛到宇宙外面去了。

Day 44 結束在一個訓練迴圈，它的最後一行是 w -= lr * w.grad。今天做的事就是把那一行換掉，其他什麼都不動：

g = grad(w)
w = opt.step(w, g)

七種更新規則都走這個介面：SGD、加 momentum 的 SGD、Nesterov、AdaGrad、RMSProp、Adam 與 AdamW。有意思的不是公式，而是它們的哪些細節是真的承重的。以下四個是，而且寫錯的時候都不會回報任何錯誤：

  • Adam 少了 bias correction，步子會太大，不是坊間說的太小——第 1 步大 3.2 倍，第 12 步大 6.6 倍，到第 1,000 步還大 1.26 倍。
  • 在 v 等於 1e-12 的座標上，sqrt(v) + eps 和 sqrt(v + eps) 差 99 倍。
  • L2 正則化放進 Adam 裡，會讓梯度最大的那些權重被衰減得少 10 倍，方向剛好相反。
  • 同一份資料，batch 1 能用的學習率比全批小 8.5 倍，因為它要遷就自己那一列的曲率，而不是平均。

執行 python optimizers.py 會印出本文的每一個數字（除了計時，其餘都是精確值）。

山谷，以及上限是怎麼來的

f(w) = 0.5(w0² + 20w1²) 這個碗，橫向的彎曲程度是縱向的 20 倍——是一道山谷。最大曲率除以最小曲率這個比值叫做條件數（condition number），而它就是決定一個碗有多難走下去的那一個數字。

純梯度下降在二次函數上做的事非常單純：每一步把每個座標乘上 (1 - lr × 曲率)。整個演算法就這樣，而收斂條件也就白送給你了——每個乘數的絕對值都必須小於 1：

lr = 0.05    largest multiplier 0.95000  converges
lr = 0.0999  largest multiplier 0.99800  converges
lr = 0.1001  largest multiplier 1.00200  diverges
lr = 0.11    largest multiplier 1.20000  diverges

限制來自最陡的那個方向，所以 lr < 2 / 最大曲率。超過之後，平坦方向照樣收斂得漂漂亮亮，陡的那個則爆炸——這也是為什麼一個已經發散的訓練，常常還有一部分參數看起來完全正常。

上限以下則是問題的另一半。lr = 0.09 時陡方向的乘數是 -0.80：每一步都衝過頭並翻面，這就是第一張圖裡的鋸齒。同時平坦方向每步只縮 0.91，根本是用爬的。你被允許的步長由最陡的方向決定，你實際的進度卻由最平的方向決定。 這個落差就是條件數，也是這個碗要走 147 步而不是幾步的原因。

momentum 把 kappa 變成 sqrt(kappa)

momentum 會累積過去梯度的和，然後沿著那個和走：

self.v = self.momentum * self.v + g
return w - self.lr * self.v

在鋸齒那個方向，正負交替的梯度在總和裡互相抵消；在谷底方向，它們方向一致因而累加。理論說每步的誤差乘數會從 (kappa - 1)/(kappa + 1) 改善成 (sqrt(kappa) - 1)/(sqrt(kappa) + 1)，kappa = 20 時就是 0.905 對 0.635。實測對上理論：

plain GD   lr 0.0952  rate 0.9048  theory 138.0 steps  measured 139
momentum   lr 0.1336  beta 0.4026  rate 0.6345  theory  30.4 steps  measured  39

純 GD 的預測跟實測只差一步，這是「我對正在發生的事的理解是對的」的好跡象。momentum 實測 39 步對上預測的 30 步，差距來自理論用的是忽略暫態的漸近速率，但仍然少了 3.6 倍的步數。

有一件事值得量而不是假設：beta = 0.9 不是什麼自然常數。這個碗最好的 beta 是 0.4026，固定 lr = 0.04 時：

beta 0       -> 338 steps
beta 0.4026  -> 190 steps
beta 0.9     -> 245 steps

從某篇文章抄來的 0.9 比調過的值更差，而且在某些學習率下比完全不用 momentum 還差。beta 在做的事是替一個振盪器調阻尼，它有一個取決於問題的正確答案。

換到真的問題上，而且每個學習率都調過

一個 400 列、3 個特徵的最小平方問題，其中一個特徵被放大 8 倍，所以條件數是 77。用同一個學習率去比較不同 optimizer 是沒有意義的——AdaGrad、RMSProp 和 Adam 會把梯度除以它自己的大小，它們的 lr 根本是另一種量——所以每一個都各自掃過一輪：

SGD                  best lr  0.0126    400 steps
SGD + momentum 0.9   best lr  0.0032    181 steps
SGD + Nesterov 0.9   best lr  0.0079    163 steps
AdaGrad              best lr  1.5849     10 steps
RMSProp              best lr  0.1585     26 steps
Adam                 best lr  0.6310    153 steps

AdaGrad 快 40 倍這件事值得解釋，而不是拿來慶祝。AdaGrad 除以的是有史以來每一個梯度平方的總和開根號，所以它的有效步長只會越縮越小。在一個小的、固定的、沒有雜訊的二次問題上，這接近理想——它等於先估出曲率再逐步退火。同樣這個性質，就是它在長時間訓練上會卡死的原因：分母一直長大、步長一直縮小，最後什麼都不動了。RMSProp 就是在那個總和上加了遺忘因子，讓步長有機會恢復；Adam 則是 RMSProp 再加上對梯度本身也做 momentum。

Adam，以及它最常被寫錯的兩個地方

Adam 維護兩個移動平均：梯度的 m 與梯度平方的 v。步長是 lr * m / sqrt(v)，所以不管某個座標的梯度尺度多大，它每步大約都移動 lr。

兩個平均都從零開始，所以早期都被低估。標準修正是把 m 除以 1 - b1^t、v 除以 1 - b2^t。坊間的說法是少了這步會讓前幾步太小。並不會——會讓它們太大，因為 v 在根號底下，兩邊的偏差不會互相抵消：

uncorrected / corrected = (1 - 0.9^t) / sqrt(1 - 0.999^t)
  step     1: 3.162x        step   100: 3.241x
  step    12: 6.569x        step  1000: 1.258x

在真問題上用 lr = 0.05 量，前三步分別是加了修正的 0.087, 0.086, 0.086 與沒加的 0.274, 0.363, 0.404。沒修正的版本在最初幾百步用的是比你指定的大好幾倍的學習率，而那剛好是模型最脆弱的時候。

第二個細節是 epsilon 放哪裡。sqrt(v) + eps 和 sqrt(v + eps) 都能防止除以零，但 eps = 1e-8 的根號是 1e-4：

v = 1e-12   sqrt(v) + eps = 1.010e-06   sqrt(v + eps) = 1.000e-04   ratio    99.0x
v = 1e-16   sqrt(v) + eps = 2.000e-08   sqrt(v + eps) = 1.000e-04   ratio  5000.0x

在任何梯度很小的座標上——很少被用到的 embedding 列、幾乎死掉的神經元——第二種寫法會悄悄把步長除以一百甚至更多。PyTorch 用的是 sqrt(v) + eps。

Adam + L2 不等於 AdamW

L2 正則化通常是把 wd * w 加進梯度裡實作的。但在 Adam 內部，這個和接著會被除以 sqrt(v)——於是每個權重實際受到的衰減被縮放了 1 / sqrt(v)，梯度最大的那些權重得到的衰減最少：

在最小平方問題上跑 400 步 Adam 後，三個權重的 sqrt(v) 是 [0.41, 0.15, 4.06]（量的是沒加懲罰項的那一次；加上去之後 sqrt(v) 最多只差 2.5%）。把平均衰減強度正規化成 1，Adam + L2 實際施加的是 [0.77, 2.15, 0.08]，AdamW 則是 [1, 1, 1]。那個 8 倍尺度特徵上的權重——梯度遠大於其他人的那個——被衰減的強度比 weight 0 少 10 倍、比 weight 1 少 28 倍。AdamW 的修法是乾脆不讓衰減經過梯度：

w = w - self.lr * mh / denom
if self.weight_decay and self.decoupled:
    w = w - self.lr * self.weight_decay * w    # decay applied straight to w

這兩行就是 torch.optim.Adam(weight_decay=...) 和 torch.optim.AdamW 的全部差別，也是 AdamW 成為 transformer 訓練預設值的原因。

mini-batch 會把上限往下搬

上面全部都是每步用整份資料。真實訓練用的是 mini-batch，而第一個改變的就是學習率上限。上限來自「一步必須撐住的最陡曲率」，而 batch 1 看到的是它自己那一列的曲率，不是平均：

ceiling from the average over all 400 rows   0.0140
ceiling from the sharpest single row         0.00165   (8.5x smaller)

lr 0.01, batch 1     after 30 epochs: blew up
lr 0.01, batch 8     after 30 epochs: 4.6e-04
lr 0.01, full batch  after 30 epochs: 1.5e+00

在那個上限以下，小 batch 在「每掃過一遍資料」這個尺度上效率高得多——然後就停住了：

after  10 epochs   batch 8 8.813e-02   full batch 4.626e+00
after  30 epochs   batch 8 2.545e-03   full batch 3.911e+00
after 100 epochs   batch 8 5.396e-03   full batch 2.210e+00
after 300 epochs   batch 8 2.484e-03   full batch 4.352e-01

batch 8 在 30 個 epoch 內多走了三個數量級，接下來 270 個 epoch 就停在 2.5e-3 附近的雜訊地板上。每個 mini-batch 的梯度方向都稍微偏一點，所以在固定步長下，參數會以一個由雜訊與學習率共同決定的半徑繞著最佳解轉。把學習率逐步調小，就是把那個半徑縮小——這正是學習率排程存在的理由。

shuffle 這件事值得量，而不是當成信仰。在本來就隨機排列的資料上，每個 epoch 重洗完全看不出差別（1.6e-3 對 1.5e-3，五個 seed 的中位數）。但在同一份資料依目標值排序過之後，重洗好 12 倍。排序過的資料讓每個 batch 在每個 epoch 都以同樣的方式不具代表性，於是同一串有偏差的更新一再重複——這才是 shuffle 真正在保護你的失敗情境。

LeetCode 462 - Minimum Moves to Equal Array Elements II（最少移動次數使陣列元素相等 II）

題目。 給一個整數陣列，求讓所有元素都相等所需的最少移動次數；一次移動是把某一個元素加 1 或減 1。

輸入／輸出。 nums 是一個整數 list。回傳一個整數：移動的總次數。

範例。 [1, 2, 3] 需要 2 次：把 1 升上去、把 3 降下來，兩者都到 2。[1, 10, 2, 9] 需要 16 次：選 9（或 2 到 9 之間的任何值），得到 8 + 1 + 7 + 0。

限制。 最多 100,000 個元素，每個介於 -10⁹ 到 10⁹。值域這麼大，排除了「用值當索引去計數」的做法；而這個規模下 O(n log n) 的排序完全可以接受。真正的限制藏在「移動次數」這個詞裡：成本是絕對差之和，不是平方差之和，而這兩者的最小值點不一樣。

選一個目標 c 的成本是 sum|x - c|。|x - c| 對 c 的導數是 c - x 的正負號，所以總導數就是「比我小的有幾個，減掉比我大的有幾個」。這個值剛好在中位數處為零：

class Solution:
    def minMoves2(self, nums: list[int]) -> int:
        nums = sorted(nums)
        mid = nums[len(nums) // 2]
        return sum(abs(x - mid) for x in nums)

陷阱是伸手去拿平均數，但平均數最小化的是平方誤差——也就是 Day 44 那條 2/n Xᵀ(Xw - y) 建立其上的東西。在 [1, 2, 3] 和 [1, 10, 2, 9] 上平均數和中位數給出同樣的答案，所以隨手測一下會過。到了 [1, 2, 3, 100]，中位數給 100、平均數給 146：一個看起來很合理、比較大、而且錯的數字。

拿今天的梯度下降去跑 sum|x - c| 是個不錯的驗證。從 c = 0 出發、配上 1/sqrt(k) 的排程，它停在 2.354，成本剛好是 100——因為元素個數是偶數時，兩個中間值之間的任何 c 都是最佳解，最小值點是一個區間而不是一個點。注意那個排程是在做實事：步長固定的話，正負號梯度在最佳解附近也不會變小，迭代會永遠震盪下去。這跟 mini-batch 那一節的雜訊地板是同一個機制，只是以最純粹的形式出現。

LeetCode 852 - Peak Index in a Mountain Array（山脈陣列的峰頂索引）

題目。 一個陣列是一座山：嚴格遞增到某個索引，之後嚴格遞減。找出那個索引。

輸入／輸出。 arr 是一個保證形成山脈的整數 list。回傳最大元素的索引（整數）。

範例。 [0, 10, 5, 2] 回傳 1：arr[1] = 10 比兩邊的鄰居都大，而且在它之後一路遞減。

限制。 元素個數介於 3 到 100,000，而且題目明確要求 O(log n)。這個要求就是整題的重點——線性掃描找得到答案，但不被接受。

離散陣列在 mid 與 mid + 1 之間的斜率，就只是 arr[mid] < arr[mid + 1] 這個比較。在一座山上，這個比較對峰頂之前的每個索引都為真、對峰頂及之後的每個索引都為假，所以它是一個排序好的布林陣列，Day 23 的二分搜尋直接適用：

class Solution:
    def peakIndexInMountainArray(self, arr: list[int]) -> int:
        lo, hi = 0, len(arr) - 1
        while lo < hi:
            mid = (lo + hi) // 2
            if arr[mid] < arr[mid + 1]:    # still going up: the peak is to the right
                lo = mid + 1
            else:                          # already coming down: mid could be the peak
                hi = mid
        return lo

在一個 4,001 個元素的山脈上，它只看了 24 個元素。說它是梯度上升，是因為它用到的唯一資訊就是斜率的正負號——只不過它不是照著斜率走一步，而是每探測一次就刪掉剩下空間的一半。連續版本的對應物是三分搜尋：在一個單峰的 f 上取兩個內部點求值，丟掉不可能含有最小值的那三分之一，完全不需要導數也能收斂。在 [-10, 10] 上對 (x - 1.234567)² + 3 跑，它還原出 1.234567。

leetcode.com/problems/peak-index-in-a-mountain-array

那為什麼還需要梯度下降？因為維度。二分與三分搜尋統治的是一維單峰問題；它們兩個碰到一百萬個參數都撐不住，而梯度一次就給出這一百萬個方向。

複雜度

--------------------------------------  ---------------------------------------  ----------------
d 個參數的一次 SGD 更新                 O(d)                                     O(1)
一次 momentum / RMSProp / AdaGrad 更新  O(d)                                     O(d)
一次 Adam / AdamW 更新                  O(d)                                     O(2d)，存 m 與 v
條件數 k 時，GD 到指定精度的步數        正比於 k                                 —
最佳 beta 下 momentum 的步數            正比於 sqrt(k)                           —
LeetCode 462                            排序 O(n log n)，用 quickselect 可 O(n)  額外 O(1)
LeetCode 852                            O(log n)                                 O(1)
三分搜尋到指定容差                      O(log(範圍 / 容差))                      O(1)

這些用在哪

Adam 多出來的 m 與 v，就是 optimizer 狀態為什麼是模型本身兩倍大的原因：用 fp32 訓練一個 70 億參數的模型，權重要 28 GB，Adam 的兩個動量再要 56 GB——而這正是分散式訓練裡「切分 optimizer 狀態」這件事大部分要處理的東西。AdamW 幾乎是每一份 transformer 訓練腳本的預設值。那些腳本開頭的學習率 warmup，處理的是跟 bias correction 同一件事：訓練初期的脆弱——在第 1 步，Adam 對梯度的尺度幾乎一無所知。強化學習的實作則傾向把 Adam 的 epsilon 設成 1e-5 而不是預設的 1e-8，因為 RL 的梯度又小又吵，預設的 epsilon 小到壓不住它。

值得留下的習慣：loss 變成 nan 時，先懷疑學習率再懷疑模型；而且記得上限是跟 batch 裡最陡的曲率走的，所以把 batch size 砍半可能就得把學習率調低。要比較 optimizer 時，每一個都得各自調過學習率，否則這個比較沒有意義。還有，當 beta = 0.9 這種超參數是從別處抄來的，值得花一輪掃描確認它對手上這個問題是不是對的。
