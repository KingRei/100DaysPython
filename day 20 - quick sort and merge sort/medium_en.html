Day 20 - Quick sort and merge sort: one sentence separates them

Code: day 20 on GitHub

100 Days of Python - day 20

Both algorithms cut the array in half and recurse. Both are O(n log n). The only difference is where the work happens: merge sort splits by index and pays for everything in the join; quick sort pays everything in the split and gets the join for free.

Everything else follows from that one sentence - stability, the worst case, whether you can sort a file bigger than memory, and how well each one parallelises. That is what today is about.

Yesterday's A* ended on work versus depth: parallel BFS has the same O(V+E) work as the sequential version, but a much shorter critical path. Sorting is where that idea gets a proper workout.

Merge sort: the join does everything

def merge_sort(a):
    if len(a) <= 1:
        return a
    mid = len(a) // 2
    return merge(merge_sort(a[:mid]), merge_sort(a[mid:]))

def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:      # <= is the entire reason it is stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    return out + left[i:] + right[j:]

mid = len(a) // 2 does no comparisons and never looks at the data. That is why the recursion tree has the same shape for every input: sorted, reversed, all-equal, random - all identical cost. "Merge sort has no worst case" is not a property of the merge, it is a property of the split being blind.

The merge is two fingers walking forward, and every comparison fixes exactly one output slot. Change <= to < and you lose stability. Sorting [(1,'a'), (0,'b'), (1,'c'), (0,'d')] by the first field gives [(0,'b'), (0,'d'), (1,'a'), (1,'c')] - a still ahead of c. One character decides that.

The merge also answers a question you did not ask. When an element is emitted from the right half, every value still sitting on the left is larger than it - and each of those pairs is an inversion:

inv += len(left) - i        # one line, in the else branch

[2, 4, 1, 3, 5] has 3 inversions. Sixty-four random values had 1230; their reverse had

  1. Brute force costs O(n^2); this is free.

Quick sort: the split does everything

Lomuto's partition maintains one invariant - everything in a[lo:i] is smaller than the pivot - and after the scan the pivot swaps into slot i. That slot is final. No later recursive call ever touches it, which is precisely why there is no join step and no scratch array.

The price is that the split now depends on the data, and the data gets a vote.

The two inputs that break it

Same code, n = 200:

input           lomuto / last pivot   lomuto / random pivot  three-way       merge sort
--------------  --------------------  ---------------------  --------------  -------------
already sorted  19900 cmp, depth 199  1502, depth 15         1494, depth 12  732, depth 8
all equal       19900 cmp, depth 199  19900, depth 199       200, depth 1    732, depth 8
random          1509, depth 14        1636, depth 14         1766, depth 16  1282, depth 8

Two different failures live in that table, and only one of them has the fix people remember.

Already sorted input with a last-element pivot means the pivot is always the largest value, so the split is n-1 / 0 and the recursion is n levels deep instead of log n. At n = 200 that is 19,900 comparisons and 199 stack frames; CPython gives up at 1000. A random pivot fixes it in one line.

All equal defeats the random pivot too. It makes no difference which element you pick when a[j] < p is never true - a two-way partition has no "equal" region, so values that are already in their final places get re-partitioned at every level. Pure wasted work.

Neither case raises an exception. They just get slow, which on an online judge reads as TLE.

Three-way partition: give "equal" a home

lt, i, gt = lo, lo, hi
while i <= gt:
    if a[i] < p:
        a[lt], a[i] = a[i], a[lt]; lt += 1; i += 1
    elif a[i] > p:
        a[i], a[gt] = a[gt], a[i]; gt -= 1    # i does NOT advance: the value
    else:                                     # swapped in from the right has
        i += 1                                # not been examined yet

The middle region retires immediately, so the recursion depth is set by the number of distinct values rather than the number of elements. On 400 equal values: 79,800 comparisons at depth 399 for the textbook version, 400 comparisons at depth 1 for this one.

That gt branch is the line everyone gets wrong. The value swapped in from the right end has never been looked at, so i must stay put and judge it next round.

External sort: merge sort's other superpower

Because merging is sequential, merge sort can sort data it cannot hold. Read a chunk, sort it, write it out as a run, repeat; then merge the runs with a heap that holds one element from each. Sorting 1000 values with room for 100 gives 10 runs and never holds more than 100 items - 10% of the data.

Quick sort cannot do this at all. Partitioning needs random access to the whole array, and random access is exactly what you do not have when the array is a file.

Work and depth: the parallel merge sort that isn't

Work is the total number of operations. Depth is the longest chain that must happen in order. Sequential composition adds depths, parallel composition takes the max, and work / depth is the most cores this algorithm could ever keep busy.

Measured on n = 1024:

                                 work    depth   most usable cores
-------------------------------  ------  ------  -----------------
one core                         10,240  10,240  1x
parallel halves, plain merge     10,240  2,046   5x
parallel halves, parallel merge  18,857  235     80x

The middle row is what most people write when asked to parallelise merge sort, and it is a trap. Yes, the two recursive calls run at the same time. But the final merge of n elements is a sequential loop - step k needs to know what step k-1 emitted - so the depth stays O(n). Five cores is the ceiling; the other 59 idle.

The fix is to make the merge divide and conquer as well: take the median of the longer half, binary-search its position in the other half, and the two sides of that cut are completely independent. Depth collapses from 2,046 to 235 for 84% more work.

That trade - spend work to buy depth - is the entire game in parallel algorithms, and it is the same ledger that decides whether a GPU kernel or an inference scheduler is worth writing.

Sample sort: quick sort's partition, scaled out

On a cluster you cannot afford log n rounds of pairwise merging, so sample sort splits once: sample the data, sort the samples, pick p-1 splitters, do one all-to-all exchange, then let every machine sort locally. It is a partition with p-1 pivots instead of one.

The only thing that can go wrong is load imbalance, and the sort finishes when the slowest machine finishes. Sampling is a lottery, so a single run proves nothing - this is the mean over 200 samplings of the same 20,000 values across 8 machines:

samples per machine  mean imbalance  worst seen
-------------------  --------------  ----------
1                    2.76x           5.54x
4                    1.82x           3.41x
32                   1.26x           1.82x

One splitter per machine leaves the busiest one 176% above a fair share. Oversampling costs a slightly bigger sort of the samples and buys nearly all of that back.

LeetCode 912 - Sort an Array

Sort an array without the built-in sort. The judge's data is duplicate-heavy and contains sorted stretches, which is to say it is built from exactly the two failure cases above. An accepted solution needs four things:

  1. a random pivot, so no input can predict the split;
  2. a three-way partition, so duplicates retire instead of being re-partitioned;
  3. insertion sort for short runs;
  4. recursion on the smaller side and a loop on the larger one:
if lt - lo < hi - gt:
    sort(a, lo, lt - 1); lo = gt + 1      # loop on the big side
else:
    sort(a, gt + 1, hi); hi = lt - 1

Point 4 is the one that separates "works" from "works on the judge": it caps the stack at O(log n) regardless of how the pivots fall.

Why this matters later

Merge sort's k-way merge is how sorted runs get combined in a database, and how a scheduler drains several ordered streams into one. The work/depth ledger is the tool used later in this series to reason about batching and about GPU kernels, where the question is never "how many operations" but "how many of them can happen at the same time". And the stability of the merge is what makes multi-key sorting work: sort by the secondary key first, then by the primary one, and the secondary order survives.
