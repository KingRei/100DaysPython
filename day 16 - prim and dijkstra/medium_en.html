Prim and Dijkstra are the same algorithm

Code: day 16 on GitHub

100 Days of Python - day 16

I learned these two as separate chapters, months apart. Prim was in the "minimum spanning tree" chapter, Dijkstra in the "shortest path" chapter, and nothing suggested they had anything to do with each other. Then I wrote them one after the other in the same file and the diff was four characters long.

Here is the punchline before the explanation: one function, one heap, one loop, and a key argument that decides which of the two algorithms you get. If key compares the weight of a single edge you have Prim. If it compares the length of the whole path from the source you have Dijkstra. Everything else - the heap, the done array, the relaxation, the complexity - is identical.

Yesterday's Kruskal built a minimum spanning tree by sorting all the edges once and filtering them with Union-Find. Prim solves the same problem from the other direction, and that change of direction is what makes Dijkstra fall out of it for free.

Growing a tree instead of collecting edges

Kruskal considers edges from anywhere in the graph and lets a forest slowly merge into one tree. Prim starts at a single vertex and never lets the tree split: at every step it looks at the edges leaving the tree and buys the cheapest one.

In the picture A, D and F are already inside the tree. The teal edges are the ones crossing the boundary, the amber ones have been bought. The next purchase is AB at 7, because it is the cheapest edge on that boundary right now.

Why is buying it immediately safe? This is the cut property again, the one that made Kruskal correct. Split the vertices any way you like; the cheapest edge crossing that split belongs to some minimum spanning tree. Prim just fixes the split to be "the tree so far | everything else" and re-uses the theorem at every step. So the amber edges in the picture are not provisional: each one is already an edge of the final minimum spanning tree, and nothing later can swap it out.

Doing that efficiently needs one data structure: for each outside vertex, the cheapest edge currently connecting it to the tree. Pull out the minimum, add more edges, pull out the minimum again - that is a priority queue, which is Day 05's heap.

The skeleton

from heapq import heappush, heappop
INF = float('inf')

def heap_greedy(n, adj, src, key):
    best   = [INF] * n          # cheapest known way to reach each vertex
    parent = [-1] * n           # who provided that way
    done   = [False] * n        # settled: never revisited
    best[src] = 0
    pq = [(0, src)]

    while pq:
        d, u = heappop(pq)
        if done[u]:             # a stale copy left behind by an update
            continue
        done[u] = True

        for v, w in adj[u]:
            nd = key(d, w)      # <-- the only difference
            if not done[v] and nd < best[v]:
                best[v], parent[v] = nd, u
                heappush(pq, (nd, v))

    return best, parent


def prim(n, adj, src=0):
    return heap_greedy(n, adj, src, lambda d, w: w)          # cost of this edge

def dijkstra(n, adj, src=0):
    return heap_greedy(n, adj, src, lambda d, w: d + w)      # cost of the whole path

d is the priority the vertex was popped with. For Prim that is the weight of the edge that pulls it in, so the lambda ignores d entirely - costs never accumulate. For Dijkstra d is the distance from the source, so the lambda adds to it, and the accumulation is what turns a spanning tree into a shortest-path tree.

The one line that looks like a bug

if done[u]:
    continue

heapq has no decrease-key. When a vertex's best improves, the obvious move would be to find its entry in the heap and lower it - but finding it costs O(n), which would ruin the complexity. So we do not. We push a second, better copy and leave the old one sitting there. When the stale copy eventually surfaces, its vertex is already settled and we skip it. This is called lazy deletion, and it is the reason the heap can hold up to E entries instead of V.

That also fixes the complexity: every edge causes at most one push, so the loop is O(E log E), and since E < V², log E < 2 log V, which people write as O(E log V).

Why settling a vertex is allowed at all

Both algorithms make an irreversible decision every iteration: pop the minimum, mark it done, never look at it again. The justification is different in each case, and that difference matters more than the code does.

Prim uses the cut property, as above. Dijkstra uses a different argument: suppose some shorter route to u existed. It would have to leave the settled region through a vertex still in the heap, and that vertex's tentative distance is already at least d, so the route is already at least as long as d before it even gets to u. Adding more edges can only make it longer.

Read that sentence again: adding more edges can only make it longer. It is true only because weights are non-negative. The entire precondition of Dijkstra hides inside that clause.

Three vertices are enough to show it. S to A costs 5, S to B costs 2, and A to B costs -10. Dijkstra settles B at 2 because 2 is the smallest thing in the heap. Later A settles at 5 and offers B a distance of 5 + (-10) = -5 - but done[B] is already True, so the improvement is discarded. The answer comes back as 2 instead of -5, with no exception, no infinite loop and no warning. Just a wrong number.

The fix is to stop finalising anything, which is Bellman-Ford: V-1 rounds, relaxing every edge each round, O(VE) instead of O(E log V). That is the price of negative weights.

Prim, meanwhile, does not care at all. Its key is w, with no accumulation, so a negative edge is simply a very cheap ticket into the tree.

The two trees are not the same tree

Both functions return a parent array, and both of those arrays describe a spanning tree. They are not the same tree, and it is worth being concrete about that.

On the example graph Prim returns a tree of total weight 39 - exactly the number Kruskal produced yesterday, even though the edges were chosen in a completely different order. Dijkstra's tree weighs 44. But walk from A to G: inside the minimum spanning tree the trip costs 23, while the true shortest path costs 22 and uses the edge FG = 11, which the MST refuses to buy.

So the MST is cheaper overall and worse for individual journeys. "Lay the least cable" and "give everyone the fastest route to the server" are different problems with different answers, and no tree optimises both. In code, the difference between the two objectives is one lambda.

LeetCode 743 - Network Delay Time

A signal starts at node k and travels along directed edges with given delays. How long until every node has received it?

class Solution:
    def networkDelayTime(self, times, n, k):
        adj = [[] for _ in range(n + 1)]
        for u, v, w in times:
            adj[u].append((v, w))              # directed - one side only

        dist, _ = heap_greedy(n + 1, adj, k, key=lambda d, w: d + w)

        ans = max(dist[1:])                    # whoever hears it last
        return ans if ans < INF else -1        # someone never hears it

Three things go wrong here more often than the algorithm does. The edges are directed, and after a week of undirected graphs it is easy to append both directions out of muscle memory - the answer then comes out too small and the sample tests may not notice. The answer is a maximum over shortest paths, not a shortest path; propagation finishes when the slowest recipient is done. And the unreachable case has to be checked explicitly, because INF is a perfectly valid float that will happily be returned as the answer.

Interview-wise, this problem is a gift: if you can say "this is single-source shortest path on a directed graph, so Dijkstra with a heap, O(E log V)" in the first ten seconds, the rest is typing.

Complexity

Prim (binary heap)          O(E log V)      dense graphs: the O(V^2) array version wins
Dijkstra (binary heap)      O(E log V)      non-negative weights only
Dijkstra (Fibonacci heap)   O(E + V log V)  better on paper, rarely in practice
Bellman-Ford                O(VE)           negative weights, detects negative cycles

The Fibonacci-heap bound is the one textbooks love and profilers hate: the constant factor is large enough that a plain binary heap usually wins on real graphs.

Why this matters later

Dijkstra is the ancestor of every informed search. Add a heuristic to the priority and it becomes A*, which is where classical graph search meets AI. Replace the heap with buckets and it becomes Δ-stepping, one of the few shortest-path algorithms that parallelises well. The same lazy-deletion trick shows up whenever a priority queue meets values that change: event simulation, beam search decoding, and the candidate lists inside approximate nearest-neighbour indexes.

And the deeper habit is the one worth keeping: when two algorithms have the same shape, find the parameter that separates them. It is usually one line, and that line is usually the whole idea.
