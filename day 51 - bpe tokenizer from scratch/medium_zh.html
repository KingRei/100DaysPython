Day 51 — BPE Tokenizer 從零實作：把一句話變成模型真正看到的那串整數

程式碼：day 51 on GitHub

100 Days of Python - day 51

tokens 這個字要花 3 個 token。 tokens——前面多一個空格——只要 1 個。

同樣五個字母。差別是一個空格，原因是 tokenizer 把「空格＋tokens」學成了一個符號——因為詞在真實文字裡就是長這樣出現的，所以它在語料裡常到值得配一個 id；而沒有空格的 tokens 沒有。

模型從來沒看過你的文字。它看到的是一串整數，而產生那串整數的東西替你做了一連串你沒做過的決定：詞在哪裡斷、開頭那個空格算不算詞的一部分、數字怎麼被切、以及你這句話要花掉幾個整數。這是整條流程裡唯一一個不是用梯度下降學出來的部分——它是用數次數學出來的。

底下全部是純 Python、沒有任何相依套件——tokenizer 本身大約一百行，另外還有測試——而 python bpe.py 會把這篇文章裡每一個量出來的數字印出來。

同一句話有四種長度

"the cost of a model call is counted in tokens"
10 個詞、45 個字元、45 個位元組、12 個 token
the | cost| of| a| model| ca|ll| is| count|ed| in| tokens

這四個數字沒有任何一個能從另一個算出來。計費用的是最後一個，context window 量的是最後一個，而唯一能算出最後一個的東西，就是 tokenizer 本身。

看 call。它被切成 ca 和 ll，因為這份語料從來沒讓 call 常到可以合併。這不是壞掉——但模型永遠不會看到 call 這個詞，它看到的是兩個碎片，而那兩個碎片在別的地方代表別的東西。

一切都先變成位元組

byte-level 的 tokenizer 一開始就把 256 個可能的位元組全部放進 vocabulary。這讓它是「全函數」的：任何輸入都表示得出來，不存在 unknown token 的問題。代價換到了別的地方。

   'a'  1 個位元組  [97]                 -> 1 個 token
   'é'  2 個位元組  [195, 169]           -> 2 個 token
   '模'  3 個位元組  [230, 168, 161]      -> 3 個 token
  '🙂'  4 個位元組  [240, 159, 153, 130] -> 4 個 token

在這個 tokenizer 上，'模型看到的從來不是你的文字' 是 13 個字元、39 個位元組、32 個 token；英文的 'what the model sees is never your text' 是 38 個字元、38 個位元組、17 個 token。大致相同的一句話，中文那句花了 1.9 倍的 token，而換算成每個字元是 2.46 對 0.45——5.5 倍。原因是 UTF-8 和訓練語料，不是模型。

訓練只有三行

數語料裡每一對相鄰符號。把最常出現的那一對合併成一個新符號。重複。

  #         pair   count   new token
  1    (32, 116)      41   ' t'
  2   (101, 110)      29   'en'
  3   (101, 114)      29   'er'
  4    (32, 105)      26   ' i'
  5   (256, 104)      21   ' th'
  6    (99, 111)      20   'co'
  7   (111, 107)      17   'ok'
  8   (262, 257)      16   'oken'

第五輪把 ' t'（它自己是第一輪的產物）跟 h 合起來。第八輪更是把兩個已經合併過的符號 ok 和 en 合成 oken。合併可以疊在合併上面，token 就是這樣從位元組長成整個詞的。

在這份語料上它跑了 143 次合併、停在 vocabulary 399，因為已經沒有任何一對出現超過一次：合併只出現一次的東西，只會讓 vocabulary 變大而文字一點都沒變短。

合併是照做出來的順序存下來的，而那個順序就是 tokenizer。編碼不過是把它重播一次。

Silent failure #1：最高票通常不只一個

看上面第二、第三輪。'en' 和 'er' 都出現 29 次。演算法說「合併最常出現的那一對」，而最常出現的有兩個。

這份語料的 143 個合併步驟裡，有 123 步（86%）在最高票上是平手的。

挑哪一個都說得過去。但挑完之後，那一對附近的計數都會變，兩個 tokenizer 從這裡開始分家。換別的平手規則重跑一次會得到 141 到 143 次合併、500 到 504 個 token：它們壓縮的結果只差幾個 token，而且對「什麼是一個 token」給出不同的答案。

所以平手規則不是實作細節，它是規格的一部分：

best = max(counts.items(), key=lambda kv: (kv[1], -kv[0][0], -kv[0][1]))[0]

第一個欄位是次數，後面兩個是平手規則。沒有它們，max 掃一個 dict 時follow的是插入順序，你的 vocabulary 就變成「你在哪個 Python 上跑的」的函數。挑最高票又要有明確平手規則，就是後面的 LeetCode 692。

編碼是照 rank 重播，不是最長匹配

' counted' 從 8 個位元組開始
套用第  6 號合併（'c' + 'o'）：   ' ' 'co' 'u' 'n' 't' 'e' 'd'
套用第 15 號合併（' ' + 'co'）：  ' co' 'u' 'n' 't' 'e' 'd'
套用第 19 號合併（'n' + 't'）：   ' co' 'u' 'nt' 'e' 'd'
套用第 25 號合併（'u' + 'nt'）：  ' co' 'unt' 'e' 'd'
套用第 32 號合併（' co' + 'unt'）：' count' 'e' 'd'
套用第 34 號合併（'e' + 'd'）：   ' count' 'ed'

每一步套用的是「現在還在的相鄰組合裡 rank 最小 的那一個」——也就是最早被學到的那一個——而不是 vocabulary 裡最長的匹配。

這件事比看起來重要。你只把 token 的字串表交給別人，他可以寫出一個最長匹配的 tokenizer，在同一個 vocabulary 上產生不同的輸出。所以跟著模型一起發佈的是那份有順序的合併清單，不是只有字串。

Silent failure #2：一個一個 token 解碼

'模型看到的' 是 15 個位元組、13 個 token，而其中 12 個單獨拿出來不是合法的 UTF-8——三個位元組的字被切在 token 邊界上是常態。

先把位元組接起來，再 decode 一次：   '模型看到的'

圖上畫的是 '€5 café €9' 而不是那句中文——同一件事，但換成圖的字型畫得出來的字元。那串是 15 個位元組、13 個 token，其中 8 個單獨不是合法 UTF-8。

第二行就是 [vocab[i].decode(errors='replace') for i in ids] 會給你的東西，而 errors='replace' 正是它不丟例外的原因。逐 token 串流輸出時最容易撞到這個：正確的修法是把還沒構成完整字元的位元組留在手上，不是用 replace 蓋過去。

一個 tokenizer 最該測的性質就是 round trip——encode、decode、比對位元組。check() 對十二種不同的字串做了 round trip，包括空字串、單一空格、emoji 和重複 500 次的字元，另外還檢查五件事：id 連續、每個合併出來的 token 等於它的兩個來源接起來、以及重跑一次會得到同一份合併清單。

Silent failure #3：那條 regex 決定了什麼可以當 token

在開始數任何東西之前，文字會先被切成「合併不准跨過去」的塊：

PRETOKEN = re.compile(r"""'(?:[sdmt]|ll|ve|re)| ?[^\W\d_]+| ?\d{1,3}| ?[^\s\w]+|\s+""")

把這一步拿掉——整份語料當成一塊——結果是：

                    合併次數  token 數  tokens/byte  中間有空格的 token
------------------  --------  --------  -----------  ------------------
一整塊，沒有 regex  144       502       0.3934       12
有 pre-tokenise     143       500       0.3918       0

壓縮率幾乎一樣。變的是什麼算一個 token：沒有 regex 的話，144 個合併裡有 12 個產生了中間夾著空格的 token，例如 ' is not '、't in'、't is '、' the tokeniz'。

這種 token 會讓一個詞取決於它後面接什麼，於是同一個詞在不同句子裡拿到不同的 id，模型得把它學兩次。那條 regex 不是優化，它是約束。裡面出力最多的兩條規則是「開頭的空格跟著後面那個詞」和「連續數字切成最多三位一組」：

     '7' -> 1 個 token   ['7']
   '128' -> 2 個 token   ['1', '28']
  '1280' -> 3 個 token   ['1', '28', '0']
'128000' -> 3 個 token   ['1', '28', '000']

最後那一行就是模型算術很奇怪的原因。1280 和 128000 並不是以數字的形式存在的，它們是幾個碰巧長得很像的碎片。

vocabulary 大小買到了什麼

vocab  合併次數  token 數  tokens/byte
-----  --------  --------  -----------
256    0         1276      1.0000
300    44        767       0.6011
350    94        598       0.4687
399    143       500       0.3918

256 的時候完全沒有合併，一個 token 就是一個位元組。143 次合併之後，同一段文字短了 61%。曲線會變平，是因為這是貪婪演算法，每一步都先拿走當下最大的那筆節省，所以後面的節省只會越來越小。真正的 tokenizer 把同一個迴圈跑到 50,000–200,000 個 token、資料量是好幾百 GB；形狀一模一樣，只是平掉的位置在很後面。

跟 Day 38 同一個貪婪動作，只是從次數表的另一端

Day 38 建 Huffman code 的方法是反覆合併最不常出現的兩個符號。BPE 反覆合併最常出現的那一對。兩個都是貪婪、都是合併，而它們在解不同的問題。

  • Huffman 在這些位元組上：每個位元組 4.6928 bits，所以語料用 749 個位元組裝得下，原本是 1,276。字母表沒變，是編碼變短了。
  • BPE 做了 143 次合併：每個位元組 0.3918 個 token，所以 1,276 個位元組變成 500 個 token。序列變短了，字母表長到 399。

Huffman 是在固定字母表下最佳化「線路上的位元數」。BPE 是在「成本按 token 計價」的模型下最佳化序列長度，而且它可以發明新符號。兩者誰也做不了對方的工作：Huffman code 不是模型能 embed 的整數，而 BPE 的 token 傳輸起來並沒有比較短。

LeetCode 692 - Top K Frequent Words（前 K 個高頻詞）

題意。 給一串單字，回傳出現次數最多的 k 個，次數多的排前面。兩個字次數一樣時，字母序小的排前面。

輸入／輸出。 一個字串串列和一個整數 k。回傳 k 個字串，順序照上面的規則。

範例。 ["i", "love", "leetcode", "i", "love", "coding"]、k = 2，答案是 ["i", "love"]。兩個字都出現兩次，所以由平手規則決定："i" 字母序在 "love" 前面。另一個例子 ["the", "day", "is", "sunny", "the", "the", "the", "sunny", "is", "is"]、k = 4，答案是 ["the", "is", "sunny", "day"]——"the" 4 次、"is" 3 次，而 "sunny" 和 "day" 是靠次數分出來的，不是靠平手規則。

限制。 1 <= words.length <= 500，每個字是 1 到 10 個小寫字母，k 介於 1 和相異字數之間。follow-up 要求 O(n log k) 時間、O(n) 空間——就是這一條排除了「全部排序」而逼出 heap。

關鍵動作。 一個排序 key 同時裝下兩條規則：(-count[w], w)，次數遞減、字串遞增。

陷阱。 heap 版本才是有趣的地方，也是 vocabulary 很大時你真正要的版本。size-k 的 min-heap 必須淘汰最差的候選，而這裡「最差」是指次數最少、同次數時字母序最後的那一個。所以次數要正著比、字串要反著比。(count, word) 這樣的 tuple 表達不了這件事——你得包一層把 __lt__ 反過來的類別，或是把次數取負配 max-heap。

這就是 BPE 合併迴圈變成面試題的樣子：找出最常出現的那個、照一條你寫下來的規則處理平手、再做一次。

class Solution:
    def topKFrequent(self, words: list[str], k: int) -> list[str]:
        count = Counter(words)
        # one key, both rules: falling on the count, rising on the word
        return sorted(count, key=lambda w: (-count[w], w))[:k]

LeetCode 394 - Decode String（字串解碼）

題意。 把一個編碼過的字串展開，其中 k[substring] 表示那段子字串重複 k 次。括號可以巢狀。

輸入／輸出。 一個字串，回傳展開後的字串。

範例。 "3[a]2[bc]" 變成 "aaabcbc"。"3[a2[c]]" 變成 "accaccacc"：裡層的 2[c] 展開成 cc，讓本體變成 acc，外層的 3[...] 再把它重複三次。"2[abc]3[cd]ef" 變成 "abcabccdcdcdef"——注意 ef 是落在展開之後，不是裡面。

限制。 1 <= s.length <= 30，數字給出的重複次數介於 1 到 300，而且輸入保證合法——沒有落單的括號，方括號裡也不會有數字（除了當重複次數）。「保證合法」這一條，就是讓你可以完全不做錯誤處理、七行寫完這個迴圈的原因。

關鍵動作。 一個 stack，每遇到一個 [ 就推兩樣東西進去：目前累積好的字串，以及等著後面那段文字的重複次數。在 ] 到達之前什麼都不展開——這就是巢狀情況不用遞迴也能work的原因。

範例刻意要露出來的兩個細節。 次數可能是多位數，所以必須寫 num = num * 10 + int(ch) 而不是 num = int(ch)，否則 12[a] 會只重複兩次。以及括號收掉之後，字元會繼續接在同一個 buffer 上，這就是第三個例子的 ef 會出現在正確位置的原因。

它就是 decoder 的形狀：一邊是一串扁平的序列，另一邊是比較長的字串，而展開完全由一張表驅動。tokenizer 的 decode 就是沒有巢狀的同一招。

class Solution:
    def decodeString(self, s: str) -> str:
        stack, cur, num = [], '', 0
        for ch in s:
            if ch.isdigit():
                num = num * 10 + int(ch)       # counts can be multi-digit
            elif ch == '[':
                stack.append((cur, num))
                cur, num = '', 0
            elif ch == ']':
                prev, times = stack.pop()
                cur = prev + cur * times
            else:
                cur += ch
        return cur

這一天為什麼重要

模型吃進去和吐出來的每一個數字都是 token，而 tokenizer 是整條流程裡唯一決定「什麼是一個 token」的地方。帳單從這裡來、context window 從這裡被花掉，而且相當多看起來很怪的模型行為也是從這裡開始的——在數字碎片上做算術、一個 prompt 因為多打一個空格而表現不同、某個語言每個字元的成本是另一個語言的五倍。

而它在結構上又是整個 stack 裡最簡單的東西：數 pair、合併最常出現的、把順序寫下來。複雜的不是演算法，是演算法替你安靜決定掉的那四個地方——平手規則、重播順序、位元組邊界，以及在這一切之前先跑的那條 regex。
