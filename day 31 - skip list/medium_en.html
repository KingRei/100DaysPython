Skip list: an ordered map built out of coin flips

Code: day 31 on GitHub

100 Days of Python - day 31

Redis has a data type that keeps millions of members sorted by score, answers "what rank is this member" in microseconds, and can hand you elements 1000 through 1020 of the ordering without touching the other 999,980. There is no tree in it. There is a linked list, a few sparser copies of that list stacked on top, and a coin.

Yesterday's caches were about forgetting things on purpose. Today is about the opposite: a structure that keeps everything in order and still answers questions quickly - without any of the rotation machinery day 28 needed to stay balanced.

The problem: order is not enough

A sorted array can be binary searched. A sorted linked list has exactly the same order and cannot be binary searched at all, because bisection needs to land in the middle and a list only lets you walk there. In the module, searching for 198 among 100 sorted keys takes 7 probes in the array and 99 hops in the list.

So the missing ingredient is not order, it is the ability to take a big step. A skip list adds exactly that and nothing else: keep the sorted list as level 0, and put sparser copies of it above as express lanes.

Search starts on the top lane and does two things forever: move right while the next key is still smaller than the target, drop a level when it is not. Every drop happens at a node already known to be below the target, so no part of the list is ever walked twice. The path is a staircase going down and to the right.

The part that is actually clever: heights are random

The obvious way to build lanes is regularly - every second node on level 1, every fourth on level 2. It searches beautifully and it is unmaintainable. Insert one key at the front and every other key's parity flips; in the 16-key example in the module, all 16 nodes change level.

So a skip list does not compute heights. Each node flips a coin when it is created: keep flipping while heads, stop at the first tail. That height is fixed for the node's whole life.

def random_level(self):
    lvl = 1
    while self.rng.random() < self.p and lvl < self.max_level:
        lvl += 1
    return lvl

This is the trade day 28 refused to make. AVL and red-black trees earn their balance by rotating on every insert, and pay for it with parent pointers, colour bits and four cases of fixup code. A skip list buys its balance from probability. There is no rebalancing code at all - and, pleasantly, no adversarial input either: the shape depends on the coin, not on the keys, so no ordering of insertions can degenerate it.

One traversal, three operations

Search, insert and delete all walk the same staircase, so it is written once:

def _descend(self, key):
    update, rank = [None] * self.max_level, [0] * self.max_level
    node = self.head
    for i in range(self.level - 1, -1, -1):
        rank[i] = 0 if i == self.level - 1 else rank[i + 1]
        while node.forward[i] is not None and node.forward[i].key < key:
            rank[i] += node.span[i]       # count what this hop flew over
            node = node.forward[i]
        update[i] = node                  # the pointer that may be rewritten
    return update, rank, node.forward[0]

update[i] is the last node on level i that is still strictly below the key - which is precisely the node whose forward pointer has to change if we insert here. Insert then splices the new node into the first lvl levels of update, and delete unlinks it from wherever it appears. Neither needs to search again.

On the 16-key list in the module, search(13) finds its answer in 2 hops and a miss like search(99) costs 3.

Spans: the same walk, now returning positions

Give every forward pointer a second number - how many level-0 nodes it flies over - and the walk you already do starts answering a different question for free. Add up the spans of the hops taken to reach key 13: 10 + 2 + 1 = 13, so its 0-based rank is 12. That is Redis's ZRANK. Run the sums the other way - descend while the accumulated span stays below k - and you get select(k), which is ZRANGE by index.

The line everyone forgets

for i in range(lvl):                      # levels the new node reaches
    node.forward[i] = update[i].forward[i]
    update[i].forward[i] = node
    node.span[i] = update[i].span[i] - (rank[0] - rank[i])
    update[i].span[i] = (rank[0] - rank[i]) + 1

for i in range(lvl, self.level):          # levels ABOVE the new node
    update[i].span[i] += 1

The second loop is easy to drop, because those levels need no pointer change whatsoever: they fly straight over the new node without noticing it. But that is exactly the problem - they now fly over one more node than before, so their count is short by one.

Delete the loop and run every test you can think of for an ordered set. keys() matches a correct list. search() matches a correct list. range() matches a correct list. Nothing raises, nothing is out of order. rank() is wrong on 197 of 200 keys, starting at key 3, which confidently reports rank 0 instead of 3 - and because a short span is inherited by everything after it, one missing bump poisons the whole tail of the ordering.

I like this bug because of what it says about testing. The forward pointers and the spans are two independent invariants living in the same node, and only one of them has a test that anyone naturally writes.

Why Redis flips an unfair coin

With promotion probability p, a node carries 1 / (1 - p) forward pointers on average and the walk has about log n / log(1/p) levels to get through. Over 20,000 keys and 2,000 searches:

p     pointers/node  theory  top level  avg steps
----  -------------  ------  ---------  ---------
0.5   2.00           2.00    15         14.1
0.25  1.34           1.33    8          19.1
0.1   1.11           1.11    6          29.2

Redis's t_zset.c sets ZSKIPLIST_P to 0.25 and ZSKIPLIST_MAXLEVEL to 32. Against a fair coin that keeps a third of the optional pointers - 0.34 per node instead of 1.00, on top of the one pointer every node must have - in exchange for 35% more hops. Memory is paid by every node; hops are paid only by a query, and a sorted set has far more members than it has queries in flight.

Three more details of the Redis structure follow from what a sorted set has to do. Level 0 carries a backward pointer as well, because ZREVRANGE walks the other way. Nodes are ordered by score and then by member, which is what gives ZRANGEBYLEX a meaning when all the scores are equal. And below zset-max-listpack-entries - 128 by default - there is no skip list at all: a flat listpack gets scanned, because for a handful of members the pointers cost more than the walk saves.

LeetCode 1206: the comparison that has to be strict

Design Skiplist allows duplicates, and erase must remove exactly one copy. That requirement alone decides the comparison:

while node.fw[i] and node.fw[i].val < target:   # strictly <, never <=
    node = node.fw[i]

With < the walk stops in front of the first copy, so the candidate node is the first copy and erase unlinks exactly that one. With <= the walk sails past all three copies of a 3 and stops in front of 5, and erase(3) reports that 3 is not in the list - while three of them sit there in plain sight. Same flavour as the span bug: sorted, uncrashed, wrong.

LeetCode 315 - count of smaller numbers after self - falls out of spans instead. Insert the array from the right and ask count_less(x) before each insert. It reproduces the Fenwick tree answer from day 29 exactly, which is the interesting part: a Fenwick tree counts prefixes over value indices and needs the values compressed into a small range first, while a skip list counts prefixes over the values themselves and does not.

The same idea, in a space with no order

The lanes are not really about sorted keys. They are about approaching something with big strides and finishing with small ones, and that idea survives when "sorted" stops meaning anything - which is what HNSW, the index inside most vector databases, is.

HNSW draws each node's top layer from floor(-ln(U) * mL) with mL = 1 / ln(M): the same geometric distribution, written for a continuous random variable. Upper layers are sparse and searched greedily; the bottom layer is searched with a beam of width ef. That beam is the one real difference, and it exists because a line cannot trap a greedy walk but a metric space can - you can be closer to the query than all your neighbours and still be nowhere near the answer.

The toy version in the module keeps recall at 1.00 while the work stays nearly flat:

n      layers  recall@1  HNSW distances  brute force  speedup
-----  ------  --------  --------------  -----------  -------
500    4       1.00      10,146          50,000       4.9x
2,000  5       1.00      12,316          200,000      16.2x
8,000  5       1.00      13,655          800,000      58.6x

16x the data, 1.1x the work. When a RAG pipeline retrieves documents by embedding similarity, this is the structure doing it - the skip list's O(log n) staircase, carried into a space where nothing can be sorted.

Complexity

Operation                        Time                  Space
-------------------------------  --------------------  -------------
search / insert / delete         O(log n) expected     O(n) expected
rank / select / countless        O(log n) expected     -
range(lo, hi)                    O(log n + k)          -
forward pointers per node        1 / (1 - p) expected  -
sorted linked list, same search  O(n)                  O(n)

Appendix: the LeetCode problems in full

Restated in my own words - what is being asked, what goes in and comes out, one worked example, and the constraints that actually change which algorithm is allowed.

LeetCode 1206 - Design Skiplist

The task. Implement a skip list from scratch, without using any built-in balanced-tree or sorted-container library. It must support search(target) returning a boolean, add(num) inserting a value (duplicates are allowed, so the same number can be present several times), and erase(num) removing one occurrence and returning whether anything was removed.

Input / output. Operation list in, booleans out of search and erase.

Example. add(1), add(2), add(3), search(0) → False, add(4), search(1) → True, erase(0) → False, erase(1) → True, erase(1) → False.

Constraints. 0 <= num, target <= 2 * 10^4, up to 5 * 10^4 calls. Duplicates are the trap: the comparison used while descending the levels has to be a strict <, not <=, or erase will delete the wrong copy and add will place duplicates on the wrong side.

leetcode.com/problems/design-skiplist

LeetCode 315 - Count of Smaller Numbers After Self

The task. For every position i, count how many elements to the right of nums[i] are strictly smaller than it, and return those counts as an array.

Input / output. Input is nums; output is a list of the same length.

Example. nums = [5,2,6,1] → [2,1,1,0]: to the right of 5 sit 2 and 1; to the right of 2 sits 1; to the right of 6 sits 1; nothing is to the right of 1.

Constraints. 1 <= len(nums) <= 10^5, values in [-10^4, 10^4]. The quadratic double loop is 10^10 operations, so it will not pass. Scanning from the right while inserting into a Fenwick tree indexed by value gives O(n log U); a merge sort that counts inversions, or an order-statistic skip list, get there too.
