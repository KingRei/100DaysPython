LRU and LFU caches: choosing what to throw away

Code: day 30 on GitHub

100 Days of Python - day 30

Here is a cache policy with a hit rate of exactly zero percent. Not "poor", not "0.3%" - zero. It is a correct, textbook LRU cache, running a workload that fits in thirty-three keys while the cache holds thirty-two. Every lookup misses. Every insert evicts precisely the key the next lookup is about to ask for. Nothing is broken, nothing raises, and the cache does a great deal of work to achieve nothing at all.

That failure, and its mirror image on the other main policy, is the whole reason this page is not simply "here is LeetCode 146, see you tomorrow".

Yesterday's segment trees answered questions about data that keeps changing. A cache is a different bargain: it answers questions about data that is expensive, by remembering answers it has already paid for. The remembering half is day 09's hash table. The interesting half is the one line that runs only when memory is full - which entry do we throw away?

The ceiling nobody can reach

Before comparing policies it helps to know what perfect looks like. Bélády's MIN evicts the entry whose next use is furthest in the future. It is optimal, provable, and unimplementable, because it needs the whole request sequence up front. Offline, though, we have the sequence - so it costs one right-to-left scan:

def belady_hits(trace, capacity):

    seen = {}

This turns "is our policy any good?" from an argument into a number. On the skewed workload later in this article, the best online policy reaches 71.6% where MIN reaches 79.0%. That seven-point gap is not a bug to be fixed; it is the price of not knowing the future.

LRU: a hash map welded to a doubly linked list

LRU bets that what was used recently will be used again, so it needs two abilities at once: find a key instantly, and find the least recently used entry instantly. No single structure does both, so it carries two.

def get(self, key):
    node = self.map.get(key)
    if node is None:
        return -1
    self._unlink(node)                 # a read IS a use
    self._push_front(node)
    return node.val

def put(self, key, value):
    if key in self.map:
        node = self.map[key]; node.val = value
        self._unlink(node); self._push_front(node); return
    if len(self.map) == self.capacity:
        victim = self.tail.prev        # least recent, always right there
        self._unlink(victim)
        del self.map[victim.key]
    node = Node(key, value)
    self.map[key] = node
    self._push_front(node)

The map answers where, the list answers who is oldest, and the victim is never searched for - it sits at tail.prev by construction. Two sentinel nodes at the ends delete every null check inside _unlink. And move_to_end plus popitem(last=False) on an OrderedDict are this exact structure with the pointer dance already compiled.

The bug that does not announce itself

Delete the two refresh lines inside get and the cache still compiles, still runs, still passes any test that only checks returned values. What changes is the meaning of the list: it now records when each key arrived rather than when it was used. LRU has silently become FIFO.

On the same call script, the two evict different keys. That is all the symptom you get - no exception, no warning, just a slightly worse hit rate in production and a wrong answer on the judge. The single most useful habit here is to remember that in a recency cache, a read is a use.

Why two structures instead of one

A list-only LRU is correct: search the list for the key, move it to the front. It is also quadratic. Over 40,000 operations against a 2,000-slot cache the list version scans 19.1 million cells and runs about 9.5x slower than the linked-list version. Writing it once, badly, is the cheapest way to understand why every real implementation carries a map and a list.

LFU: buckets, and a minimum that never searches

LFU bets on popularity instead of recency: evict whichever entry has been used least often. That sounds like it requires a heap, or a scan for the minimum count. It requires neither, and the reason is a one-line observation: a count only ever changes by one.

self.buckets = defaultdict(OrderedDict)   # count -> keys, least recent first
self.min_freq = 0

def _bump(self, key):
    f = self.freq[key]
    del self.buckets[f][key]
    if not self.buckets[f]:                       # the min bucket just emptied
        del self.buckets[f]
        if self.min_freq == f:
            self.min_freq = f + 1
    self.freq[key] = f + 1
    self.buckets[f + 1][key] = None               # newest at the back

min_freq moves in exactly two situations: it steps up to f + 1 when a hit empties the bucket that was the minimum, and it resets to 1 when a new key arrives, because a newcomer has earned nothing yet. There is no third case. That is where the O(1) comes from - not from a clever structure, but from the fact that the minimum can never jump.

Inside a bucket, order matters. Keys tied on count are broken by recency, oldest use first - and LeetCode 460 tests it. A version that breaks ties by insertion order passes every value-level check and still returns different keys:

cache.put(1, 1); cache.put(2, 2)
cache.get(2); cache.get(1)      # both at count 2; key 2 is the older use
cache.put(3, 3)                 # evicts... which one?

# LFU with LRU tie-break  -> get(1) = 1,  get(2) = -1     (what LC 460 wants)
# LFU by insertion order  -> get(1) = -1, get(2) = 2

Strip the values away and what remains - a sorted chain of count buckets, each holding a set of keys - is LeetCode 432 by itself. inc, dec, getMaxKey, getMinKey, all O(1), because the destination bucket is always the neighbour and the extremes are the two ends of the chain.

The two ways these policies fail

Four synthetic workloads, 32 slots, opt being Bélády's offline ceiling:

workload                  opt    lru    lfu    fifo   mru    slru
------------------------  -----  -----  -----  -----  -----  -----
zipf (skewed popularity)  79.0%  63.2%  71.6%  57.6%  22.2%  69.5%
scan (loop of 33 keys)    96.1%  0.0%   0.0%   0.0%   96.1%  0.0%
shifting hot set          95.7%  94.9%  26.8%  94.8%  27.3%  30.5%
hot set + cold scans      77.0%  64.1%  76.6%  55.6%  16.7%  76.4%

Scan pollution is the zero row.

A loop over 33 keys through 32 slots: each miss evicts the oldest entry, which is exactly the key the next request wants. The policy is in lockstep with the workload and one step behind it forever.

The instructive part is the rest of that row. LFU is also at zero, and SLRU with it - because nothing is ever touched twice, no counter ever rises, and no entry ever earns protection. Frequency cannot help when there is no frequency. Only MRU survives, at 96.1%, by doing the apparently idiotic thing: throwing away the entry it just inserted, sacrificing the same slot repeatedly so that the rest of the working set lives.

LFU stickiness is the other one. When the hot set moves - a new set of keys is hot in each phase - LFU falls to 26.8% while LRU holds 94.9%. Those counters are the scoreboard of a popularity contest that finished, and yesterday's champions squat in the cache against today's traffic. Real LFU implementations age their counters, or refuse to trust the count alone.

Nothing in the table wins everywhere. That is not a gap in the table; it is the actual result.

Which is why sglang ships five of them

python/sglang/srt/mem_cache/evict_policy.py declines to pick a winner. The five strategies are five key functions over one shared heap:

LRUStrategy   ->  node.last_access_time
LFUStrategy   ->  (node.hit_count, node.last_access_time)
FIFOStrategy  ->  node.creation_time
MRUStrategy   ->  -node.last_access_time
SLRUStrategy  ->  (node.hit_count >= threshold, node.last_access_time)

victim = heapq.nsmallest(1, entries, key=strategy.get_priority)[0]

Chosen at launch with --radix-eviction-policy {lru,lfu,fifo,mru,slru}. Every node stores the same three fields; the policy is expressed as how to compare, not as five data structures. Adding one is a lambda, and the zero-percent disaster above becomes a flag rather than a rewrite.

SLRU is the compromise visible in the last row: an entry becomes protected once it has been hit twice, which is worth twelve points over LRU on "hot set + cold scans" (64.1% to 76.4%) without inheriting LFU's stickiness on the shifting one.

Why this matters later

This machinery is not decoration around an inference server - it is load-bearing. The KV cache stores the attention keys and values already computed for every prompt prefix, so a request that shares a prefix with an earlier one can skip recomputing it. A radix tree (day 24) finds the longest shared prefix. And when GPU memory fills, something has to go - chosen by exactly the policies above, applied to tree nodes instead of plain keys.

The stakes are different there. Evicting a key from a web cache costs you a database round trip. Evicting a prefix node costs you the GPU time that computed it, and a scan-shaped workload - many unrelated prompts arriving back to back - is precisely the pattern that drives a pure LRU tree to zero reuse. That is why the policy is a launch flag: the right answer depends on traffic that the engine cannot see in advance.
