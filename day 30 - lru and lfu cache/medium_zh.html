Day 30 — LRU 與 LFU 快取：滿了的時候丟掉誰

程式碼：day 30 on GitHub

100 Days of Python - day 30

先給一個數字：命中率 0.0%。不是「不太好」，不是 0.3%，是剛好零。而且它是一個完全正確、照教科書寫的 LRU 快取，只是工作負載是一個 33 個 key 的迴圈，而快取有 32 格。每一次查詢都 miss，每一次插入丟掉的，都剛好是下一次要問的那個 key。程式沒壞、沒噴錯，只是忙了半天什麼也沒接住。

這個失敗，加上另一個主流策略上完全對稱的失敗，就是今天不只是「這是 LeetCode 146，明天見」的原因。

昨天的區間結構處理的是「資料一直在變」的查詢。快取換的是另一種帳：它處理的是「算起來很貴」的東西，靠記住已經付過的答案。記住的那一半就是 Day 09 的 hash table，沒別的。真正有趣的是只有在記憶體滿掉時才會跑的那一行——要丟掉哪一個？

先看看天花板長什麼樣

比較策略之前，得先知道「完美」是多少。Bélády's MIN 丟掉的是「下一次使用離現在最遠」的那一個。它是最佳解、可以證明，而且不可能實作，因為它要先知道整串請求。不過離線分析時我們手上就有整串，所以它只要從右往左掃一遍：

這讓「我們的策略到底好不好」從嘴砲變成數字。在後面那個偏態工作負載上，最好的線上策略拿到 71.6%，MIN 拿到 79.0%。中間那 7 個百分點不是 bug，那是「不知道未來」的定價。

LRU：hash map 焊上一條雙向串列

LRU 賭的是「最近用過的還會再用」，所以它同時需要兩種能力：瞬間找到某個 key，以及瞬間找到最久沒用的那個。沒有單一結構能同時做到，所以它帶兩個。

def get(self, key):
    node = self.map.get(key)
    if node is None:
        return -1
    self._unlink(node)                 # 讀也算用過
    self._push_front(node)
    return node.val

def put(self, key, value):
    if key in self.map:
        node = self.map[key]; node.val = value
        self._unlink(node); self._push_front(node); return
    if len(self.map) == self.capacity:
        victim = self.tail.prev        # 最久沒用的，它本來就在那
        self._unlink(victim)
        del self.map[victim.key]
    node = Node(key, value)
    self.map[key] = node
    self._push_front(node)

map 回答「在哪裡」，串列回答「誰最舊」，而受害者從來不用找——照定義它就坐在 tail.prev。頭尾兩個 sentinel 節點讓 _unlink 裡一個 null 檢查都不用寫。至於 OrderedDict 的 move_to_end 和 popitem(last=False)，就是同一組指標動作，只是已經編譯成 C 了。

不會自己舉手的 bug

把 get 裡那兩行刷新刪掉，程式照樣編譯、照樣跑、任何只檢查回傳值的測試照樣過。改掉的是串列順序的意義：它現在記的是每個 key 進來的時間，而不是被用的時間。LRU 就這樣悄悄變成了 FIFO。

同一串呼叫跑下去，兩者丟掉的 key 不一樣——而這就是你能拿到的全部症狀。沒有例外、沒有警告，只有生產環境上稍微差一點的命中率，和 judge 上一個錯誤答案。這裡最值得養成的習慣只有一句：在 recency 快取裡，讀也算用過。

為什麼要兩個結構

只用一個 list 的 LRU 也是對的：在 list 裡找到 key，搬到最前面。它同時也是平方級的。在 2000 格的快取上跑 40,000 次操作，list 版本掃了 1910 萬格，比串列版本慢大約 9.5 倍。花十分鐘把慢的那版寫一次，是理解「為什麼每個真實實作都同時帶 map 和 list」最便宜的方法。

LFU：一個次數一格，而且最小值永遠不用找

LFU 賭的不是最近而是熱門：丟掉被用最少次的那個。聽起來需要一顆 heap，或是掃一遍找最小次數。其實兩個都不用，理由只有一句話：次數一次只會變動 1。

self.buckets = defaultdict(OrderedDict)   # 次數 -> keys，最舊的排前面
self.min_freq = 0

def _bump(self, key):
    f = self.freq[key]
    del self.buckets[f][key]
    if not self.buckets[f]:                       # 最小那格剛好被清空
        del self.buckets[f]
        if self.min_freq == f:
            self.min_freq = f + 1
    self.freq[key] = f + 1
    self.buckets[f + 1][key] = None               # 新的放後面

min_freq 只有兩種變法：命中把原本的最小格清空時變成 f + 1，以及插入新 key 時重設回 1（剛進來的東西還沒有任何資格）。沒有第三種情況。O(1) 就是從這裡來的——不是靠什麼精巧的結構，而是因為最小值不可能跳號。

同一格裡面的順序也有講究：次數相同時比最久沒用，舊的先死——LC 460 會考。改成「先插入的先丟」的版本，所有只看數值的檢查都會過，但回傳的 key 不一樣：

cache.put(1, 1); cache.put(2, 2)
cache.get(2); cache.get(1)      # 兩個都在 count 2；key 2 是比較舊的那次使用
cache.put(3, 3)                 # 丟掉誰？

# LFU + LRU 平手規則 -> get(1) = 1,  get(2) = -1     （LC 460 要的）
# LFU + 先插入先丟   -> get(1) = -1, get(2) = 2

把 value 拿掉，剩下的東西——一條按次數排好的 bucket 鏈，每格裝著一組 key——本身就是 LeetCode 432。inc、dec、getMaxKey、getMinKey 全部 O(1)，因為目標格永遠是隔壁，而最大最小就是鏈的兩端。

這兩種策略各自會死在哪

四個合成工作負載，32 格，opt 是 Bélády 的離線天花板：

掃描污染就是那排零。

33 個 key 繞 32 格：每次 miss 丟掉最舊的那個，而那個剛好就是下一個請求要的。策略和工作負載完全同步，而且永遠慢一步。

這排真正值得看的是其他欄。LFU 也是零，SLRU 也是零——因為沒有任何 key 被用到第二次，沒有計數器會上升，也就沒有任何 entry 能取得保護。沒有 frequency 的時候，frequency 幫不上忙。活下來的只有 MRU（96.1%），靠的是看起來很蠢的做法：丟掉剛剛才放進去的那一個，反覆犧牲同一格，讓其他的 working set 活著。

LFU 的黏性是另一種死法。當熱點會移動（每個階段熱的是另一組 key），LFU 掉到 26.8%，LRU 還有 94.9%。那些計數器是一場已經結束的人氣比賽的記分板，昨天的冠軍佔著位子不走。真實世界的 LFU 因此都會讓計數器老化，或者乾脆不單獨相信次數。

表格裡沒有任何一欄到處都贏。這不是表格做得不好，這就是結論。

所以 sglang 直接給你五種

python/sglang/srt/mem_cache/evict_policy.py 拒絕選邊站。五種策略就是同一顆 heap 上的五個 key function：

LRUStrategy   ->  node.last_access_time
LFUStrategy   ->  (node.hit_count, node.last_access_time)
FIFOStrategy  ->  node.creation_time
MRUStrategy   ->  -node.last_access_time
SLRUStrategy  ->  (node.hit_count >= threshold, node.last_access_time)

victim = heapq.nsmallest(1, entries, key=strategy.get_priority)[0]

啟動時用 --radix-eviction-policy {lru,lfu,fifo,mru,slru} 挑。每個節點存的欄位完全一樣，策略被寫成「怎麼比大小」，而不是五份資料結構。要加一種只是一個 lambda，而上面那個 0% 的災難也就變成一個參數，而不是一次重寫。

SLRU 是最後一排看得到的折衷：被命中兩次之後就進入保護區。在「熱點 + 冷掃描」上這值 12 個百分點（64.1% → 76.4%），同時不會繼承 LFU 在移動熱點上的黏性。

這些東西後面會用在哪

這套機制不是推論引擎旁邊的裝飾品，它是承重牆。KV cache 存的是每段 prompt 前綴已經算好的 attention key/value，所以跟舊請求共用前綴的新請求可以整段跳過不算。radix tree（Day 24）負責找出最長的共用前綴。而當 GPU 記憶體滿掉時，總得丟掉一些東西——丟誰，就是上面那幾條策略決定的，只是對象從單純的 key 換成樹的節點。

只是那邊的賭注不一樣。網頁快取丟掉一個 key，代價是多一趟資料庫。丟掉一個前綴節點，代價是當初算它的那段 GPU 時間；而「一堆彼此無關的 prompt 連續打進來」這種掃描形狀的流量，正好就是把純 LRU 的樹逼到零重用的那種模式。這也是為什麼它是一個啟動參數：正確答案取決於引擎事先看不到的流量。

LeetCode 146 - LRU Cache（LRU 快取）

題目。 設計一個固定容量的快取，提供 get(key) 與 put(key, value)。get 回傳值，key 不在 就回 -1。put 新增或覆寫；如果插入後超過容量，就淘汰最久沒被用到的 key。get 和 put 都算「用到」。

輸入／輸出。 建構子吃 capacity；get 回傳整數，put 沒有回傳值。

範例。 容量為 2：put(1,1)、put(2,2)、get(1) → 1，接著 put(3,3) 會淘汰 key 2 （因為 get(1) 剛剛把 key 1 刷新了），所以 get(2) → -1。

限制。 1 <= capacity <= 3000、0 <= key <= 10^4、0 <= value <= 10^5，最多 2 * 10^5 次呼叫。兩個操作都必須是平均 O(1)，這一條就把「掃過去找最舊的」或「對時間戳排序」全部排除， 只剩下 hash map 加雙向鏈結串列。

LeetCode 460 - LFU Cache（LFU 快取）

題目。 外型和 LRU 一樣，淘汰規則不同。每個 key 帶一個使用次數，對該 key 的每次 get 和 put 都加一。快取滿的時候，淘汰次數最小的 key；如果有多個並列，就淘汰其中最久沒用的那個。

輸入／輸出。 建構子吃 capacity；get 回傳值或 -1，put 沒有回傳值。

範例。 容量 2：put(1,1)、put(2,2)、get(1) → 1（此時 key 1 次數為 2、key 2 為 1）， put(3,3) 淘汰 key 2。之後 get(2) → -1、get(3) → 3。

限制。 0 <= capacity <= 10^4，key 與 value 最大到 10^9，最多 2 * 10^5 次呼叫，而且兩個 操作一樣要求平均 O(1)。這個 O(1) 就是整題的難處：找最小次數不能用搜尋 —— 所以標準解是 每個頻次各掛一條串列，再維護一個每次最多只動一格的 min_freq。

LeetCode 432 - All O`one Data Structure（全 O(1) 的資料結構）

題目。 設計一個存「字串 key → 正整數次數」的結構，支援四個操作：inc(key) 加一（key 不存在 就以次數 1 建立）、dec(key) 減一並在次數歸零時把 key 移除、getMaxKey() 回傳次數最大的任一個 key、getMinKey() 回傳次數最小的任一個 key。結構為空時兩個 getter 都回傳 ""。

輸入／輸出。 輸入操作串列，輸出兩個 getter 的字串。

範例。 inc("hello")、inc("hello")、getMaxKey() → "hello"、getMinKey() → "hello"， 再 inc("leet") 之後，getMaxKey() → "hello"、getMinKey() → "leet"。

限制。 1 <= len(key) <= 10，最多 5 * 10^4 次呼叫，而且 dec 保證只會用在目前存在的 key。 每個操作都必須是 O(1) —— 這是把 LFU 的桶子結構推到極致：一條由「次數桶」組成的雙向鏈結串列， 最大值和最小值就是兩端。
