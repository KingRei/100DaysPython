The tree that stores a shared prefix exactly once

Code: day 24 on GitHub

100 Days of Python - day 24

A hash set can tell you whether rubicon is in your dictionary. It cannot tell you that rubicon, rubicundus and ruber all start the same way, because hashing destroys exactly that information - it is designed to. If the question you actually have is "what do these strings have in common", you need a structure that keeps the prefix, and that structure is the trie.

Yesterday's binary search ended on sglang's galloping prefix match. Today is the tree that match was walking, and the last stop is the same cache one abstraction up: the thing that lets an inference server serve two requests with the same system prompt without computing that prompt twice.

One node per character

A trie stores one node per character. The root is the empty string, each edge is labelled with a single character, and walking down from the root spells a string out. A boolean on the node, is_word, says whether the string ending here was actually inserted.

class TrieNode:
    __slots__ = ("children", "is_word")

    def __init__(self):
        self.children = {}      # character -> TrieNode
        self.is_word = False


class Trie:
    def insert(self, word):
        node = self.root
        for ch in word:
            nxt = node.children.get(ch)
            if nxt is None:
                nxt = TrieNode()
                node.children[ch] = nxt
            node = nxt
        node.is_word = True

Look at what is not in that loop: no hash, no resize, no collision, no comparison against any other stored key. Insertion costs O(len(word)) whether the trie holds ten words or ten million. That independence from n is the property everything else in this article rests on.

The other property is that every prefix is a node. So search and starts_with are the same walk, and differ only in what they check at the end:

    def search(self, word):
        node = self._walk(word)
        return node is not None and node.is_word

    def starts_with(self, prefix):
        return self._walk(prefix) is not None

That single boolean is the entire difference between "car is a word" and "ca is a place we pass through", and it is the whole of LeetCode 208. Autocomplete falls out too: walk to the prefix node, then collect the subtree under it. autocomplete('rom') on the seven-word tree in the module returns ['romane', 'romanus', 'romulus'], and the cost is the walk plus the size of the answer - nothing proportional to the dictionary.

The chains that carry no information

The price is space. Those seven Latin words - romane, romanus, romulus, rubens, ruber, rubicon, rubicundus - take 28 nodes, and most of them are single-child chains. Once you are standing at rubicund there is nowhere else to go; the five nodes spelling out undus are five pointer hops doing the work of one strcmp, and each one is a dict allocation and a cache miss.

A radix tree - Morrison's PATRICIA tree, 1968 - collapses each of those chains into a single edge labelled with the whole substring. Nodes become branch points; strings live on the edges. The same seven words take 14 nodes, half as many, and on a 32-word English list it is 115 nodes down to 43, a 63% cut. The trick that keeps lookups fast is to key each node's children by the first character of the edge label, so choosing an edge is still one dict lookup and never a scan over siblings.

The split

Compression costs you one thing, and it is worth doing by hand once. Walking down to insert, one of three things happens: the edge label is consumed and we descend, the word is consumed and we mark the node, or the two disagree in the middle of a label. That last case is the split.

            label, child = edge
            k = common_prefix_len(label, word[i:])
            if k == len(label):
                node, i = child, i + k     # edge fully consumed, descend
                continue
            # diverged inside the label: split it at k

            mid.children[label[k]] = (label[k:], child)   # old tail reparents
            node.children[first] = (label[:k], mid)       # shared head stays here
            i += k
            if i == len(word):
                mid.is_word = True
            else:
                mid.children[word[i]] = (word[i:], RadixNode(is_word=True))
            return

The shared head becomes a new internal node, the old edge keeps its tail and hangs under it, and the rest of the new word becomes a sibling. Nothing is copied, nothing else in the tree moves - a split is a local, O(1) pointer rearrangement. Building the seven-word tree needs exactly six of them.

That is what makes a radix tree more than a compressed trie you build once and freeze. It stays compressed while it is being written to, which is exactly what an online cache needs.

Most specific wins

Every packet leaving a machine gets matched against a routing table, and the rule is "most specific wins": 10.20.30.0/24 beats 10.20.0.0/16 beats 10.0.0.0/8 beats the default route. Put the prefixes in a binary trie over the address bits and that rule becomes something you get for free: the deepest marked node on the path from the root. Remember the last marked node you walked past, and when the walk falls off the tree, that is your answer.

Two consequences matter more than the constant factor. Rule order is irrelevant, because specificity is depth and depth does not depend on insertion order - so the table can be edited without re-sorting anything. And the walk is bounded by the address, not the table: at most 33 nodes for IPv4, whether the table holds the five routes in my example or the roughly one million a core router carries. The linear scan it replaces touches every rule. That is why hardware routing tables are tries.

The same tree, serving tokens

An LLM inference server has a structurally identical problem. The attention state for token i depends only on tokens 0..i, so two requests with an identical prefix have an identical KV cache for that prefix. Keep the prefixes in a radix tree whose "characters" are token ids and whose edge labels are runs of tokens, and prefix sharing becomes a lookup. That is sglang's RadixCache, and it is what the RadixAttention paper is named after.

In the module's worked example, three requests sharing a 40-token system prompt ask for 160 tokens in total and occupy 68 KV slots - 57% saved. A fourth request that diverges in the middle of a cached run triggers exactly the split above, which is the point: the boundary between "shared" and "not shared" does not have to exist when the run is stored, only when someone needs it.

Two details are where the theory meets the hardware. First, KV memory is paged, so a match is truncated to a whole number of pages:

        tokens = tokens[: len(tokens) // self.page_size * self.page_size]

Ten tokens in common with page_size=4 gives you eight reusable tokens. The last two are byte-for-byte identical and still get recomputed, because they share a page with a token the two requests disagree about. One line, and it is the difference between the cache hit rate you measure and the one you expected.

Second, eviction is LRU over leaves only:

        while freed < n_tokens:
            cands = self.leaves()
            if not cands:
                break
            victim = min(cands, key=lambda n: n.last_access)
            del victim.parent.children[self._child_key(victim.key)]
            freed += len(victim.key)

An interior node is a prefix that something else is still using, so it cannot be freed no matter how old it is. A cold branch peels away one node at a time, and each removal may turn its parent into a leaf, so the branch eventually disappears from the tip inwards - while the hot system prompt near the root survives everything hanging off it. Nobody wrote that policy; it falls out of the tree shape. Freeing 16 tokens in my example takes the tree from 80 nodes to 64 and never touches the root path.

Complexity

With L the key length, n the number of keys, T the total characters stored and sigma the alphabet size:

Operation                        Trie            Radix tree
-------------------------------  --------------  ----------
insert / search / startswith     O(L)            O(L)
autocomplete, k results          O(L + k)        O(L + k)
nodes needed                     O(T)            O(n)
longest prefix match, b-bit key  O(b)            O(b)
linear scan of the same table    O(n · L)        -
wildcard search, d dots          O(sigma^d · L)  -
split on insert                  -               O(1)

The interview version

LeetCode 208 is the trie itself, and the line that matters is search versus startsWith. LeetCode 211 adds a '.' wildcard, and it is the problem that proves a trie is not a compressed hash map:

    def _dfs(self, node, word, i):
        if i == len(word):
            return node.is_word
        ch = word[i]
        if ch != ".":
            nxt = node.children.get(ch)
            return nxt is not None and self._dfs(nxt, word, i + 1)
        return any(self._dfs(child, word, i + 1) for child in node.children.values())

A '.' means there is no key to look up, so the walk forks into every child and the lookup becomes a DFS. It is still bounded - the depth is the pattern length - but it is no longer a single path, and no hash table can do this at all. LeetCode 648 is longest prefix match on English: walk until you hit a marked node and stop, which is the routing table with word roots instead of subnets.

Where this goes

The pattern to carry forward is that a trie turns "compare against everything" into "walk the key". Routing tables, autocomplete, IP lookup, prefix caches in an inference server and the compressed key indexes inside a modern database are all the same tree with different alphabets. When we get to RadixAttention, none of it will be new - it is this structure, plus an eviction heap.

Next up is string matching, where the question changes from "which stored key does this share a prefix with" to "where inside this text does a pattern occur", and prefixes come back in a completely different disguise.
