100 Days of Python - day 24

hash set 可以告訴你 rubicon 在不在字典裡，但它沒辦法告訴你 rubicon、rubicundus、ruber 這三個字開頭是一樣的 —— 因為 hash 就是設計來把這個資訊銷毀掉的。如果你真正想問的是「這些字串之間有什麼共通的地方」，你需要一個會 把前綴留下來的結構，那個結構就是 trie。

昨天的二分搜尋最後停在 sglang 的 galloping prefix match。今天講的就是那個 match 在走的那棵樹，而且最後會走到同一個 cache 的上一層抽象：讓 inference server 在兩個 request 共用同一段 system prompt 時，不用把那段 prompt 算兩次的東西。

一個字元一個節點

trie 的做法是一個字元一個節點。root 是空字串，每條邊掛一個字元，從 root 往下走就把字串拼出來。節點上的一個布林值 is_word 負責說明「走到這裡的這個字串」有沒有真的被插入過。

class TrieNode:
    __slots__ = ("children", "is_word")

    def __init__(self):
        self.children = {}      # character -> TrieNode
        self.is_word = False


class Trie:
    def insert(self, word):
        node = self.root
        for ch in word:
            nxt = node.children.get(ch)
            if nxt is None:
                nxt = TrieNode()
                node.children[ch] = nxt
            node = nxt
        node.is_word = True

值得注意的是這個迴圈裡沒有的東西：沒有 hash、沒有 resize、沒有 collision、也沒有跟任何其他 key 做比較。不管 trie 裡面已經放了十個字還是一千萬個字，插入都是 O(len(word))。這個「與 n 無關」的性質，是這篇文章後面每一段的 地基。

第二個性質是：每一個前綴都是一個真的節點。所以 search 和 starts_with 走的是同一條路，差別只在最後檢查什麼：

    def search(self, word):
        node = self._walk(word)
        return node is not None and node.is_word

    def starts_with(self, prefix):
        return self._walk(prefix) is not None

那一個布林值就是「car 是一個字」跟「ca 只是路過」之間的全部差別，也就是 LeetCode 208 的全部內容。autocomplete 也是順便的：走到前綴節點，然後把底下的子樹收集起來。在那棵七個字的樹上，autocomplete('rom') 回傳 ['romane', 'romanus', 'romulus']，成本是「走下去」加上「答案有多長」—— 沒有任何一項跟字典大小成正比。

不帶任何資訊的那些鏈

代價是空間。那七個拉丁字 —— romane、romanus、romulus、rubens、ruber、rubicon、rubicundus —— 要用掉 28 個節點，而且大部分都是單一子節點的鏈。當你站在 rubicund 上時，根本沒有別條路可以走；拼出 undus 的那五個節點，做的事情等同於一次 strcmp，但每一個都是一次 dict 配置和一次 cache miss。

radix tree（Morrison 在 1968 年提出的 PATRICIA tree）把每一條這樣的鏈壓成一條掛著整段子字串的邊。節點變成 分歧點，字串則活在邊上。同樣那七個字只需要 14 個節點，剛好一半；換成 32 個英文單字的清單，是 115 個節點降到 43 個，少了 63%。讓查詢維持一樣快的關鍵是：每個節點的 children 用邊標籤的第一個字元當 key，所以選邊仍然是一次 dict 查詢，永遠不用掃 sibling。

split

壓縮只讓一件事變難，而且這件事值得親手推一次。往下走要插入時，只會發生三種情況：邊標籤被吃完（往下走）、要插入的字 被吃完（把節點標成 word），或是兩邊在標籤中間就分岔了。第三種就是 split。

            label, child = edge
            k = common_prefix_len(label, word[i:])
            if k == len(label):
                node, i = child, i + k     # edge fully consumed, descend
                continue
            # diverged inside the label: split it at k
            mid = RadixNode()
            mid.children[label[k]] = (label[k:], child)   # old tail reparents
            node.children[first] = (label[:k], mid)       # shared head stays here
            i += k
            if i == len(word):
                mid.is_word = True
            else:
                mid.children[word[i]] = (word[i:], RadixNode(is_word=True))
            return

共用的那個頭變成新的內部節點，舊的那條邊留著自己的尾巴掛到它下面，新字剩下的部分變成兄弟。沒有任何東西被複製， 樹上其他地方也完全沒有動 —— split 就是一次局部的、O(1) 的指標重接。那棵七個字的樹，剛好需要六次。

這也是 radix tree 不只是「壓縮過一次就凍起來的 trie」的原因：它在被寫入的過程中維持壓縮狀態，而這正是一個線上 cache 需要的性質。

最明確的規則獲勝

每一個離開機器的封包都要拿去比對路由表，規則是「最明確的獲勝」：10.20.30.0/24 勝過 10.20.0.0/16，勝過 10.0.0.0/8，勝過預設路由。把這些 prefix 放進一棵以位址位元為字元的 binary trie，這條規則就變成免費的東西： 從 root 往下這條路徑上，最深的那個被標記的節點。走的時候記住最後一個經過的標記節點，走到樹外面時，那就是答案。

有兩個推論比常數項重要。第一，規則順序完全不重要，因為「明確程度」就是深度，而深度跟插入順序無關 —— 所以這張表 可以隨便編輯，不用重新排序任何東西。第二，這趟走訪的長度取決於位址而不是表的大小：IPv4 最多 33 個節點，不管表裡 是我範例中的五條路由，還是核心路由器上大約一百萬條。它取代掉的線性掃描則是每一條規則都要碰。這就是硬體路由表都是 trie 的原因。

同一棵樹，改成服務 token

LLM inference server 遇到的是結構上一模一樣的問題。token i 的 attention state 只跟 token 0..i 有關，所以兩個 prefix 相同的 request，那段 prefix 的 KV cache 也一定相同。把 prefix 放進一棵「字元是 token id、邊標籤是一串 token」 的 radix tree，prefix sharing 就變成一次查詢。這就是 sglang 的 RadixCache，也是 RadixAttention 這個名字的由來。

在這個模組的範例裡，三個共用 40 個 token 的 system prompt 的 request，總共要了 160 個 token，只佔用 68 個 KV slot，省下 57%。第四個在已快取的 run 中間分岔的 request，觸發的就是上面那個 split —— 這正是重點：「共用」與「不共用」 之間的邊界，不需要在存進去的當下就存在，只需要在有人需要它的時候存在。

有兩個細節是理論撞上硬體的地方。第一，KV memory 是分頁配置的，所以 match 會被截斷成整數個 page：

        tokens = tokens[: len(tokens) // self.page_size * self.page_size]

共同的 10 個 token，在 page_size=4 之下只有 8 個可以重用。最後那兩個 token 一模一樣，還是得重算，因為它們跟 一個兩邊不一樣的 token 待在同一頁裡。就這一行，卻是「你量到的 cache 命中率」跟「你以為的命中率」之間的差距。

第二，eviction 是只對 leaf 做 LRU：

        while freed < n_tokens:
            cands = self.leaves()
            if not cands:
                break
            victim = min(cands, key=lambda n: n.last_access)
            del victim.parent.children[self._child_key(victim.key)]
            freed += len(victim.key)

內部節點是「還有別人在用的 prefix」，所以不管它多舊都不能砍。一條冷掉的分支會一個節點一個節點地剝掉，每砍掉一個 leaf，它的 parent 就可能變成新的 leaf，所以整條分支是從末端往內慢慢消失的；而靠近 root 的熱門 system prompt，會 活得比掛在它下面的所有東西都久。沒有人寫過這條政策，它是從樹的形狀掉出來的。我的範例裡釋放 16 個 token，樹從 80 個節點變成 64 個，root 那條路徑一次都沒被碰到。

複雜度

L 是 key 長度，n 是 key 的數量，T 是存進去的總字元數，sigma 是字母表大小：

操作                                Trie            Radix tree
----------------------------------  --------------  ----------
insert / search / startswith        O(L)            O(L)
autocomplete，k 筆結果              O(L + k)        O(L + k)
需要的節點數                        O(T)            O(n)
longest prefix match，b 位元的 key  O(b)            O(b)
同一張表用線性掃描                  O(n · L)        -
萬用字元查詢，d 個點                O(sigma^d · L)  -
插入時的 split                      -               O(1)

面試版本

LeetCode 208 就是 trie 本身，重點在 search 跟 startsWith 的差別。LeetCode 211 加上一個 '.' 萬用字元，而它正是 證明「trie 不是壓縮版 hash map」的那一題：

    def _dfs(self, node, word, i):
        if i == len(word):
            return node.is_word
        ch = word[i]
        if ch != ".":
            nxt = node.children.get(ch)
            return nxt is not None and self._dfs(nxt, word, i + 1)
        return any(self._dfs(child, word, i + 1) for child in node.children.values())

'.' 代表沒有 key 可以查，所以這一步要分岔到所有 child，查詢就變成了 DFS。它仍然是有界的（深度就是 pattern 長度），但已經不是一條單一路徑了，而且 hash table 根本做不到這件事。LeetCode 648 則是英文版的 longest prefix match： 一路走到遇見被標記的節點就停，就是把子網路換成字根的路由表。

這條線往後接到哪裡

要帶走的模式是：trie 把「跟所有東西比較」換成「沿著 key 走一趟」。路由表、autocomplete、IP 查表、inference server 的 prefix cache，還有現代資料庫裡壓縮過的 key index，全部都是同一棵樹配上不同的字母表。等到講 RadixAttention 的時候，你會發現沒有什麼新東西 —— 就是這個結構，再加一個 eviction 用的 heap。

下一篇是字串比對，問題會從「這個 key 跟哪個已存的 key 共用前綴」變成「這個 pattern 出現在文字的哪裡」，而前綴會用 一個完全不同的偽裝再回來一次。

LeetCode 208 - Implement Trie (Prefix Tree)（實作 Trie（前綴樹））

題目。 實作一個 trie，提供三個方法：insert(word) 存入一個字、search(word) 只有在那個字 被完整插入過時回傳 True、startsWith(prefix) 只要有任何一個字以該前綴開頭就回傳 True。

輸入／輸出。 評測會送一連串操作與參數進來，比對每次的回傳值；建構子不吃參數。

範例。 執行 insert("apple") 之後：search("apple") 是 True、search("app") 是 False、 startsWith("app") 是 True；再 insert("app")，search("app") 就變成 True。

限制。 1 <= len(word) <= 2000，只有小寫英文字母，總共最多 3 * 10^4 次呼叫。重點在於 不論存了多少字，search 和 startsWith 都必須是 O(len(word))。

LeetCode 211 - Design Add and Search Words Data Structure（設計加入與搜尋單字的資料結構）

題目。 做一個 WordDictionary，提供 addWord(word) 與 search(word)。*搜尋*字串裡可以出現 .，每個 . 可以對應任何一個字母；只要存過的字裡有任何一個能對上，search 就回傳 True。

輸入／輸出。 和 LeetCode 208 一樣的操作串列格式。

範例。 先加入 "bad"、"dad"、"mad"。那麼 search("pad") 是 False、search("bad") 是 True、search(".ad") 是 True、search("b..") 也是 True。

限制。 1 <= len(word) <= 25；加入的字只有小寫字母，查詢的字可以有小寫字母和 .，而且 最多兩個 .；最多 10^4 次呼叫。就是這個「最多兩個點」的限制，讓在 trie 上分岔的 DFS 還 跑得動。

LeetCode 648 - Replace Words（單字替換）

題目。 給一組字根（roots）和一個句子。句子裡只要某個單字以某個字根為前綴，就要換成那個字根； 如果有多個字根都符合，取最短的那個。沒有字根對得上的單字保持原樣。

輸入／輸出。 輸入是 dictionary（字根串列）與 sentence（單字之間以單一空白分隔），輸出是 改寫後的句子。

範例。 dictionary = ["cat","bat","rat"]、 sentence = "the cattle was rattled by the battery" → "the cat was rat by the bat"。

限制。 1 <= len(dictionary) <= 1000，每個字根長度 1..100，句子最長 10^6 個字元，全部 都是小寫字母與單一空白。句子這個長度正是「每個單字都去試過所有字根」會太慢、而走一次 trie 才是 正解的原因。
